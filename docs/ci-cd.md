# Onyx CI/CD: PR to production without handoffs

Riley authorized routine PR merges without per-PR approval (2026-11-11). Since 2026-11-14 ("one user, move fast") a PR
runs only one fast check, the full test suite runs on a schedule, and testing and deploying are independent: target
PR to merge in about a minute.

## Flow

1. **PR opens** (any agent, same repo, owner identity, not draft). `Autonomous CI` runs the single required check `offline-checks` (Python syntax validation only; no behavioral tests). Nothing else runs per PR; Vercel builds `master` only.
2. **Merge train** (`.github/workflows/merge-train.yml`, `tools/merge_train.py`) runs on PR events, on CI completion, and every 15 min. Per pass it:
   - merges every PR whose required check is green on its exact head, oldest first (squash, pinned to that head SHA; GitHub still enforces branch protection, there is no admin bypass);
   - merges a PR that is behind master as it is: protection is not strict, so there is no rebase-and-retest round. Two PRs that each pass but break together are caught by the Production build and the scheduled tests.
3. **Production**: Vercel deploys master on merge; its build only compiles (type check and lint are skipped there since 2026-11-14 and run in the scheduled suite), so a type error can deploy. `post-merge.yml` waits for the `Production` deployment of that commit (not for tests), then runs the production smoke test (one retry). A failed build is pinned on the commit that broke it, and only on evidence (`culprit_of`, Codex review 2026-11-14): the oldest commit of the unbroken run of failed builds is reverted when that run ends at a good build. When the history cannot name the commit (a merge in the run with no build, because Vercel skips a commit superseded by a newer push; a deployment that is `inactive` = canceled, `error` or still pending; a deploy that never finished; no good build within 8 commits) the result is `halt`: nothing is reverted, a `train-halt` issue asks for a diagnosis from the Vercel log, and closing it resumes the train. When master moves on while a merge waits for its deploy: its smoke test would run this commit's tests against the newer production build, so the result is `skipped` and the newer merge's verification smoke-tests what production serves.

   **Smoke provenance (DEL-02, 2026-11-16).** The smoke test loads the production alias (generated deployment URLs sit behind Vercel's sign-in) and the alias moves to every newer deployment, so each run is bound to one commit. `merge_train.py smoke-target` runs before any checkout or credential use and refuses a commit that is not on master or has no successful Production deployment; the tests of that exact commit are then checked out, and the signed-in `/api/version` (commit + `VERCEL_URL`) must show that commit right after login, as soon as the session exists and before anything on Today is checked, so a commit that breaks Today itself still leaves both records (`e2e/auth.setup.ts`, which stops the run on a mismatch), and after every test (`e2e/provenance.teardown.ts`). GitHub's deployment records cannot tell a superseded deployment from the live one (Vercel leaves a single `success` status on each, checked 2026-11-16), so "live" is never read from them. Two modes. **Post-merge** (`post_merge: true`): verify hands both attempts the commit and its deployment (`expected_sha`, `deployment_url` = the GitHub deployment's `environment_url`); the target is refused up front when a newer master head already has a successful deployment (production no longer serves it), and both records must name exactly that deployment (a record without one is not confirmed). A record that names a deployment of the same commit which is none of that commit's GitHub Production deployments means `/api/version` and the deployment records no longer name hosts the same way: that run is `unverified` with a "Smoke provenance broken" annotation (it fails, and after the retry the train halts), never a quiet deferral that would leave every later merge unverified. **Scheduled** (every 6 h and `workflow_dispatch`): the newest master commit with a successful Production deployment, starting at `expected_sha` or master head when the job runs (a head still deploying or with a failed build falls back to its parent), matched on the commit alone; nothing is attributed. Verdicts (`smoke-verdict`, from the workflow's own commit): `pass` / `fail` = that target at both ends; `deferred` = production served something else (alias moved, redeploy, Vercel rollback) or the tests passed but the target was not confirmed: pending verification, never a pass; `unverified` = tests failed and the target was not confirmed: never attributed. The job fails on `fail` and `unverified`; Playwright stops the suite after 8 minutes in CI and the test step stops after 10, inside the job's limit, so a hanging production ends as a failed run the verdict reads, not as a cancelled job (cancelled = superseded by a newer run for the same commit = pending); a scheduled run also fails, with an error annotation, on any deferral except production moving on to a newer master commit (every deferral is annotated), so a Vercel rollback, a broken provenance read or an unresolvable target cannot keep the tripwire green. The `receipt` job records the post-merge result as the commit status `post-merge/smoke` (success / failure / pending) with the run link, on master commits only, and never writes "pending" over an earlier exact pass or fail (readers also skip pending rows). It writes that status only while the repository variable `SMOKE_RECEIPT_STATUS` is `on` (see the last sentences of this item); while it is off the job summary is the only receipt, nothing is written and every smoke failure halts with an issue, never a revert (a revert needs its failure recorded as a receipt, which a queued rollback PR is reconciled against). It reverts only a commit whose two attempts failed on its own deployment while its parent's receipt is a pass from the last 3 hours (the suite reads live data, so an older pass does not rule out changed data); a parent that was superseded, deferred, already failed or passed earlier, an unverified failure, a retry that never ran, or a receipt that could not be written halts with an issue and no revert. A smoke failure is "already fixed" (no revert, stale rollback PR closed) once an exact smoke pass is recorded AFTER that failure, on a newer master commit containing it or on a later run of the commit itself. The failure's time is the receipt job's `observed_at` (handed to `rollback --failed-at`) or, for a queued rollback PR, the commit's newest exact failure receipt; a pass recorded before it never counts, so an exact failure, a pass, then a run that failed twice without confirmed provenance still halts (the old pass stays the newest exact receipt, since pending never overwrites it). The same check runs before a halt without a revert: when a newer master commit containing the change built (a halt on a failed build), or an exact smoke pass was recorded after the halt's failure, production works again and no halt issue is filed. A halt with no failure time (its receipt could not be written, a deploy that never finished) is always filed. `post-merge/smoke` is a smoke receipt, not a deploy signal: it is `pending` on every merge that was superseded or deferred and `failure` on an exact smoke failure, so once it is written the combined commit status of master no longer says whether the deploy succeeded: a reader that wants the deploy result reads the `Vercel` entry of `statuses[]` in `GET /commits/master/status` (or the deployment), never the combined `state`. GitHub's combined `state` counts every context, so no context name keeps a receipt out of it: `SMOKE_RECEIPT_STATUS` is set to `on` (`gh variable set SMOKE_RECEIPT_STATUS --body on`) only after every reader of master's combined status reads the `Vercel` context (the personal-agents devops and onyx-pm specs, with the devops page republished), and deleting the variable turns the receipts off again. Only the three smoke secrets reach the smoke workflow (no blanket secret inheritance), its token is read-only, both checkouts drop the token, and nothing is uploaded. Every run's job summary is its receipt (mode, expected commit + deployment, what production served before and after, verdict).
4. **Failure**: the train halts (open `train-halt` issue), a `rollback/<sha>` revert PR is opened and labeled `rollback`; the train merges it (checks still apply), its `Closes #N` closes the halt issue and the train resumes. The revert is itself verified like any release. Never reverts a revert.
5. **Post-deploy test failures** (the `offline-tests` job of Post-merge verify, a red `Scheduled tests` run, a red speed budget) never revert and never halt the train: deploys and merges keep going. The cloud watchdog raises them on its issue (`scheduled-tests-failed`, `speed-budget-broken`) and devops fixes forward with a normal PR. Only a failed Production build or a smoke test that fails twice reverts or halts.

## Tests run on a schedule

`scheduled-tests.yml` runs the rest of the suite against master every 30 minutes: `frontend-types` (all `frontend/tests/*.test.cjs` and `scripts/test-*.mjs`, `tsc`, a compile-only `next build`, the Today browser regressions), `lint` (`npm run lint`, which the Vercel build skips), `stats-tests` (`tests/run_offline_tests.py`, no secrets) and `focus-policy`. A commit that already passed is skipped in seconds. A failure never blocks a merge or a deploy: the run goes red, the cloud watchdog raises it (`scheduled-tests-failed`), and the fix ships as a normal PR. `focus-ios`, `kindle-harvester-test` and `rocketmoney-harvester-test` run after merge (push to master, path-filtered), not per PR. Run the suite by hand: Actions > Scheduled tests > Run workflow (`force` re-tests a commit that passed).

## Merge ownership and exclusions

Branches under `builder/` belong exclusively to the local feature worker in `personal-agents/local/feature_worker.py`. The train skips them even when ready and green: it never selects them for an update, CI dispatch or merge. Only the worker has the exact-head review and type-check receipt, and its merge uses `--match-head-commit`. Marking a PR ready does not pin its head; letting the train independently merge a later head would bypass that receipt. Land this exclusion before activating the worker's exact-head guard. If the worker is unavailable, the PR waits for worker recovery or an explicit owner decision; the train does not take over. Ordinary feature branches and `rollback/` retain their existing rules.

Drafts, forks, PRs from anyone but the owner login, PRs with the `hold` label, conflicts, any red or running check (the Vercel Preview Comments check is ignored), more than 100 files, and any PR touching a protected path: `.github/**`, the train itself, auth/login/token/session code, `middleware.ts`, RLS/owner-read SQL, `.env*`, `vercel.json`, `CODEOWNERS`.

## Conventions

- **Tests are discovered, not listed.** Add `frontend/tests/<name>.test.cjs` (run with `node --test`) or `frontend/scripts/test-<name>.mjs` (files ending `-ui.mjs` need a browser and are not auto-run); `scheduled-tests.yml` picks them up. Do not edit the workflows to add a test line: they are protected paths, and every PR appending to the same lines conflicts. Do not run it before merging, not even locally (Riley, 2026-11-15): the scheduled suite runs it against each deployed revision, and a red run comes back as a fix PR.
- **Stop a PR:** `hold` label or draft. **Stop everything:** open an issue labeled `train-halt`, or disable the "Merge train" workflow.
- **Audit:** every action is in the run summary of Merge train / Post-merge verify and as a comment on the PR; halts and reverts are issues/PRs; git history is the release log.
- **Rollback drill** (exercise the path without breaking prod): Actions > Post-merge verify > Run workflow, `sha` = any harmless commit on master (a docs-only one), `drill` = true.

## Security notes

Uses only the workflow `GITHUB_TOKEN` (no PAT, no stored secrets in the train). `pull_request_target` is safe here because nothing from the PR is checked out or executed; fork PRs are ignored. Opening the revert PR needs Settings > Actions > General > "Allow GitHub Actions to create and approve pull requests"; until enabled, a failed release halts the train, pushes the revert branch and files an issue with the one-click compare link.

## Postdeployment-only automated tests (Riley, 2026-11-15)

The existing required `offline-checks` status now parses Python only; it is not a test pass. Branch protection and security settings are unchanged. Vercel compilation, authentication, signing and permission controls remain. Behavioral/offline tests run after evidence of a successful Production deployment for the exact revision. Post-merge verification starts the credential-free suite; the 30-minute schedule retries deployed revisions. A skipped/deferred run is not evidence of a passing test. Production smoke remains after deployment, and existing live write tests stay manual opt-in only. No automated tests were run before deploying this policy change, per Riley's instruction; independent source review is the validation before publication.

The live HRV matrix check remains daily/manual, not every UI release, to avoid additional production database load. Model-retraining data-integrity checks and iOS entitlement/signing checks are separate safety/build workflows and are unchanged.
