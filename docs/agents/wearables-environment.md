## Garmin

- **Garmin sleep timestamps:** `garmin_sleep.sleep_start` / `sleep_end` are stored as true UTC instants (`sleepStartTimestampGMT` from the API). The previously-used `*Local` field encoded the local clock as UTC, shifting timestamps by ~4-5h.
- **Garmin empty days (2026-11-11):** Garmin returns a daily summary for every day, worn or not (goals, profile BMR, stress -1/-2, `sedentary_seconds` 86400), so `garmin_daily_summary` gets a row per day either way. "Worn" = steps > 0 or any heart-rate / body-battery / SpO2 / respiration value (`daily_summary_has_wearable_values` in `garmin_etl.py`, `GARMIN_WEARABLE_FILTER` in `lib/status-freshness.ts`; keep the two in step). A run whose fetched days are all unworn (no worn summary, no sleep / HRV / activity rows) logs a `partial` heartbeat whose message starts `No wearable data`, and the `/status` Garmin card keys freshness on the newest worn day, so an unworn watch shows red after 3 days instead of green. Test: `tests/test_garmin_empty_days.py`.
- **Garmin acute / chronic training load (2026-11-14):** `pds.garmin_training_status.acute_training_load` / `chronic_training_load` come from the training-STATUS endpoint (`garmin.get_training_status`, `mostRecentTrainingStatus.latestTrainingStatusData.<device>.acuteTrainingLoadDTO.dailyTrainingLoadAcute / dailyTrainingLoadChronic`), not the readiness payload the rest of the row (and `raw_json`) comes from. Only a device record whose `calendarDate` is the synced day counts: the endpoint reports the most recent status as of the date, so for a day the watch did not sync it can return an earlier day's record, which is treated as no data. A missing endpoint's columns are left out of the upsert, never sent as NULL. Before this both columns were NULL in every row (656 on 2026-11-14). History: `python garmin_etl.py --backfill-training-status 930` (two calls per day, writes a `garmin|training_status_backfill` heartbeat). The analysis keeps one copy of each (`acute_training_load`, `chronic_training_load`; the view's `garmin_` copies are dropped at the join). Test: `tests/test_garmin_training_load.py`.

## Eight Sleep

- **Eight Sleep bed / room temperature self-heals (2026-11-12, hardened 2026-11-13).** Eight Sleep's `/intervals` collection returns only the 10 most recent sessions, so after a 10+ day pause the gap nights have no `median_bed_temp` / `median_room_temp`. After every normal sync `eight_sleep_etl.py:self_heal_temps` reads `eight_sleep_trends` rows of the last 60 days (today excluded) with a NULL temp and fills them from `/intervals/{mainSessionId}`: at most 20 lookups per run (`--selfheal-max`, 0 = off), one lookup per session even when both bed sides share it, only NULL columns are written, and when more sessions are waiting than the cap allows the starting point rotates daily. The sync itself never sends a NULL temp for a night it has no interval for (`_split_rows_by_temp`), so a wide `--days` catch-up cannot erase stored temps. Heartbeats: `eight_sleep|temp_selfheal` on every run (`records_synced` = rows healed, 0 = nothing to heal); a failed lookup or scan never fails the sync but turns both that row and the `eight_sleep|trends` row (the `/status` card) `partial` with the counts. Older gap: `gh workflow run eight-sleep-etl.yml -f selfheal_days=N`; `eight_sleep_temp_backfill.py [--apply]` is the same function with no look-back bound. Test: `tests/test_eight_sleep_selfheal.py`. **Dates (2026-11-16, `docs/eight-sleep-date-contract.md`):** `calendar_date` is the trends API `day` unchanged, the wake-up date in the stationary bed's zone (`EIGHTSLEEP_TIMEZONE`; all three `onyx_*` dates are copies of it, never re-dated in SQL); interval values attach to a day by its `mainSessionId` (else its only session; a day with several sessions and no main id gets none and keeps its stored temps), never by their own timestamp, no row is written without a trend day, an `/intervals` item without an id, or a run where no interval pairs although sessions fall in its window, turns `partial`, and a session reporting a zone with another UTC offset turns the run `partial` (`GUARD eight_sleep_bed_tz:`). `eight_sleep_temp_backfill.py --compare` is the read-only, counts-only check of stored temps against each row's main session (whole table, paged; `--max-lookups N` raises the 1000-lookup cap, since an identical re-run repeats the same lookups; history is clean only when `clean` is true: complete, `differ = 0` and no unverifiable row; it needs the Supabase and Eight Sleep credentials in the shell, which the PC does not hold (no `.env`), and never runs from Actions, whose log is public; keep its output private). The self-heal logs counts only, never a date, a temperature or a session id, reports a failed scan, lookup or crash by its type and HTTP status or database code only (`_safe_error`, never the error text), and turns the HTTP client loggers down while it runs (`quiet_http_logs`: httpx logs every request URL at INFO, and the heal's URLs carry the ids and the healed row's date). Test: `tests/test_eight_sleep_date_contract.py`.

## WHOOP steps and energy

- **WHOOP daily steps (2026-11-13, `sql/whoop_cycles_step_count.sql`).** WHOOP's v2 API returns `step_count` on every cycle (top level of the cycle, not inside `score`; null, never 0, when there is no step data), so `whoop_etl.py` reads cycles from `/v2/cycle` (same integer cycle id and score fields as `/v1/cycle`; profile and body measurement also moved to `/v2`, with a `/v1` fallback on 404/410) and stores it in the nullable `pds.whoop_cycles.step_count`. It exists because the Garmin watch is rarely worn (last on 2026-10-02) while the strap is worn daily. History was filled on 2026-11-13: all 740 cycles back to 2024-10-27 carry a count. **Which day: a cycle runs from one sleep onset to the next, so its steps are the waking day after that onset, dated from the cycle's OWN start** (`hrv_alignment.cycle_waking_day`, mirrored in `lib/steps.ts:whoopStepsDay`): the −6 h behavioral-day rule applied 12 h after the onset in the cycle's local time (`start_time` + `timezone_offset`, ET when missing), i.e. the date of local start + 6 h. For a night-time onset that is `onyx_behavioral_date` + 1, like strain and kilojoule; an onset between 06:00 and 18:00 local counts its own clock day. Cycles landing on the same day are summed. Do not use "main cycle per behavioral date + 1": when an onset is after 06:00 two cycles share a behavioral date, and longest-wins put the wrong cycle's count on the wrong day (review 2026-11-14; live: 7 such dates, 1 wrong value and 7 dropped days, all fixed by the own-start rule, which puts 0 cycles on a shared day and keeps all 739 closed cycles). Checked on live data: same clock day vs Garmin r = 0.949 over 507 days; the earlier offset scan (cycle dated D vs Garmin day D + 1 r = 0.94, every other offset from D − 2 to D + 3 between −0.11 and 0.22; WHOOP running distance r = 0.75 at D + 1, under 0.14 elsewhere) still holds. The open cycle holds the steps so far and is overwritten hourly until it closes. **Page:** the Steps tile and Daily Steps chart on `/activities` show, per day, the LARGER of the Garmin and WHOOP counts (`lib/steps.ts:mergeDailySteps`; WHOOP on a tie), because the watch is often worn for part of a day (Garmin under half of WHOOP on 112 of 505 shared days); one device per day, never summed; each bar, the tile and the chart badge name the device; a day that includes the open cycle is marked "so far". Display only: the HRV pipeline uses WHOOP alone. `step_count` is in `WHOOP_CYCLE_COLS`, and the chat's `query_whoop_cycles` rows carry `steps_day`. No new `/status` card: it rides on the WHOOP card's hourly `whoop|full_sync` heartbeat. **HRV pipeline:** the matrix view is NOT changed; `hrv_analysis.merge_whoop_steps_features` merges the column in pandas as `whoop_steps` (each closed cycle dated by `hrv_alignment.cycle_waking_day`, cycles on one day summed; a day with an open cycle or a null count stays NaN, nothing is zero-filled; loaded in its own fail-open read). It is a separate column from Garmin's `total_steps` (two devices, never blended), is in `NOT_FORECAST_PREFIXES` (today's cycle is still open when the evening forecast runs) and is THE steps `CONTINUOUS_TREATMENTS` median split (family behavior). Garmin `total_steps` was dropped as a causal treatment on 2026-11-14 (one signal per FDR family, like the caffeine rule; the watch's partial-wear days make it the weaker measurement) and stays a matrix column for Spearman, the forecast and the alignment guard. The runtime guard (`al.check_rekey_directions`) and `tests/test_hrv_alignment_live.py` fail if WHOOP steps ever line up with Garmin steps on an adjacent row. **Deep re-reads:** `gh workflow run daily-etl.yml -f days=800 -f whoop_cycles_only=true` runs `whoop_etl.py --cycles-only` (cycles endpoint only, Garmin job skipped, heartbeat `whoop|cycles_backfill`; a failed cycles read or profile check writes a `failed` row there and exits 1). Use it instead of a large plain `days`: that also re-reads years of Garmin days and runs `whoop_tz_backfill` over the whole window, which on 2026-11-13 proposed 21 new `user_tz_log` rows for old trips the log already covers (dry run; nothing was inserted). Fixed 2026-11-14: the pass now checks each cycle against the log at its own instant, and a full-history check finds 0 cycles to propose. Tests: `tests/test_whoop_steps.py`, `frontend/tests/steps.test.cjs`.
- **"Calories burnt" / daily energy expenditure: WHOOP is the canonical source, not Garmin.** Any UI/query/feature surfacing TDEE reads `pds.whoop_cycles.kilojoule` and converts kJ → kcal via `/4.184`. Tag each cycle to its ET cycle date via the `+12h` rule (matches the timezone convention, database.md). Don't substitute Garmin's `total_kilocalories` even though it covers the same concept — Garmin's BMR + active calc may diverge, and Riley has confirmed WHOOP as the source of record on Onyx. Implementation reference: `frontend/src/lib/queries.ts:getWhoopCaloriesBurnt` and the Calorie Trend / Net Energy Balance charts on `/nutrition`.

## Body weight (Tanita)

- **`pds.weight_log` stores daily body weight — Tanita scale ETL is the primary path (flipped 2026-06-09; was manual-only), manual `/nutrition` entry is the fallback/override.** One row per ET date (PK on `log_date`); `weight_kg NUMERIC(6,3) NOT NULL` is the canonical storage unit (matches `whoop_body_measurements.weight_kilogram`). Frontend accepts + displays pounds via `kgToLb`/`lbToKg` helpers. **`source TEXT NOT NULL DEFAULT 'manual'`** (`'manual'` | `'tanita'`, no CHECK so future scales don't need a migration): `tanita_etl.py` rolls up the **earliest measurement per ET day** (morning weigh-in convention) with `source='tanita'`, and **never overwrites rows where `source != 'tanita'`** — manual entries take precedence. The check is made by the database write itself (2026-11-16, audit PIPE-05): the rollup sends one `{log_date, weight_kg, logged_at}` row per day to `pds.upsert_tanita_weight_days` (`sql/weight_log_tanita_rollup.sql`, service-role only), whose single `INSERT … ON CONFLICT … WHERE source = 'tanita'` keeps a manual save made during the run and skips unchanged days; it answers inserted / updated / unchanged / skipped_manual counts (logged as counts only), and there is no plain-upsert fallback while the function is missing (the run fails naming the file; raw measurements are kept). Test: `tests/test_tanita_weight_rollup.py`. A manual POST re-log of a tanita-owned day explicitly sends `source='manual'` (flipping ownership so the ETL stops touching that day; explicit because the upsert UPDATE branch doesn't apply column defaults). PATCH deliberately leaves `source` untouched. **DELETE on a tanita-owned day doesn't stick** — the measurement still exists upstream, so the next ETL run re-inserts it; the override path for a bogus scale reading (guest on the scale) is manually re-logging the correct weight for that date, which flips ownership. API at `/api/weight` (GET/POST/PATCH/DELETE — all selects include `source`). UI: "Body Weight" section on `/nutrition` with KPI tiles (the Latest tile shows a TANITA badge when scale-sourced), quick-log card, trend chart (ChartCard `source` shows TANITA / TANITA + MANUAL), and recent entries with per-row TANITA pills. **Not joined into `daily_health_matrix` today** — weight changes too slowly for the daily-ATE causal layer (already excluded in `causal_inference.py`); it's a standalone trend store. If we later want weight as a slow-moving covariate (e.g. body comp regressions), join via `LEFT JOIN pds.weight_log wl ON gds.calendar_date = wl.log_date`. Schema in `weight_schema.sql`.
- **`pds.tanita_measurements` is the raw Tanita Health Planet store** (`tanita_schema.sql`): one row per measurement instant — PK `measured_at TIMESTAMPTZ`, `weight_kg`, `body_fat_pct`, `model` (device code), `raw_json` JSONB (grouped API items, passed as dicts), ADR-0001 quad via the standard `pds.set_onyx_dates_tanita_measurements` trigger (pure-instant variant), RLS anon-read/service-full. **Health Planet API facts** (healthplanet.jp/apis/api.html, Japanese): OAuth client-application type with redirect to the API's own `success.html` → copy-paste `code` (10-min TTL) — bootstrap via `python tanita_etl.py --auth` then `ci_token_helper.py upload tanita`. Access tokens last 30 days (`expires_in=2592000`); the `refresh_token` grant is **undocumented but works** and the ETL refreshes only within 7 days of expiry (don't exercise an undocumented grant more than needed). Rotation behavior is unconfirmed upstream, so the refresh path is **robust both ways (2026-11-16)** via the pure decision function `tanita_etl.merge_refresh_response`: a returned `refresh_token` that is present AND different replaces the stored one; a response that omits it (or echoes the stored value) keeps the old one; an empty value never overwrites the stored token; and a rejection (HTTP 400/401, or an `error` body — Health Planet error shapes are undocumented and the endpoint can answer 200 with an error key) raises `TanitaAuthError` whose message names the recovery steps and never quotes the response body — `run_etl` then writes a `failed` `tanita|weight` heartbeat with that message and **exits 1** (red on Actions; the token file is untouched). Test: `tests/test_tanita_token_refresh.py`. Data endpoint `/status/innerscan.json` with `date=1` (measured, not registered), tags `6021` (weight kg) + `6022` (body fat %) — tags 6023–6029 (muscle mass, BMR, bone…) were **retired from the public API 2020-06-29**, don't design around them. One array item per tag; items sharing `(date, model)` = one physical weigh-in. **Windows >3 months are SILENTLY truncated** (the API corrects `to` to from+3mo with no error) → the ETL pages backfills in ≤80-day windows; rate limit 60 req/h. **Timestamps are TZ-naive `yyyyMMddHHmm` in DEVICE-LOCAL wall-clock time** (verified empirically 2026-06-09: a ~11:26 PM ET weigh-in returned `202606092326`, not the JST equivalent) — parsed via `TANITA_TZ = America/New_York` in `tanita_etl.py`; re-verify with `--inspect` if the scale ever changes time zones. `/status`: the manual "Weight" card was **replaced** by the automated "Tanita" card — freshness from newest `measured_at`/`onyx_et_date` + the `tanita|weight` sync_log heartbeat, daily-cadence `deriveStatus` thresholds like Eight Sleep.

## Activity taxonomy

- **Activity taxonomy (run / sauna + MULTI-select strength tags) — auto-categorized, with manual multi-select split + muscle groups.** Onyx classifies every ingested workout into a small user-facing taxonomy. `run` and `sauna` are **auto-derived** from device sport labels (Garmin `activity_type` contains `run`; WHOOP `sport_name` = `running`/`sauna`). **`sauna` additionally has a manual override (2026-06-14):** an `is_sauna BOOLEAN NOT NULL DEFAULT FALSE` flag (`sql/activity_is_sauna.sql`, migration `add_is_sauna_to_workouts`) on both tables, surfaced as a single on/off toggle on every **non-`weightlifting_msk` WHOOP row** on the `/activities` page (for saunas the device logged under a generic sport, or bundled with another activity). It is ETL-preserving exactly like `is_excluded` (not in the upsert payloads) and **OR's into `act_sauna`** in the pipeline. It **replaced the deactivated "Used a sauna?" habit (HAB-43)** — going forward sauna is sourced from the activity, not the habit. The lifting dimensions devices can't distinguish — WHOOP logs all resistance training as one generic `weightlifting_msk` and Garmin records no strength at all — are reported manually as **two MULTI-select dimensions** (a session can be many things at once: an upper day is push + pull, a full day touches everything):
  - **coarse split** — `split_labels TEXT[]`, elements ⊆ `{leg, pull, push}`.
  - **granular muscle groups** — `muscle_groups TEXT[]`, elements ⊆ the canonical 11-tag set `{chest, back, shoulders, biceps, triceps, forearms, quads, hamstrings, glutes, calves, core}`.

  Both columns live on `whoop_workouts` + `garmin_activities` (nullable; array-containment `<@` CHECK constraints; `sql/activity_muscle_groups.sql`, migration `add_split_labels_and_muscle_groups` 2026-06-07). The **legacy scalar `split_label TEXT`** (`sql/activity_split_label.sql`) is **kept as a passive mirror of the PRIMARY split** (= `split_labels[0]`) so un-migrated readers + rollbacks stay safe; `split_labels` is canonical and the API writes both on every save. Both arrays are set from the **`/activities` page** — each strength row shows a multi-select Split pill row + a multi-select Muscles pill row (toggle each on/off) → `POST /api/activities/categorize` (`{source, id, split_labels[], muscle_groups[]}`, partial updates allowed; passes `id` as a **string** because `whoop_workouts.workout_id` is TEXT; accepts the legacy `{split_label}` form for BC). **ETL-preserving exactly like `is_excluded`:** neither array is in the Garmin/WHOOP upsert payloads, so the hourly re-sync's `ON CONFLICT DO UPDATE` (which only touches payload columns) never clobbers them. The `/activities` page also shows an auto-derived category badge (run/sauna/strength) per row.
  - **LLM tag suggestions (2026-11-11) - one-tap confirm, never auto-written.** For strength-type rows with NO tags from the last 30 days, `/activities` shows a Claude-proposed split + muscle set as ghosted (dashed) chips in the same pill rows, with **Accept** (writes through the existing `POST /api/activities/categorize`, which still validates the arrays), **Dismiss**, and every chip individually toggleable before Accept. The suggestion is generated on demand by `POST /api/activities/suggest-tags` (session auth only; body `{items:[{source,id}]}`, hard cap 10 per call, one model call per request, model `claude-sonnet-5-5`, effort `low`, JSON-schema output) from the session's name, duration, strain, HR, HR-zone minutes, weekday/time and the newest 15 already-tagged strength sessions as examples. The server re-reads every requested row and ignores any that is tagged, excluded, older than 30 days or not strength (same rule as the page: `deriveActivityCategory` in `lib/activity-tags.ts`); model output is validated per item (ids, arrays, values outside the canonical sets stripped) and any model failure degrades to "no suggestion" (HTTP 200, `failed: true`, nothing cached, retried on a later load). Cache + audit table `pds.activity_tag_suggestions` (`sql/activity_tag_suggestions.sql`, PK `(source, activity_id)`, service-role only): a row with a cache entry is never sent to the model again, and `dismissed=true` means dismissed OR accepted (`POST /api/activities/suggest-tags/dismiss`; it stores a tombstone when no cache row exists). The page requests suggestions in an effect after the list has loaded - they are deliberately NOT in the ISR prefetch, and no request is made when nothing is eligible. WHOOP's typed `zone_*_milli` columns are empty in the live table, so the HR-zone minutes are read from `raw_json->score->zone_durations`. Not an ingestion source, so no `/status` card. Tests: `frontend/tests/activity-tag-suggest.test.cjs` (also fails if the tag sets drift between the lib, `/api/activities/categorize` and the SQL CHECKs).
  - **HRV integration:** `hrv_analysis.py:aggregate_activity_categories()` derives per-behavioral-day `act_run/act_sauna/act_leg_day/act_pull_day/act_push_day` + 11 `act_mg_<muscle>` flags, reading the arrays via **non-exclusive membership** (a push+pull day fires BOTH `act_push_day` and `act_pull_day`; a chest+triceps day fires `act_mg_chest` + `act_mg_triceps`; legacy `split_label` is a fallback when `split_labels` is absent). **Keyed on `onyx_behavioral_date`** (not ET-of-start) so it co-locates with the spine and its outcome (the sleep closing that day, same row) even for a post-midnight session; a day with no such session is blanket-filled to 0 (harmless — every downstream consumer drops rows lacking the HRV outcome/lagged-HRV confounders first). `days_since_sauna` reads the robust `act_sauna` (WHOOP `sport_name='sauna'` **OR the manual `is_sauna` override toggle**, OR'd in `aggregate_activity_categories`) instead of the now-dropped WHOOP-journal "used a sauna" question (`journal_used_a_sauna` is dropped in `build_feature_matrix` 2026-06-14 — habit HAB-43 deactivated in Notion with all 288 rows preserved, mirroring the HAB-21 food-habit drop; takes effect on the next retrain). **`is_sauna=true` workouts are loaded UNCONDITIONALLY** (a second `whoop_workouts` fetch that ignores the main loader's `score_state='SCORED'`/`is_excluded` filter) and unioned into the activity-taxonomy frame only — so a hand-flagged sauna WHOOP returned non-SCORED still reaches `act_sauna`, without leaking unscored rows into the strain/workout-to-sleep-gap features that share `whoop_wk`. `act_` is in `CONTROLLABLE_FEATURE_PREFIXES` + the SARIMAX/Prophet exog seed list (so `act_mg_*` inherits SHAP-actionable + exog-seed coverage for free). `causal_inference.py` registers all of `act_run/act_sauna` + the 3 split + 11 `act_mg_*` as `EXPLICIT_BINARY_TREATMENTS` (family `behavior`); **`is_run_day` was dropped as a treatment** (superseded by the WHOOP+Garmin `act_run`, which treats rest days as control vs `is_run_day`'s active-only control) but **kept as a matrix column** (`consecutive_run_days` + XGBoost use it). Stats populate after ~3 weeks of labels (cell-size gates); the muscle groups have no history so they sit in `dropped_low_n` until enough tagged sessions accrue, then enter the FDR family. Not a new ingestion source → no `/status` card or nav change (an annotation layer over existing sources, like `is_excluded`).

## Air quality, weather and pollen

- **Air quality (PM2.5) — `pds.air_quality_daily` from Open-Meteo (`air_quality_etl.py`, 2026-11-11, `sql/air_quality_schema.sql`).** Keyless: `air-quality-api.open-meteo.com/v1/air-quality` (CAMS model analysis, ~0.4° grid outside Europe, global history from 2022-07-29), hourly `pm2_5` + `us_aqi` requested in **UTC** (`timezone=GMT`); **the ET clock day is built in the ETL from UTC hours**, exactly like `weather_etl.py` (2026-11-14): Open-Meteo applies ONE UTC offset to a whole response, the one in force when the request is made, so asking for `America/New_York` put every day of the other DST season an hour off. Each window asks for one extra UTC date so its last ET day is complete; DST days have 23 / 25 hours. Rows written before the fix need one re-sync from 2024-01-01 (`gh workflow run air-quality-etl.yml -f days=<days since 2024-01-01>`); upserts replace them in place. One row per ET day: `pm25_mean`/`pm25_max`, `us_aqi_mean`/`us_aqi_max`, `n_hours`, `latitude`/`longitude`, `source`. Hours after now are forecasts and never stored, so today's row is partial until the day ends. Location is fixed to central Atlanta (33.75, -84.39; `AIR_QUALITY_LAT`/`AIR_QUALITY_LON` or `--lat/--lon` override it — **change them when the NYC move happens**; every row carries its coordinates). It deliberately ignores Garmin GPS: a trip would silently move the whole series, and the data is regional model output, not a sensor at the apartment. Runs every 3 h (`air-quality-etl.yml`), re-upserting the last 7 days (hours get revised); an EMPTY table backfills itself from 2024-01-01, and `gh workflow run air-quality-etl.yml -f days=N` re-syncs N days. Service-role only (no browser read). Heartbeat `air_quality|daily` on every run (success / partial = API returned no PM2.5 / failed incl. a missing table, whose message names `sql/air_quality_schema.sql`); `/status` card "Air Quality" (badge OPEN-METEO; >4 h partial, >12 h red); allow-listed in `tools/watchdog_cloud.py` `SCHEDULED`. **HRV pipeline:** `hrv_analysis.py:merge_air_quality_features` puts clock day D on row D (same row as the sleep that closes behavioral day D; no re-keying, no shift) as `aqi_pm25`, `aqi_pm25_max`, `aqi_us_max`; days with <20 hourly values and days the table does not cover stay NaN (never zero); fail-open when the table is empty or missing. `aqi_` is in `NOT_FORECAST_PREFIXES` (today's row is partial when the evening forecast runs) and in `CONTROLLABLE_FEATURE_PREFIXES` (exposure is changeable even if the air is not; inert while it is out of the forecast). `aqi_pm25` is a `CONTINUOUS_TREATMENTS` median split (family behavior, common lag-1 confounders only — **no seasonal/temperature adjustment**, so read it as exploratory). Apply the SQL once, then `gh workflow run air-quality-etl.yml`; until then the card is red with that instruction. Tests: `tests/test_air_quality.py`.
- **Weather — `pds.weather_daily` from Open-Meteo (`weather_etl.py`, 2026-11-13, `sql/weather_schema.sql`).** Keyless: `archive-api.open-meteo.com/v1/archive` (ECMWF IFS + ERA5, hourly; today's hours are already there, so no forecast endpoint).
