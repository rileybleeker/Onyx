## Database basics

- Schema: `pds`
- All tables use upsert with conflict resolution (idempotent ETL)
- `ci_tokens` table stores rotating OAuth tokens for GitHub Actions (Garmin + WHOOP)
- Sync operations logged to `pds.sync_log`
- `supabase-py` schema access: always use `supa.schema("pds").from_(table)` — NOT `supa.table()` which defaults to `public`
- `whoop_workouts` has no `cycle_id` column; use `workout_id` + derive `calendar_date` from `start_time` via ET-of-start (see TZ convention below)

## Timezone convention and matrix views

- **Timezone convention** — governed by [ADR-0001 — Timezone & Behavioral-Day Handling](../adr/0001-timezone-and-behavioral-day-handling.md) ([Notion mirror](https://www.notion.so/36bbf5b44bf281c0895edb425358b458)). Three date types are carried per event:
  - `onyx_et_date` — clock day in `America/New_York` (canonical comparison key, MFP energy-balance semantics).
  - `onyx_behavioral_date` — bedtime-to-bedtime "day of Riley's life" via `(instant_local_tz − 6h)::date` (HRV pipeline, causal layer, behavior-affects-recovery analytics).
  - `onyx_local_date` — clock day in the TZ Riley was physically in (time-of-day features like `meal_last_hour`, `bedtime_hour`, travel-aware dashboard rendering).

  Every source table holding a TIMESTAMPTZ instant carries all three columns plus `onyx_tz_source` (provenance: `source_field | cycle_anchor | user_tz_log | gps_inferred | default_et_fallback`). Source date columns stay untouched (hard constraint). TZ detection ladder: WHOOP `timezone_offset` (free; already in DB) → Garmin activities offset (`start_time_local − start_time_gmt`) → cycle-anchor → `pds.user_tz_log` → ET fallback (flagged). **Fallback labels and date-only rows (`sql/tz_derivation_edge_cases.sql`, written 2026-11-14, applied only once Riley runs it):** `pds.tz_log_resolve(ts)` is the only code that writes `user_tz_log` / `default_et_fallback`; a trigger branch with only a date (no instant) calls `pds.derive_onyx_dates_for_day(date)` (three dates = the date, label = log coverage of that day), never a hand-rolled noon-ET probe. `garmin_hrv` stays on Garmin's wake-up `calendar_date` (`source_field`) because `hrv_alignment.py` does the one-day shift. Journal entries go through `pds.journal_entry_onyx_dates`; the migration has no backfill (journal_etl's hourly re-upsert re-derives journal rows), its rollback is `sql/rollback_tz_derivation_2026-11-16.sql`, `sql/tz_derivation_preapply_counts.sql` (run before applying, SELECT only) counts the stored rows the new rule would derive differently, and `sql/tz_derivation_postdeploy_checks.sql` runs right after (pass rules per check kind in its header); the WHOOP-journal and transition-flag parts are in `sql/tz_derivation_whoop_followups.sql` (not applied). Tests: `tests/test_tz_derivation_edge_cases.py`.

  **Matrix views** (ADR-0001):
  - **`pds.daily_health_matrix_behavioral`** — every source join keyed on `onyx_behavioral_date`. **This is the canonical view for HRV / causal / behavior-affects-recovery analytics.** WHOOP cycle deduplicated via `LATERAL ... LIMIT 1` (longest cycle per behavioral day) so transition-day "arrival nap + main cycle" doesn't double-count. `onyx_is_transition_day` aggregated via `bool_or` across all cycles on the day. Consumers: `hrv_analysis.py`, `causal_inference.py`, `/analytics/hrv`, `lib/queries.ts:getHealthMatrix`. DDL: `sql/adr_0001_08_daily_health_matrix_behavioral.sql`.
  - **`pds.daily_health_matrix`** (legacy clock-date view) — **DROPPED 2026-11-08** (`sql/drop_legacy_daily_health_matrix.sql`): no code readers, no DB dependents, and its WHOOP join mis-attributed travel days. Restore from `sql/deprecated/daily_health_matrix_live_2026-11-07.sql` if ever needed. Do not reintroduce clock-date matrix reads — use the behavioral view.
  - **`pds.daily_health_matrix_behavioral_mat`** — materialized copy of the behavioral view for **frontend page-load reads only** (perf, 2026-06-11; the live view's ~30-relation join cost 150-650 ms mean with 1.5-2.7 s tails via PostgREST). Refreshed every 30 min by pg_cron (`10,40 * * * *`; was every 15 min until 2026-11-11, cut to halve Disk IO — see `sql/matview_refresh_30min.sql`) through `pds.refresh_daily_health_matrix_behavioral_mat()` (a CONCURRENTLY refresh: readers never wait), which writes a `pds.sync_log` heartbeat (`matrix_mat`|`refresh`) on success AND failure and includes a pg_attribute **schema-drift tripwire** — surfaced as the "Matrix Matview" card on `/status`. **⚠ RULE: every migration that changes `pds.daily_health_matrix_behavioral` MUST drop + recreate the matview (+ unique index on `onyx_behavioral_date`, `calendar_date` index, anon/authenticated grants) in the same migration — the matview's `SELECT *` is frozen at creation. NEVER `DROP VIEW ... CASCADE` on the canonical view.** Frontend consumers: `getHealthMatrix`/`getNutrition`/`getCaffeineHrvPairs` (queries.ts), `getHistoricalHrv`/`getEnvDoseResponseData` (queries-hrv.ts), travel's `getHRVData`. The Python pipeline and the chat tools deliberately stay on the LIVE view. Full doc + recreate recipe: `sql/perf_matrix_matview.sql`.

  **`pds.user_tz_log`** — hand-maintained table of TZ transitions. Schema: `(effective_from TIMESTAMPTZ PK, tz TEXT IANA, notes TEXT)`. Insert one row per flight landing into a non-ET zone (and back). NY trips don't need entries (default). Read by `pds.tz_for_instant(ts)` which is used by every non-WHOOP / non-Garmin-activity trigger to derive local TZ.

  **`pds.tz_log_gaps`** — canary view comparing WHOOP `timezone_offset` to `pds.tz_for_instant`. Any disagreeing cycle = "Riley traveled but forgot to log it." `/status` page reads this and renders a yellow banner.

  **Behavioral-day rule** — for any instant `ts` with resolved local TZ:
  - `onyx_behavioral_date = ((ts AT TIME ZONE local_tz) − 6h)::date`
  - Generalizes the existing `whoop_journal.behaviors_date` trigger formula. Pre-midnight bedtimes attribute to today; post-midnight bedtimes (84.4% of nights for Riley) attribute back to yesterday.

  **Legacy view rules** (historical — applied in the dropped `pds.daily_health_matrix`; still relevant to `pds_legacy.daily_health_matrix_v0`):
  - **Point-in-time events** (workouts, weigh-ins): `(start_time AT TIME ZONE 'America/New_York')::date`
  - **WHOOP cycles** (bedtime-to-bedtime spans): `((start_time + INTERVAL '12 hours') AT TIME ZONE 'America/New_York')::date` — wake-day attribution.
  - **Garmin `start_time_local`**: stored as local wall-clock labeled as UTC (+00); `::date` yields ET date directly.
  - The `hrv_analysis.py` pipeline previously mirrored these rules via `to_date_str()` / `to_et_date_str()` / `to_cycle_et_date_str()` helpers; post-ADR-0001 it reads the behavioral view, so `calendar_date` in the loaded matrix IS `onyx_behavioral_date`.

  **Snapshot for A/B**: `pds_legacy.daily_health_matrix_v0` is a frozen materialization of the pre-ADR view (794 rows), retained for the Phase 2 sensitivity test and rollback if needed.

  **GPS-based TZ auto-population** (ADR-0001 Phase 4 step 4): `gps_tz_backfill.py` scans `pds.garmin_activities` for `(start_latitude, start_longitude)` and inserts new `pds.user_tz_log` rows whenever the GPS-inferred IANA TZ disagrees with what `pds.tz_for_instant` currently returns. Filters out same-UTC-offset cases (e.g. Toronto/Louisville share EDT with NY — geographically distinct but behaviorally identical). Runs automatically at the end of `garmin_etl.py` with `--since <earliest_date_this_run>` to keep the per-run cost ~5s. One-shot full-history sweep available via `python gps_tz_backfill.py --apply`.

  **WHOOP-cycle-based TZ auto-population** (ADR-0001 Phase 4 step 4 extension): `whoop_tz_backfill.py` is the companion path for trips where Garmin GPS doesn't fire (rest trip, no outdoor activity, watch off). Runs automatically at the end of `whoop_etl.py`. Every WHOOP cycle ships a `timezone_offset` (e.g. `-06:00`) — the script detects cycles whose offset disagrees with `pds.tz_for_instant`'s current resolution and inserts new `user_tz_log` rows (it reads the log once and looks each cycle up at its own instant, with the run's own proposals added as it goes; before 2026-11-14 it read the log only at the first cycle, so wide `--since` windows re-proposed trips the log already covered). Tests: `tests/test_whoop_tz_backfill.py`, `tests/test_tz_backfill_in_memory_current_tz.py`. Since WHOOP gives offset only (not IANA), the script picks the most-common IANA for that offset from Riley's MANUAL `user_tz_log` entries (history-derived), falling back to a generic offset → IANA map. Same-offset cases skip (no behavioral difference). The notes field tags every auto-insert (`whoop-auto: cycle <id> offset <off>; <provenance>; log was <prior_tz>`) so they're distinguishable from manual entries — and the history-derived defaults computed from ONLY manual entries to avoid bootstrap bias.

  **Resolution priority across the three TZ-population paths**: Manual > GPS-auto > WHOOP-auto. Manual entries are never overridden; the auto scripts only fill gaps. GPS gives exact IANA when available; WHOOP gives offset always. Together they cover essentially every realistic trip without manual maintenance — manual SQL is only needed if both devices are left at home.

## SQL and ETL write conventions

- SQL schema changes: create a .sql file, then apply via Supabase MCP or dashboard **Migrations sent through the Supabase MCP must contain no `DROP …` statement, not even `DROP TRIGGER/POLICY IF EXISTS` guards** — the connector asks for an interactive confirmation on anything destructive and returns "Migration was declined" when the session can't answer (2026-11-09: two declines until the guards were replaced with `CREATE OR REPLACE TRIGGER` + plain `CREATE POLICY`). It is not a Claude Code permission problem; no allow rule fixes it. The check appears to read the whole text, so strip header comments that mention the word too before sending.
- Always upsert (never raw insert) to keep ETL idempotent
- **JSONB writes: pass dicts/lists directly to supabase-py; do NOT wrap with `json.dumps()`.** supabase-py serializes dicts to JSONB natively. Wrapping with `json.dumps()` produces a JSONB column whose top-level type is `'string'` rather than `'object'`/`'array'`, silently breaking every downstream JSON path query (`raw_json->>'field'` returns NULL). For dicts containing non-JSON-safe types (datetime, Decimal, numpy floats), use `json.loads(json.dumps(obj, default=str))` to sanitize-then-unwrap instead of double-encoding. Audit pass on 2026-05-26 found this bug at 25+ sites across every ETL and the analysis pipeline; backfilled via `(col #>> '{}')::jsonb` migration (`audit_jsonb_backfill_*`). The `pds.spotify_plays.raw_json` column was the only one that got it right from the start because the Spotify ETL was written after the bug pattern propagated elsewhere.
- **A bulk upsert must carry ONE key set (2026-11-13).** supabase-py sends a list upsert with `columns=` set to the union of every row's keys, and PostgREST writes NULL for a key a row does not have, overwriting the stored value. Never put rows that set an optional column next to rows that leave it out in the same `upsert([...])`; group them first (`journal_etl.uniform_batches`). Found live in `journal_etl.py`: unchanged entries carry no `embedding` key, so one edited page wiped the embedding of the 24 unchanged entries in its batch, the next hourly run re-embedded those and wiped the others, and semantic search was missing 1 or 24 of 45 entries at any moment. The other ETLs have not been checked for this.
- **Sync_log writers:** every ETL goes through `sync_log_helper.log_sync` (thin per-ETL wrappers are fine). Still hand-written: `garmin_etl.py` and `hrv_analysis.py:log_sync_entry`.
- **Every Python script that writes to Supabase emits a `pds.sync_log` heartbeat on EVERY run** — success AND failure, including uncaught exceptions. The audit caught silent retrain failures because `hrv_analysis.py` lacked a heartbeat, so its crashes were invisible to `/status`. Pattern: wrap `main()` in try/except in `if __name__ == "__main__"`, call `log_sync_entry(status='success'|'failed', records=N, error=str|None, duration=T)` in both branches. Without this, downstream effects (predictions, dashboards) keep looking healthy via cached state while the upstream pipeline is broken.
