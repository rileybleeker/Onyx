## Habit tables and sync

- **`habit_journal` is THE single behavior table (WHOOP journal merge, 2026-06-11 — `sql/whoop_journal_merge.sql`).** The WHOOP in-app journal was replaced by the habits system: the 12,360-row WHOOP history (Oct 2024 → 2026-06-08, explicit Yes/No answers) was copied in verbatim with a `source` column ('whoop'|'habit'), and the 30 questions active in the final export became Notion habits with **VERBATIM question text as titles** (the question string is the HRV pipeline's variable identity — `journal_*` slugs derive from it). Key invariants:
  - **`source` routing is by QUESTION IDENTITY, not write path**: `habit_name_map.channel` ('whoop'|'habit') drives a trigger that stamps `source='whoop'` on any insert of a WHOOP-derived question — so post-cutover habit taps keep feeding the same `journal_*` feature columns. Native habits stay `source='habit'` → `habit_*` columns.
  - **WHOOP-derived habit names are FROZEN.** DB guard triggers RAISE on rename (map + journal level), and the sync route skips + surfaces blocked renames. Renaming one requires a coordinated migration (history rewrite + `hrv_analysis.py`/`causal_inference.py` hard-coded slug updates).
  - **The WHOOP era (cycle_date ≤ 2026-06-08, source='whoop') is IMMUTABLE** — guard trigger `zzz_block_frozen_whoop_era` rejects writes from every path; API routes also refuse with a clear error. Bypass for coordinated migrations only: `SET onyx.allow_frozen_writes = 'on'`.
  - **Date semantics across the cutover**: whoop-era rows keep `cycle_date` = WHOOP bedtime-day with a separate `behaviors_date` (bedtime−6h); post-cutover rows use `cycle_date` = behavior-day with `behaviors_date = cycle_date`. The **behaviors_date axis is continuous**; `cycle_date` is not. Behaviors-day **2026-06-08 is a permanent 1-day NaN hole** (final export covered through 06-07; the (2026-06-08, question) PK slots hold frozen rows) — do NOT "fix" it.
  - **Missing = unknown (NaN), post-cutover (policy REVERSED 2026-07-19; was missing=No 2026-06-11→2026-07-19)**: `hrv_analysis.py` no longer 0-fills unlogged `journal_*`/`habit_*` days — a missing row means "not logged", not "No". Explicit No rows map to 0.0 via `is_yes`; only explicitly answered days feed Welch No-arms, Spearman, and causal confounders post-cutover. The original 0-fill predated tri-state capture (absence was then the only way to express No); with explicit Yes/No rows and backdated grids, zero-filling would manufacture fake No days for unlogged gap weeks. Native daily habits' explicit-No backfill (AI, Lumosity, first completion → 2026-06-10) still stands as real data.
  - `pds.whoop_journal` is a **frozen archive** (write-blocked by trigger; kept as immutable backup of the original rows). The native 'Journaled' habit's 13 completions were merged into 'Journaled your thoughts?' (Yes-wins on behaviors_date; 6 No→Yes flips) and the habit retired.
- `journal` view = `SELECT … FROM habit_journal` (single-table since the merge; same column contract as the old whoop+habit UNION: cycle_date, behaviors_date, question, category, answer, notes, synced_at, source)
- Habit definitions are managed in Notion (Habits DB under Project Onyx, ID: `29cc936fd5e14ae8b10a4fe5c5f7a6cd`); the 30 WHOOP-derived habits are Frequency='Ad Hoc' so the /habits Today-ring + rate KPIs aren't distorted by 30 observational/negative questions (flip individual ones to daily in Notion if desired)
- Bidirectional sync: completions from Onyx/Chat update both Supabase and Notion; Notion "Last Completed" syncs to Supabase on page load. Notion LC is always recomputed as MAX(cycle_date) over **answer='Yes'** rows (the table carries explicit No rows now), restricted to **cycle_date > 2026-06-08** for WHOOP-derived habits.

## Tri-state answers and the daily check-in

- **Tri-state habit answers (2026-06-11).** Every (habit, day) cell is `Yes` / `No` / not-logged. **Direct selection UI:** /habits heatmap cells open a fixed-position Yes/No/Clear popover on click, for corrections (the 2026-06-11 one-tap "Today's Habits" checklist and its backdate picker were removed 2026-11-15: daily answers are entered on Log's check-in, see "One place to enter data"). **Writes are OPTIMISTIC** (`setAnswer` in `HabitsClient.tsx`: local state applies immediately, reverts on a non-OK response; per-cell monotonic seq guards rapid re-taps) and the `/api/habits/complete` route responds right after the Supabase write — the Notion Last-Completed mirror runs post-response via Next 15 `after()` (best-effort; the hourly habits-sync self-heals misses). Perf siblings: `getHabitJournal` pages in parallel (count-first, was ~10 serial 1000-row roundtrips at 365d), and /habits fetches once on mount — range switches re-derive locally with no refetch/skeleton. `/api/habits/complete` accepts `answer: 'Yes' | 'No' | null` where **null DELETES the row** — row absence stays the canonical "not logged" (the missing=No pipeline fill, the (cycle_date, question) PK, and the backfill trigger all assume it; legacy `undo: true` still maps to null). Chat's `mark_habit_complete` takes an optional `answer` enum (the tool description tells the model to record 'No' only on an explicit "I didn't…"). Explicit 'No' counts exactly like not-logged in every KPI/streak/Notion-LC computation (all keyed on answer='Yes') and maps to 0.0 via pivot_journal/pivot_habits' `is_yes`. In the HRV ANALYSIS pipeline the two now differ (2026-07-19): explicit No = 0.0, not-logged = NaN (unknown) — see the missing=unknown policy bullet. `getHabitJournal` fetches Yes+No rows; the hourly Notion-LC sync SKIPs (and surfaces) any date explicitly marked 'No' instead of flipping it back to 'Yes' — a direct answer in Onyx out-ranks Notion's date-only signal. DB hardening: CHECK `habit_journal_answer_check` (`answer IN ('Yes','No')`), applied as a Supabase migration + mirrored in `sql/habit_journal_answer_check.sql`. Toward (but not yet) the parked daily check-in flow — the capture mechanism now exists; the guided prompt does not.
- **Daily check-in (`/check-in`, 2026-11-07) is the primary habit-capture surface** — the successor to the WHOOP journal's daily compliance (logging had stopped entirely after 2026-07-19). Every evening at 21:30 ET the sms-reminders Worker posts one "Check-in for <day>" card in the `check-in` conversation of `/agents` (push deep-links straight to `/check-in?date=…`); if it is still open at 9 AM the next day, the card is re-posted once. The screen (`app/check-in/CheckInClient.tsx`) shows the **core** questions (the WHOOP-derived questions + daily/weekdays habits, grouped by category, explicit Yes/No each) and a collapsed **"Also did"** section (weekly / ad-hoc native habits; blank = not logged). **Answers are written to the behavior day the check-in is FOR, never the clock day** — so finishing after midnight or the next morning lands correctly. Accepts behavioral today and the 2 days before only (catch-up tabs); older days stay unlogged (= NaN in the pipeline). **Data-backed pre-fills only, labeled with their source**: alcohol Yes when Cronometer has `alcohol_g > 0`; rest day No on a training workout (WHOOP sports other than yoga/activity/other/walking/sauna, or any non-walk Garmin activity), Yes when no workout at all, else blank; plane Yes when `pds.tz_for_instant` changes across the day. Everything else starts blank. Taps persist as a localStorage draft per day. `GET/POST /api/habits/checkin` (under the `/api/habits/*` auth boundary) writes the whole day in one upsert/delete (null = delete = not logged) and mirrors Notion Last Completed via `after()` only for habits whose value moves; answers save as they are tapped (autosave, 2026-11-15: the local draft first, then one request per touched part 600 ms after the last tap; no Save button), and once every core daytime question of the day has a saved answer the screen calls the Worker's `POST /onyx/checkin/done` once to settle the card (`dayComplete` in `lib/checkin-cells.ts`; on today that is the save that also stores the day's pre-fills; a half-answered day keeps its card; this also suppresses that evening's send if Riley checked in on their own). Active-habit fetch is shared via `lib/habits-notion.ts`. The backfill-signal trigger now also exempts **yesterday** (`affected_date < today_et - 1`) so a late check-in doesn't schedule an extra full retrain — the 12:00 UTC daily retrain covers it.
- **Check-in: less typing (2026-11-13, rules + thresholds in `lib/checkin.ts`).** The 38-question screen was abandoned after 3 days (2026-11-08..10), so: (1) **`OCCASIONAL`** — 14 questions with at most 4 Yes answers ever (dimmed lights, read non-screen in bed, vacation day, MEMOS, Case Study, History, Math, Meditated, Chess, Substack, Lumosity, Duolingo Spanish, News, BI/Python/AL/Excel) are asked only in the collapsed "Also did" section (blank = not logged = NaN in the pipeline); a code list, nothing changed in Notion — remove a name to ask it daily again. (2) **More pre-fills, same contract as before** (shown with their source, stored only when Riley saves, never written by the GET): "Viewed a screen device in bed?" from Screen Time `minutes_last_hour_before_sleep_est` (≥20 min Yes, ≤1 min No; the Yes threshold was 10 until 2026-11-13 and is printed in the Yes label — hourly data lets phone use that ended 60–90 min before sleep add up to 15 min to the estimate, so 20 means use inside the last hour itself; **only once that day's sync is complete** — `lib/checkin-screen.ts:settledLastHourMinutes`: synced after the day ended, sleep scored, sync at least an hour past sleep onset — because the estimate reads 0, not NULL, between WHOOP scoring the sleep and the phone's ~10 AM sync, which made the 9 AM catch-up card suggest No from missing data); "Slept in the same bed as usual?" from Eight Sleep (a non-`away` row dated D+1 with ≥3 h slept = Yes; No only when that night is missing and a later night has synced — checked against 126 past answers: 93/97 Yes nights had the row, 25/29 No nights did not); "Journaled your thoughts?" from `pds.journal_entries` (Yes on an entry; No only for a finished day); Duolingo / Substack / News Yes from ≥3 min in the app (never a No). (3) **One-tap answers**: "Usual kit" fills the 5 sleep-kit questions with the last answer given to each (`usualKit`), and "No for the other N" answers every blank daytime question. Both are ordinary taps (draft, then saved like any tap). (4) **Sleep is asked per finished NIGHT, never on a day tab and never for tonight.** An answer stored on behavior day D describes the night that CLOSES day D (the pipeline scores day D's answers against that sleep), so on day D itself that night has not happened. The screen therefore has two parts: a **Sleep** block (`CheckinPayload.nights` from `sleepNights(today)`: last night = behavior day today−1, always; the night before while its saved answers are incomplete), labeled "Last night · Thu night → Fri morning", with that night's kit button and pre-fills; and **Daytime** (the day tabs, whose progress counts daytime questions only). Each autosave POSTs the day under its date and each changed night under THAT NIGHT's date. Do not move the sleep questions back into a day tab. Guards (from the 2026-11-13 review): the screen reloads when it comes back after a minute away, and the POST carries the `today` the screen was drawn with and answers **409 `stale`** when the day has rolled over, so a page left open overnight cannot write "last night" onto the night before (the refused taps are dropped and must be re-answered); **a part (the day, or one night) is saved only when Riley tapped or cleared something in it** — its pre-fills go with it, untouched pre-fills stay suggestions, and the day's card is settled only when the day was sent (`savePlan` in `lib/checkin-cells.ts`, which holds the screen's pure state rules: drafts carry the stored answer they were made against, so a tap is ignored once that answer changed elsewhere; on behavioral today the day part sends only Riley's taps and clears, and the day's pre-fills are stored only in the save that completes the day counting them (every core daytime question shows an answer), which is also when the card settles; catch-up days and nights keep pre-fills-with-the-first-touch); **every write path refuses a Yes/No to a sleep question dated behavioral today or later** (`sleepDateError`, used by `/api/habits/checkin`, `/api/habits/complete` and the chat tool; clearing is allowed); the behavioral-today fallback is Eastern time − 6 h; "Read (non-screened device) while in bed?" is a sleep question shown as an optional row in the night block. Other write paths follow the same rule: the chat tool stores a sleep answer with no date on yesterday (`sleepAnswerDate`), the `/habits` "Today's Habits" checklist leaves the sleep questions out, and the hourly `/api/habits/sync` never turns a Notion "Last Completed" date into a sleep answer (a date cannot say which night; skipped quietly, 2026-11-14). Known limit: before 06:00 local the night just slept is not offered yet (behavioral today has not rolled), which is why the weekday span, not "Last night", is the main label. Catching up the night before (today−2) can schedule one extra hourly retrain, as the catch-up day tabs always could. The sleep answers saved on the old screen (cycle_date 2026-11-09 and 11-10; 2026-11-08 has none) were given 2–4 h before the night they are stored on began (saved Mon 22:07 and Wed 00:30 ET, sleep onset 02:04 and 02:43), so they most likely describe the night before. Left as stored (settled 2026-11-14): the 8 answers are identical on both days, Eight Sleep (6.6 h, 5.8 h) and Screen Time (47 and 28 min in the last hour) confirm same-bed and screen Yes for the stored nights, and the kit is the same on every answered night 11-09..13 apart from one sleep mask (11-12), so moving them a night would change no value on 11-09 and only blank 11-10. "AI" is a learning habit, not app use, so it is not derived. **"Say it once" box (2026-11-14):** a collapsed box in the Daytime part where Riley types or dictates a few sentences; `POST /api/habits/checkin/voice {date, text, today}` makes one Claude call that maps them to Yes/No for that day's daytime questions AND for **last night's** sleep questions (`night` = `sleepAnswerDate(today)`, the newest finished night; every sleep answer passes `sleepDateError`, so never tonight, and the page puts them only into the night block on screen with that date), and returns the labels of a **journal draft** of the same words (title, mood, confidence, topics, following the journal field rules in the Notion journal note (reading-journal.md); the route's prompt mirrors them, so change both together). A screen whose `today` is old gets 409 `stale` and reloads. The page applies the answers as ordinary taps marked "from what you said", which save like taps; the route writes nothing and never stores or logs the text. The journal draft (a card under the box) keeps the words **verbatim** as the body, with editable labels, and is written only by **Save to journal** → `POST /api/journal/entry` (session only and same-origin, never a CI route; `lib/journal-entry.ts`), which creates the Notion "Entries" page with all six properties set (a repeat with the same date and title returns the page already there); `journal_etl.py` brings it into `pds.journal_entries` at :35. Once it is saved, "Journaled your thoughts?" gets a draft Yes for that day ("from the journal entry you saved"). **iPhone Shortcut hand-off:** opening `/check-in#say=<URL-encoded words>` puts the words in the box and runs Fill once on the fresh check-in (a fragment never reaches the server, and it is cleared from the address at once); the Shortcut itself lives on Riley's phone. ## Renames and retraining

- `habit_name_map` tracks Notion page ID → name (+ `channel`); renaming a **native** habit in Notion auto-updates all historical `habit_journal` entries via the FK's ON UPDATE CASCADE (the sync renames the map row and lets the cascade do the work); the 29 retired WHOOP questions have synthetic `whoop-archived:<md5>` map rows for FK coverage
- **Backdated habit completions trigger HRV retraining.** A Postgres trigger (`habit_journal_backfill_trigger`, defined in `sql/habit_journal_backfill_trigger.sql`) fires on every INSERT/UPDATE/DELETE on `pds.habit_journal` and emits a `pds.sync_log` row (`source='habit_journal', data_type='backfill_signal'`) whenever the affected `cycle_date` is in the past (ET). **No-op UPDATEs are suppressed (2026-06-11)** — the hourly sync's idempotent Last-Completed upserts previously fired 3 signals/hour, scheduling a full retrain EVERY hour (31 in 48h); the sync route also now skips the upsert when the completion row already exists. `hrv_backfill_check.py` reads this signal alongside its row-scan checks; either path setting `backfill_detected=true` triggers a full `hrv_analysis.py` retrain on the next hourly tick. The trigger covers paths the original row-scan missed: the UPDATE branch of upsert (which doesn't bump `synced_at` because the API call doesn't include it in the patch object) and DELETE (which leaves no row for `WHERE synced_at > last_analysis` to find — relevant when Riley undoes a backdated completion). Today's writes are deliberately suppressed by the trigger; same-day mutations are picked up by the daily safety-net retrain at 12:00 UTC instead, since an hourly retrain on every habit tap would be wasteful.
