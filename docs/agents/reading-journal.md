## Reading module

- **Reading module (`/reading`, 2026-11-07) — a gamified reading log with highlight + comment capture and a Notion mirror.** Tables in `sql/reading_schema.sql`: `pds.books` (slug, total_chapters, start/target_date, status, `notion_page_id` = the per-book reading-log page, `habit_name` = the habit stamped on session days), `pds.reading_sessions` (behavioral `session_date`, chapter range, minutes, medium, `recall` = the from-memory note, `question`), `pds.book_highlights` (passage + `comment` + `concept` tag + source, UNIQUE on (book, passage) for idempotent Kindle re-imports, SM-2-lite fields `ease`/`interval_days`/`next_review`), `pds.reading_reviews` (grades), `pds.reading_quizzes` (checkpoint scores). **Everything gamified is derived, never stored** (`lib/reading.ts:computeOverview`): XP (10/chapter, 20/recall ≥40 chars, 5/commented highlight, 15/review day, 10/quiz point, 50/on-time checkpoint), levels every 100 XP with plant-themed titles, streak over behavioral days, pace vs the linear start→target line, checkpoints at 30/65/100% of the book, 10 badges. Writes: `POST /api/reading/sessions` (with `client_key`, a UUID per new /log session, `sql/reading_sessions_client_key.sql`: a create retried after a lost answer returns the stored session, `replayed: true`, with no second XP, habit stamp or Notion entry; also upserts `habit_journal` Yes for `books.habit_name` on that day — so /habits + the HRV `habit_*` columns see reading for free — and flips `status=finished` on the last chapter) and **`PATCH`/`DELETE /api/reading/sessions/[id]`** (2026-11-15, `updateSession` / `deleteSession` in `lib/reading.ts`: the autosaving /log form edits or removes the session it created; same rules; Kindle sessions 409; an edit or removal undoes what the earlier value did: a finish this session caused goes back to reading when no other session reaches the last chapter (a moved finishing session moves the finish day), and a new day or book stamps that book's habit Yes there while the old day's Yes is removed only when this session created it (`habit_created_on`, reported by the server and sent back by the form) and no other session with the same habit is on that day; owner session only, never in `isCiRoute()`, same-origin JSON, 48 KB cap; the Notion block follows in `after()`; both create routes re-read the row after storing `notion_block_id` and update, trash or move the entry when an autosave edit or removal landed first), `/api/reading/highlights` (the /reading "Highlight + comment" form saves itself: created on the first non-empty passage, then PATCHed; a create retried after a lost answer adopts the row its own send made) (+ `/[id]` PATCH incl. passage + source / DELETE soft-archive, `/import` for pasted Kindle "Export notebook" HTML / My Clippings.txt / plain lists via `lib/kindle-import.ts`), `/api/reading/review` (grade → reschedule), `/api/reading/quiz`, `/api/reading/books`. **Notion mirror (`lib/reading-notion.ts`, best-effort in `after()`):** each session is inserted as a quote block right after the "Session log → Newest first." paragraph of the book's page, each highlight under a "Highlights" heading the code creates on first use, and the top callout's "Progress: chapter X of N" line is rewritten — `notion_block_id` on the row records the mirror; the Onyx Notion integration must be able to see the page (The Goal's page lives under Project Onyx). Chat tools: `get_reading_status` (coaching + quiz source material), `log_reading_session` (recall passed VERBATIM), `add_book_highlight`, `record_reading_quiz` (the model asks 5 questions one at a time, then records the score; 80% passes). `/status` has a manual-method "Reading" card keyed on the newest session. No in-app e-reader by design: Kindle/Audible files are DRM-locked, so capture happens here and reading happens there. **Automatic Kindle ingestion = `tools/kindle_harvest/harvest.mjs`** (Riley's PC, Task Scheduler "Onyx Kindle Harvest" every 3 h while logged on — the StreetEasy-harvester pattern, because Amazon has no highlights API and the reader needs a signed-in browser; persistent Chrome profile `%LOCALAPPDATA%\\Onyx\\kindle-harvest-profile`, one-time `node harvest.mjs --login`). **The task is registered by `tools/kindle_harvest/register-task.ps1` (2026-11-09)**: `wscript.exe run-hidden.js` launches node with no console window and passes its exit code through; runs on battery, `StartWhenAvailable` catches up runs missed during sleep, 20-min execution limit, never wakes the PC — the original bare `schtasks … node.exe` registration refused to start on battery (`0x800710E0`) and skipped sleep-missed runs, leaving the heartbeat 32 h stale. Re-run that script instead of hand-writing `schtasks`. **v2 (2026-11-08) reads the Kindle for Web READER, not the Notebook DOM:** opening `read.amazon.com/?asin=<ASIN>` makes the app fetch, and the script intercept, (a) `getAnnotations` JSON = every highlight/note with its Kindle **position** and real **timestamp**, (b) the first `renderer/render` tar whose `toc.json` (chapter → start position), `location_map.json` (`navigationUnit` = print page labels) and `metadata.json` (book length) are parsed with a minimal ustar reader (skip the `PaxHeaders.X/` stubs), and (c) the page HTML's `mostRecentPositionRead` = the Whispersync reading position. The direct `getAnnotations` URL is NOT callable with cookies alone (403 "not an ADP session request") — intercepting the app's own call is the supported path. It posts `{asin, last_position, total_positions, chapters[], items[{passage, comment, position, position_end, page, location, highlighted_at, note_at}]}` with `harvest: true`; the route upserts `pds.book_chapters` (numbered TOC entries only), bumps `books.last_position` monotonically, upserts highlights (idempotent on passage; chapter derived from position), then runs **`lib/reading-kindle.ts:syncKindleSessions`** — a pure recomputation that writes ONE `source='kindle'` session per behavioral day (unique partial index): a highlight ending within ~800 positions of a chapter's end or on its last page **completes that chapter**, a highlight inside chapter N proves N−1, the reading position works the same way, and **any day with a new highlight or note gets a session** (chapter_from/through NULL when nothing completed, `in_chapter` set, `recall` = that day's notes verbatim) — so Kindle reading is never logged by hand; manual/`chat` sessions are untouched and stay the path for audiobook/paper. Session day = the highlight's own timestamp through `pds.behavioral_date_for()` (trigger-set `book_highlights.behavioral_date`); the position is attributed to the harvest day. Opening the book in the web reader does not move the reading position. Heartbeat `kindle|highlights` success/partial/failed (an expired Amazon session or an Amazon `/checkpoint/` bounce after one 30 s retry is a failed row). Token: `~/.onyx_ci_token` (= `ONYX_CI_TOKEN`). `/status` "Kindle" card: >12 h degraded, >48 h or error = red (loose because the PC may be off). Adding a book = a `pds.books` row + `{slug, asin, titleMatch}` in `books.json`. **Run now (2026-11-16):** the `/status` Kindle card's button (`components/KindleRunNow.tsx`, `lib/kindle-run.ts`) calls `POST /api/kindle/run` (owner session only, never in `isCiRoute()`; same-origin JSON `{}`, 256-byte cap), which inserts a row into `pds.pc_run_requests` (`sql/pc_run_requests.sql`, applied; service-role only, in the `supabase_realtime` publication); a press while the newest request is unanswered (< 2 min) or still running (< 25 min) returns that one. **Event driven, no polling job on the PC (Riley's requirement):** Supabase Realtime pushes the INSERT to `tools/kindle_harvest/run-listener.mjs` (one idle Node process holding one websocket with the service key from `~/.onyx_supabase_secret`; started hidden at sign-in by a Startup-folder shortcut, set up and restarted by `register-listener.ps1`; one instance via a named-pipe lock; reconnects with backoff and after sleep), which starts the "Onyx Kindle Harvest" task (IgnoreNew keeps a pressed and a scheduled run apart) and writes `picked_up_at` + `outcome` (started / already_running / failed), then `finished_at` + `exit_code`, on the row; the button reads it via `GET /api/kindle/run?id=`. No answer in 15 s = the PC looks asleep or off. Tests: `frontend/tests/kindle-run.test.cjs`, `tools/kindle_harvest/run-listener.test.mjs`.

## Personal journal (Notion Entries)

- **`pds.journal_entries` is the personal Notion journal — distinct from `pds.journal` (the WHOOP+habit *behavior* view).** Notion DB "Entries" (ID `96541038264d45aba2a9601d9b175a7e`, parent page "Journal"). One row per Notion page; PK = `notion_page_id`. Properties: `entry_date` (ET-naive — Notion's Date property has no time component), `title`, `mood` (low/neutral/good/great), `source` (voice/remarkable/typed), `confidence` (high/medium/low), `topics` (JSONB array), `content_md` (page body as markdown), `word_count`, `embedding` vector(1024) from Voyage `voyage-3-large`, `archived` (soft-delete). Skip-if-unchanged guard: `notion_edited_at` — ETL only re-fetches blocks / re-embeds when Notion's `last_edited_time` advances. Indexes: B-tree on `entry_date` + `mood`, GIN on `topics`, HNSW (cosine) on `embedding`. RPC `pds.search_journal_entries(query_embedding, date_from, date_to, mood_filter, topic_filters, result_limit)` exposes filtered + similarity-ordered search to the chat tool. **Not auto-joined into `daily_health_matrix`** — same isolation principle as Spotify; cross-analysis happens at query time only. Notion is single write surface (read-only direction, unlike habits which is bidirectional). The app has two journal writers, both following the rules below and writing to Notion, never to the table: the /check-in journal draft (`POST /api/journal/entry`, 2026-11-14; every label reviewed by Riley and sent) and the /log **Journal** section (`POST /api/journal/file`, 2026-11-15, `lib/journal-file.ts` + `lib/journal-file-server.ts`; see "Log screen"): the body exactly as sent, Date = today in New York, Source as sent, and any of Title / Mood / Confidence / Topics left blank filled by ONE structured-output model call (`claude-sonnet-5-5`, effort low) that returns only those four labels (it never sees a way to change the body); a repeat of the same day and words within 15 minutes returns the page already there (Notion query on Date + created_time, then the page's paragraphs compared with the body). Both share the Notion calls in `lib/journal-file-server.ts`; neither logs the text. Sync via `journal_etl.py` hourly at `:35`. A Notion-hosted image is stored in `content_md` as `![caption](notion-image:<block id>)`, never as its download URL (signed, dead after about an hour); the embedding text carries only `[image: caption]`. Rows that were re-embedded and rows that were not are upserted in separate requests (`uniform_batches`; see the bulk-upsert rule under Conventions). Test: `tests/test_journal_etl.py`. Journal DB must be shared with the "SMS Reminders" Notion integration (same blocker as initial habits deployment — `project_onyx_habits.md` memory).

  **When creating a journal entry in Notion (e.g. forwarding a Claude conversation Riley dictated):** the `notion-create-pages` call **must** populate all four metadata properties — `Source`, `Confidence`, `Mood`, `Topics` — plus `Title` and `Date`. Never create a journal page with any of these unset. Parent: `{ type: "data_source_id", data_source_id: "de49562b-652b-4e95-94b1-085dc7ce8c99" }` (the Entries data source under the Journal DB).

  **Field rules** — these mirror the canonical version in the **"Reminders/Habits/Journal Entry"** Claude.ai Project, which is the source of truth for the mobile/web Claude flow. **When changing the rules here, also update that Project's custom instructions to keep both surfaces in sync.**
  - **`Source`** (select: `voice` | `typed` | `remarkable`). DEFAULT `voice` — anything originating from a Claude conversation. Override to `typed` only if the user explicitly says the entry's origin was typed text; `remarkable` only if it came from their reMarkable tablet.
  - **`Confidence`** (select: `high` | `medium` | `low`). Measures the **user's certainty about the entry's content** (NOT transcription confidence — repurposed 2026-05-24; the Notion property description was updated to match). DEFAULT `medium` whenever the entry doesn't clearly signal certainty — never leave blank. `high` for explicit conviction ("I know…", "definitely"); `low` for hedging ("I think maybe…", "could be wrong").
  - **`Mood`** (select: `low` | `neutral` | `good` | `great`). Infer from content; never leave blank. low = negative affect, neutral = informational/flat, good = positive affect, great = strong positive. If torn between adjacent values, pick the lower one.
  - **`Topics`** (multi-select). Prefer existing tags when one fits — current list: `work, relationships, dating, health, gym, running, alcohol, sobriety, mental-health, family, travel, reflection, goals, finance, sleep`. New tags are allowed only when none of the existing ones reasonably fit (don't add "fitness" when "gym" or "running" applies; don't add "anxiety" when "mental-health" applies). At least one tag per entry.
  - **`Title`** (title): short, specific, 3–8 words. Scannable in a list. Avoid generic titles like "Journal Entry" or "Note".
  - **`Date`** (date): today in `America/New_York`, date-only. Override if the user names a different date ("yesterday", explicit date).

  **Body — VERBATIM RULE.** The page body MUST be the user's raw text exactly as they said it. Do NOT summarize, paraphrase, condense, restructure, rewrite for clarity/flow/grammar, remove tangents/repetition/filler, add headings or bullet structure the user didn't provide, or add narrator framing ("Today Riley reflected on…"). The journal is a primary-source record of the user's own words. The ONLY editing allowed: sentence-ending punctuation + commas at clear speech pauses, paragraph breaks at natural topic shifts, capitalization, and unambiguous dictation-typo fixes (e.g. "their"/"there"). The `Title` is where summarization belongs — never let title-style condensation leak into the body. If the user explicitly asks for a summary ("just summarize this", "give me the gist"), summarize — otherwise the body is verbatim.
