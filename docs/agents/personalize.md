## UI preferences

- **UI preferences (2026-11-14, `sql/ui_preferences.sql`, `lib/ui-preferences.ts`, `/api/ui/preferences`)**: layout choices that follow Riley across devices, one row per key in `pds.ui_preferences` (`key` lower-case dotted, e.g. `overview.cards`; `value` a JSON object or array of at most 4 KB). Owner-readable (`owner_read`), written only by `PUT /api/ui/preferences` `{key, value}` with the service role; `GET /api/ui/preferences?key=…` answers `{key, value, updatedAt}` (value null = nothing saved). The route is owner-session only (never add `/api/ui` to `isCiRoute()`), same-origin JSON, 8 KB body cap, logs a database code only. Layout only: never store health or finance data there. Reuse it for any new synced layout setting (sidebar order, Personalize) under its own key instead of adding a table. Test: `frontend/tests/ui-preferences.test.cjs`.

## Personalize (2026-11-15)

Business Central-style page personalization (`components/personalize/*`, `lib/personalize-*.ts`). **Personalize** in the sidebar footer, the phone's More drawer and the command palette (on every page) opens the "Personalizing <page>" banner: **Done**, **Clear personalization** (this page, with a confirm), **Cancel** (drops this session's changes), **+ Add part** (hidden parts). Every part gets a frame with a drag handle (mouse: drag anywhere on the part; touch: the handle, plus up / down buttons on phones) and a menu: Move up / down / to top, Width (full / half / third, desktop only), Collapse by default, Hide. While a part is dragged (or moved with the keyboard: Space on the handle, arrow keys, Space to drop, Escape to cancel) an accent line shows exactly where it lands and the parts on either side move apart. Hidden parts show as hatched slots with Show while personalizing and are not rendered otherwise. Tables built with `PersonalTable` get a Columns chooser (show / add hidden columns, reorder) and a menu per header (move, hide, freeze pane); used on `/financials` transactions and `/status` Sync History. Leaving the page while personalizing keeps the changes.
- **Side panel and scroll order (`layout.areas`, `lib/nav-areas.ts`, `lib/nav-arrange.ts`, `components/personalize/NavArranger.tsx`):** while Personalize is on (any page; on a page without parts Personalize opens just this, "Personalizing the side panel"), the desktop sidebar's pages can be dragged within their section and sections by their name, with the same accent line; the phone drawer shows up / down buttons (44 px) plus Done / Cancel. Plain clicks do not navigate while arranging (Ctrl / Cmd + click does). The result is the app's ONE area order, `grids.main.order` of the UI preference `layout.areas` (area ids = `areaId(href)`: `/analytics/hrv` -> `analytics.hrv`): the sidebar and the drawer order pages within sections by it and sections by their first page, and the continuous scroll (`lib/feed-order.ts`) follows it. Saved with the page's changes on Done (`personalize-store` keeps a draft per key). **The scroll follows the draft live (2026-11-15):** each change to the `layout.areas` draft fires `LAYOUT_DRAFT_EVENT` (`onyx:layout-draft`, detail `{key, layout}`) on window, and `layout: null` when the session ends (after Done's save, or on Cancel / Clear); `ContinuousScroll` uses the draft while it is on and the saved copy otherwise, without importing the store (shell bundle); a scroll that starts listening mid-session fires `LAYOUT_DRAFT_REQUEST_EVENT` and an open session answers with its draft. This device's copy wins over the server's whenever it exists, even when it is a cleared (empty) layout, so Clear never brings the server's old order back. When the order changes under the scroll, `keepInOrder()` keeps the pages around the routed one that still follow each other in the new order and drops the rest, and the scroll grows again from there (it used to start again from the routed page). A full page load paints the saved order before React: `Sidebar` renders `navBootScript()` (plain ES5, reads `onyx.layout.areas`, writes CSS `order` on `[data-nav-area]` / `[data-nav-section]`), removed once React renders the same order; the drawer is closed at load, so it just re-renders. Keep `data-nav-area` / `data-nav-section` and the flex containers when editing the sidebar. Today's overview cards are a `layout.areas` grid too (`components/overview/Overview.tsx`: `<PartGrid storeKey={AREAS_KEY} target={false} bare>`, part ids = area ids, "Hide (also from the scroll)"), so the cards, the side panel and the scroll share one order; the area grid is editable in every Personalize session. The old `overview.cards` value is copied into `layout.areas` the first time the server has no area order (`personalize-store` `migrateOverviewCards`), then ignored; the overview's own Edit mode is gone. Tests: `frontend/tests/nav-areas.test.cjs`, `frontend/tests/personalize-draft.test.cjs`, `frontend/tests/feed-order.test.cjs`.
- **Pin, hide and the bottom bar (2026-11-15, same `layout.areas` value, read by `areaPrefsOf()` / `arrangeNav()` in `lib/nav-areas.ts`, written by `lib/nav-arrange.ts`):** while personalizing, each page in the side panel has a Pin button (to the **Quick access** group; drag a page into Quick access to pin it there, drag within it to reorder) and a ⋯ menu with Move up / down, **Hide from navigation** and **Hide from scroll** (two separate toggles). Hidden pages are listed under **Show hidden** (also outside Personalize, so they stay one click away; the command palette and G shortcuts still reach them). Stored as grid entries: `grids.main.hide` = left out of the continuous scroll (and its Today card, as before), `grids.quick` = Quick access (`order` = pinned pages in order, `hide[id]` true = a default pin, `QUICK_ACCESS`, taken out, false = another page pinned; the default pins store nothing), `grids.nav.hide` = left out of the sidebar and the drawer (hiding also unpins), `grids.tabs.order` = the phone bar's four slots. **Quick access pages lead the continuous scroll** (`parseAreaOrder` returns `pinned`, `areaOrder` puts them first; `DEFAULT_PINNED` in `lib/feed-order.ts` must equal `QUICK_ACCESS`). The phone drawer shows Quick access first too, and in Personalize (drawer, up to 340 px wide) a **Bottom bar** box: a preview plus one select per slot (Left 1, Left 2, Log fixed in the centre, Right 1, Right 2), each a page or More; choosing a page already on the bar swaps the two (`chooseTab`, `tabSlots` in `lib/mobile-tabs.ts`); with More off the bar the drawer opens from a menu button in the top bar. Pre-paint: the sidebar renders EVERY page twice, once in Quick access (`data-nav-quick`) and once in its section (`data-nav-area`), the copy not shown carrying `data-off="true"` and `hidden`, so `navBootScript()` can show a saved panel before React with CSS only (tests and the perf spec count only links without `data-off`); the bottom bar's `tabsBootScript()` keeps changed slots invisible (never moved) until React renders them. Tests: `frontend/tests/nav-areas.test.cjs`, `frontend/tests/mobile-tabs.test.cjs`, `frontend/tests/feed-order.test.cjs`.
- **How to make a page personalizable (the exact API; convert pages in parallel with this):**
  1. `import { Part, PartGroup, PartGrid } from "@/components/personalize/PartGrid";` (client component; a server component may render it).
  2. Right after the page header (keep the header, its `data-testid="page-heading"` and any range filter OUTSIDE the grid): `<PartGrid page="/your/route" title="Page title">`.
  3. Each section becomes `<PartGroup id="section-id" title="Section name" header={<the section heading element/>}>` and EVERY card, KPI tile, chart, panel and list block in it becomes `<Part id="part-id" title="Readable name" width="…">` as a direct child (no wrapper divs between them; drop the old grid wrapper and the `mb-*` margins: the group's grid spaces parts). Widths: `full` (default), `half` (2 per row from 1024 px), `third` (3 from 1024, 2 from 768), `quarter` (KPI tiles: 4 from 1024, 2 below). A part can also sit at the top level (a group of one). Parts move within and between the groups of the page; groups move, hide and collapse as one.
  4. Ids: lower-case, stable, unique on the page, never reused for something else (they are the saved layout's keys); titles are what Personalize shows. `{cond && <Part/>}` is fine (a data-dependent part keeps its saved place).
  5. Keep each chart's `<DeferredMount minHeight>` INSIDE its `<Part>`, keep data fetching where it is (a part that fetches its own data stops fetching when hidden), keep `isAnimationActive={false}` and every smoke-test string.
  6. Tables: build them with `PersonalTable` (`components/personalize/PersonalTable.tsx`: `columns` with `{id, label, th, td, hidden?, locked?}` and `rows` of `{key, className?, cells: {colId: node}}`) inside a `<Part>`; Personalize then offers the column chooser and the freeze pane.
  7. Where the page renders: client-rendered pages (the ISR dashboards with a `dynamic(ssr:false)` client) need nothing more. A force-dynamic server page passes `parts={[{id, title, node, members?}]}` (plain data) and `initial={layoutFromCookie(cookie)}` and is added to `SSR_LAYOUT_PAGES` (see `/financials`). A static server-rendered page (hydrates, like Today) uses `<PartGrid mode="css">` per container: order and hide only, no moves between containers. A page drawn inside the continuous scroll needs no change (`useInFeed` keeps the routed page as the Personalize target).
  8. Run `npx tsc --noEmit`; check it on production after the deploy (Personalize, drag one part into another group, Cancel).
- **Opting in (details):** wrap the page's blocks in `<PartGrid page="/route" title="…">` with `<Part id title width?>` as DIRECT children (`{cond && <Part/>}` is fine); ids are stable, lower-case, never reused for something else. Keep each part's `DeferredMount` (and its `minHeight`) inside the part, keep data fetching where it was, keep `data-testid="page-heading"` and the header outside the grid. A block holding its own `<PartGrid zone="…">` is a `<Part nested>` (parts then move only within that zone; prefer a `<PartGroup>`, whose parts also move between sections: `/status` source cards are a group with `gridClassName="pz-grid pz-tiles …"`, the dense tile columns, where Full / Half still widen a card). A server-rendered (force-dynamic) page passes `parts={[{id, title, node}]}` plus `initial={layoutFromCookie(cookie)}` and is listed in `SSR_LAYOUT_PAGES`. Adopted so far: `/analytics/hrv` (sections; its "On this page" list follows the layout via `usePartOrder`), `/sleep`, `/nutrition`, `/activities`, `/financials`, `/status`, `/today` (Today's own panels, 2026-11-15: ONE `<PartGrid page="/today" mode="css">` in `TodayClient.tsx` holding every panel AND the three section headings ("Heading: What needs you" etc.) as parts, so a panel moves into another section by dragging it past that section's heading; the header (h1 + Refresh) stays fixed and the overview cards keep their own `layout.areas` grid below; CSS mode = move and hide only, no width or collapse; the jump links do not follow the layout).
- **Storage:** one overlay per page in `pds.ui_preferences` under `layoutKey(route)` (`layout.analytics.hrv`, `layout.sleep`, …; at most 40 characters, the live table's limit), value `{v: 1, grids: {main: {order, hide, width, collapse}, <group id>: {order}}, tables: {<id>: {order, hide, freeze}}}` (top-level order in `main`, each group's order in its own entry, so a part listed in another group's order has moved there; hide / width / collapse are page-wide in `main`) holding only differences from the default: new parts appear at their default spot, removed parts drop out, Clear stores `{v: 1}`. This device keeps it in localStorage `onyx.layout.*` (wiped on sign-out); server-rendered pages also in a cookie scoped to the page's path. `?personalize=off` shows default layouts for one load.
- **Performance rules (Riley: "we need to be really fast"):** (1) the first render reads localStorage synchronously, so the personalized layout is the first thing painted: no request before paint, no re-render, nothing moves (the ISR dashboards render their parts client-side with `ssr:false`; server-rendered pages get it from the cookie); (2) a hidden part is not rendered, so it mounts nothing and fetches nothing (Weather and PM2.5 on `/analytics/hrv` fetch only when shown); page-level data (the ISR payload, `/api/status`) is shared and still loaded; (3) everything for editing (`PersonalizeEditor.tsx`: banner, frames, drag, menus, column chooser) is a separate chunk loaded only when Personalize starts (or on hover / focus of the entry); normal pages carry only `PartGrid` + `personalize-layout` + the store, and the shared shell only the tiny `personalize-registry`; (4) the server copy is checked in an idle slot after load, at most every 15 minutes per page, through the shared client cache; a newer copy from another device applies the next time the page opens (Personalize adopts it before editing); a change is written only when the layout changed (Done / Clear), in the background, retried on the next open when offline; (5) dragging writes the indicator and the gap straight to the DOM (no React render per pointer move). Tests: `frontend/tests/personalize.test.cjs` (overlay, columns, cookie, drop position).
