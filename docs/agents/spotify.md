## Spotify

- **Spotify tables are isolated from health data by design.** `spotify_plays` + `spotify_tracks` are NOT joined into `daily_health_matrix`. Listening behavior stands on its own; any health correlation happens at view/query time only. `spotify_daily_signature` is a per-ET-date aggregate view (play counts, unique tracks/artists, mean audio features) — frontend reads go through it where possible. PK on `spotify_plays` is `(played_at, track_id)` for idempotent upserts. `played_date_et` is a stored generated column matching the ET-canonical TZ convention.
- **Spotify audio features come from ReccoBeats, not Spotify.** Spotify deprecated `/v1/audio-features` for apps registered after 2024-11-27 (this app is post-cutoff). `spotify_tracks.features_source` records provenance (`'reccobeats'` or null when unresolved). The `spotify_daily_signature` view only computes feature means over plays with non-null valence so partial coverage doesn't bias the signal.
- **Spotify OAuth scope is `user-read-recently-played playlist-modify-private`** — both ingestion (ETL) and write (playlist creation from chat or `/spotify` button) use the same refresh token in `pds.ci_tokens`. If the scope changes, re-run `python spotify_etl.py --auth` then `python ci_token_helper.py upload spotify`; old refresh tokens still work but only carry their original scope claim. The Next.js client (`lib/spotify-server.ts`) refreshes on every call and writes the blob back to `ci_tokens` so the Python ETL stays in sync; that write-back is newer-wins (next bullet).
- **Spotify sign-in renewal: Reconnect on the `/status` Spotify card (2026-11-13).** The refresh token stops working 180 days after the sign-in (see Token recovery (Spotify) under GitHub Actions ETL). The Spotify card shows a **Reconnect** control (`components/SpotifyReconnect.tsx`) when its message means "sign in again" (`needsSpotifyReconnect` in `lib/spotify-reconnect.ts`: refresh token rejected / expired / revoked, `invalid_grant`, "sign-in expires", no token) and from **day 165** after the sign-in, when a healthy card also reads Degraded and shows "Reconnect by <date>". Flow: (1) `GET /api/spotify/auth-url` returns Spotify's authorize link and sets a random state in an httpOnly, Secure, SameSite=Strict cookie (Path `/api/spotify`, 10 minutes); the card shows the link, which opens in a new tab. (2) Spotify redirects that tab to `http://127.0.0.1:8888/callback?code=…&state=…`; nothing listens there, so the tab shows a page that fails to load, which is expected. (3) The address of that tab is pasted into the card → `POST /api/spotify/exchange` (`{callback}`; the full address, the query alone or the bare code; the address and the query must carry their state) checks same-origin + JSON + a 4 KB cap, compares the pasted state with the cookie (constant-time; the cookie is cleared after one attempt, except when Spotify's token endpoint did not answer, so Finish can be pressed again; only a bare code carries no state and is accepted on the cookie being present), exchanges the code server-side, requires a refresh token and both scopes, makes ONE `recently-played` call with the new token and only then stores the blob. A wrong account, a missing scope or a failed check leaves the stored token untouched. **Both routes are owner-session only: never add `/api/spotify/*` to `isCiRoute()`** (they mint and store OAuth credentials, and the CI token is held by several devices). The redirect address is ONE constant (`SPOTIFY_REDIRECT_URI` in `lib/spotify-reconnect.ts`, the address `spotify_etl.py --auth` has always used) for both the link and the exchange; never read it from env on Vercel. Answers carry a fixed message by code (`RECONNECT_ERRORS`) and never a token, the client secret, the code or Spotify's own response. **Token blob:** `pds.ci_tokens.token_data` is TEXT holding pretty JSON (indent 2) with `access_token, token_type, expires_in, refresh_token, scope, obtained_at` (epoch s of the last refresh) plus **`authorized_at`** (epoch s of the sign-in; absent on tokens from before 2026-11-13). Every sign-in route builds exactly this blob, in this key order, and refuses a sign-in that did not grant both scopes: Reconnect (`buildTokenBlob`) and `--auth` / the workflow's `auth_code` input (`token_blob_from_response` in `spotify_etl.py`); `tests/test_ci_token_spotify_guard.py` checks the two agree. Every refresh path keeps `authorized_at`; `/api/status` reads it server-side and exposes ONLY the derived date (`reconnectBy`: the ET calendar day of expiry minus one day; the `spotify|plays` heartbeat names the same day), because that response is CDN-cacheable. **Newer-wins writes:** a later `authorized_at` always wins, then the later `obtained_at` so a run or a site call that loaded the old sign-in's token before a reconnect never writes it back over the new one; within one sign-in the site's write-back also skips the write when the stored refresh token was rotated elsewhere and Spotify returned no new one. **Both refresh writers (the site's write-back and the workflow's upload) write only through `pds.save_spotify_token`** (`sql/spotify_token_atomic_save.sql`, applied 2026-11-14), which locks the row, compares and writes in one transaction and answers an outcome code (`written` / `same` / `older_signin` / `older_refresh` / `rotated` / `invalid`), never a token; a read-then-upsert in code let a reconnect landing between the two be overwritten (Codex review #168). `isNewerBlob` / `shouldWriteBack` and `spotify_upload_decision` are the offline models the tests use; never write the Spotify row from a refresh path with a plain upsert. The Reconnect store stays a plain upsert (it is the new sign-in; its write takes the same row lock). After a reconnect the card stays red until the next hourly run; `gh workflow run spotify-etl.yml` confirms at once. Needs `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET` in Vercel (the same Spotify app as the GitHub secrets). Tests: `frontend/tests/spotify-reconnect.test.cjs`, `tests/test_ci_token_spotify_guard.py`.
- **Spotify Feb 2026 API migration** affects this codebase. Use the post-migration endpoints in `lib/spotify-server.ts`: `POST /me/playlists` (NOT the removed `POST /users/{user_id}/playlists`) for create, and `POST /playlists/{id}/items` (NOT the removed `/tracks`) for add. Symptom of using the old endpoints is a bare `403 {"error":{"status":403,"message":"Forbidden"}}` with no scope hint. Migration guide: https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide. Development Mode apps additionally require the app owner to have an active Spotify Premium subscription. **Batch GET endpoints (`/v1/artists`, `/v1/tracks`, `/v1/albums`, etc.) were also removed** — same bare-403 symptom; replacement is per-id `/v1/artists/{id}` etc. `spotify_etl.py:SpotifyClient.artists()` already does this with a 50ms sleep between calls.
- **`pds.spotify_playlists`** logs every playlist Onyx creates (one row per `playlist_id`) with `track_ids` JSONB, `created_via` (`'chat'` | `'button'` | `'builder'`), and the originating `prompt` if from chat or builder. Audit + UI history. Not joined to other tables.
- **Playlist generation has three entry points**, all share `lib/spotify-server.ts:createPlaylist`:
  1. `/api/spotify/create-playlist` — one-click "Create from top tracks" button on `/spotify`, no LLM (passes a known track list). `created_via='button'`.
  2. `/api/chat` — general-purpose chat with 3 Spotify tools mixed in alongside health tools. `created_via='chat'`.
  3. `/api/spotify/generate-playlist` — **dedicated SSE-streamed endpoint** behind the "Generate playlist" modal in the `/spotify` page header. Free-text prompt + structured controls (source_pool, vibes[], era, genres[]). Runs a focused agentic loop with the same 3 Spotify tools, but **gates which tools the agent sees by `source_pool`** (`history` → only `query_spotify_tracks_by_features`; `discovery` → only `search_spotify_catalog`; `mix` → both) so the mode can't drift. Streams `status` / `tool_use` / `tool_result` / `message` / `done` / `error` events. `created_via='builder'`.
- **`pds.spotify_artists`** is a dim table for artist enrichment (genres, images). Spotify's Dev Mode `GET /v1/artists/{id}` post-Feb 2026 strips `genres`, `popularity`, and `followers` from the response — only `id/name/images/href/uri` come back. So genres come from **MusicBrainz** (no API key, 1 req/sec, polite User-Agent), looked up by artist name; top match's tags (sorted by user-vote count, top 8) populate `genres` as a JSONB array. Hit rate during initial backfill: 49/51 artists matched. Two artists initially missed via name-format issues (`JAŸ-Z` diacritic, `¥$` collab project); the lookup now retries a no-match with a normalized name (`normalize_artist_name`: NFKD, accents stripped, casefolded, punctuation/symbols removed) and accepts a retry result only when its normalized name equals the normalized query or its MusicBrainz score is ≥ 95 — the 1 req/sec limit and User-Agent unchanged (a symbol-only name like `¥$` normalizes to empty and is not retried). Refresh empty rows with `python spotify_etl.py --refresh-genres`. Tests: `tests/test_spotify_musicbrainz_normalize.py`. Initial seed for existing artists: `python spotify_etl.py --backfill-artists` (Spotify enrich) then `--refresh-genres` (MusicBrainz tags). The regular ETL handles both for new artists. Genre tags are crowdsourced — expect some noise like "british", "2020s", "favorites" mixed in with real genres.
- **Spotify play coverage is incomplete by design.** `recently-played` only contains plays that Spotify's backend received — offline playback from Spotify-licensed partner devices (Garmin watches with downloaded playlists, some car head units, older standalone wearables) does **not** report per-track telemetry back to the account, so those plays are invisible to our ETL, to Wrapped, and to Spotify-generated personalization playlists. Phone/desktop/web app plays are reported in real time and *are* captured. The `/spotify` page surfaces this as a coverage note under the page header so users interpreting the sonic profile / volume / ledger understand the dashboard under-counts Garmin-heavy workout listening. No code-level fix is possible — Spotify's partner SDK simply doesn't pipe the data.
