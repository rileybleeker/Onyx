## Financials (2026-11-12; SimpleFIN feed since 2026-11-14)

`/financials` reads a persisted finance ledger: `pds.finance_accounts`, `pds.finance_transactions` (`txn_key`; **`amount_cents` is expense-positive**, purchases +, income and refunds -; a non-empty `ignored_from` excludes the row) and `pds.finance_balance_snapshots` (per account, `captured_at`, `balance_cents`, `kind` asset|liability|null). **Since 2026-11-14 the feed is SimpleFIN Bridge** (`simplefin_etl.py`, next paragraph); everything before the cutover came from Rocket Money (CSV export + a browser harvester, now retired) and stays as it is (`finance_transactions.source` = `rocketmoney` | `simplefin`). **Rocket Money rows are keyed on Rocket Money's own transaction id (`source_txn_id`, `sql/finance_source_txn_id.sql`, partial unique index), not on the name or the amount**: the daily harvester reads the Transactions list from inside the signed-in app (no email, no export button; pending rows skipped) and upserts by that id, attaching the id to an export-origin row with the same (account, date, amount) instead of inserting a twin, or inserting with `txn_key` = sha256(`rmid|`+id) first 32 hex; the 7,009 export rows were tied to their ids once by `tools/rocketmoney_harvest/reconcile-ids.mjs` (6,997 matched; the n-th row of a same-day group in the file takes the n-th smallest id). `import-csv.mjs` stays for manual backfills and inserts only the surplus of CSV rows per (account, date, amount) group so a re-import cannot duplicate web rows. **The tables are SERVICE-ROLE ONLY** (RLS on, no policies, no grants to anon/authenticated, like `phone_usage_*`): the browser never queries them, the only reader is `lib/finance-ledger-server.ts` (`server-only`, service role, explicit column lists, 1000-row count-driven paging) called from the server page behind the owner-only middleware, no chat/LLM tool reads finance data, and nothing logs rows (errors log a code only). **The page is `force-dynamic`, deliberately NOT ISR** (private data: no CDN or shared cache, `noindex`); do not copy the ISR pattern here. Logic is pure and unit-tested in `lib/finance-ledger.ts`: money in/out exclude the one `NON_SPENDING_CATEGORIES` constant (Internal Transfers, Credit Card Payment, Savings Transfer) and ignored rows; refunds count as money in; net worth subtracts liabilities by absolute value; a balance with `kind` null is shown as unclassified and left out (never guessed from the account type); non-USD is never mixed into USD totals; balances older than 48 h get a stale badge. The page keeps empty ledger, failed query and data as three different states. `/status` card **SimpleFIN** (badge SIMPLEFIN, automated, `lib/finance-status.ts`, also the `/financials` freshness line): worst of the `simplefin|transactions` and `simplefin|balances` heartbeats, more than 14 h degraded, more than 30 h or a failed run red with the allowlisted SimpleFIN note (SEC-07: a fixed code and its wording, re-rendered from the code); heartbeats only, no amounts reach that cacheable endpoint. The Rocket Money card was removed with the harvester (its old `rocketmoney` heartbeats keep their history label). The browser-memory CSV workspace (PR #28) stays as a secondary "Preview a CSV" disclosure; it does not touch the ledger. Keep real finance data out of tests, screenshots, PR text and logs (the repo is public). Tests: `cd frontend && node --test tests/finance-ledger.test.cjs tests/finance-ledger-view.test.cjs tests/finance-ledger-server.test.cjs && node scripts/test-financials.mjs`.

**SimpleFIN Bridge feed (2026-11-14, `simplefin_etl.py`, `simplefin-etl.yml`, `sql/finance_simplefin.sql`, doc `docs/financials-simplefin.md`).** Replaced the Rocket Money harvester because its web sign-in expired within hours every day (no long-lived session, no refresh token on disk). SimpleFIN Bridge (beta-bridge.simplefin.org, $15/yr, Riley's account) aggregates the banks; Onyx holds only its read-only **Access URL** (credentials inside the URL) in the GitHub secret **`SIMPLEFIN_ACCESS_URL`** and `~/.simplefin_access_url` on the PC. One-time setup: Riley connects the banks on SimpleFIN's site, saves a setup token to `~/.simplefin_setup_token`, then `python simplefin_etl.py --claim --set-github-secret` (a setup token works once). Runs every 6 h at :30 (one `GET /accounts?version=2`, 45-day window (SimpleFIN warns above 45), max 90; SimpleFIN allows 24 requests a day and disables the Access URL beyond that, so do not raise the cadence). Investment accounts (Fidelity, the Wells Fargo brokerage; 2026-11-17) also write positions to `pds.finance_holdings` and trades / deposits to `pds.finance_investment_activity` (`sql/finance_holdings.sql`, service-role only, never in the spending ledger; a failed write never fails the run), shown as the Investments panel on `/financials` (`lib/finance-holdings-server.ts`). Coverage (2026-11-14): Amex, Wells Fargo, Citi, Discover, Fidelity daily; **Apple Card monthly** ("Updated Monthly"); **Apple Cash not offered** (Apple exposes it only on-device via FinanceKit). Rules (all pure, `tests/test_simplefin_etl.py`): pending rows are not requested; amounts flipped to expense-positive; dates = UTC date of `transacted_at`, else `posted`. **Account matching** (`finance_accounts.simplefin_id`): stored link, else institution + last four, else institution + name; an account that could be an existing one but is not unique is **skipped and reported** (heartbeat `partial`), never guessed; a new account gets its own row with a type inferred from its name, and an Investment or Unknown account is **balances-only** (trades and dividends are not spending). **Cutover** per account: a SimpleFIN row transacted more than 3 days before the last Rocket Money row and posted by that date is dropped; any other row is dropped only on identity evidence (PIPE-04, 2026-11-16: same amount and currency plus the same date and a description that names a merchant, paired one for one, or within 3 days the same merchant (one side's distinctive words all on the other, both rows leading with the word that names the business, and a shared word that is neither a city nor a kind of business: a city (the words before a trailing state code), a kind of business like COFFEE or a shared first word alone never counts; two-letter names such as `ZQ` and `XK` are merchant words, so they never collapse to the city) at the smallest date gap of both rows, in a group that is one to one or has as many SimpleFIN as Rocket Money rows that cannot be told apart (so a purchase repeated daily pairs day by day; a group of unequal size is never guessed, all kept as ambiguous and recorded with every candidate; the nearest date counts held and ambiguous rows too, so a row whose nearest candidate is held is never paired with a farther one); payee names whose distinctive words contradict, store numbers that contradict (`0042` vs `0099`), or two different kinds of business (`DEMO CAFE` vs `DEMO HOTEL`) are never a match, a shared STORE or COFFEE is no evidence); every SimpleFIN row of the response takes part, so a Rocket Money row is taken by its twin before the window (that match is recorded too), and a Rocket Money row a recorded decision matched stays taken on later runs (the ledger is read from before the earliest date in the answer, and every Rocket Money row the record names is read by key, whatever its date), the candidates of a row recorded as ambiguous stay held while that row is missing from a later answer, and a recorded match or ambiguity a row no longer carries (its amount or text changed) is re-recorded before the ledger write (`unconfirmed`, kept for review); an equal amount alone never drops a row: ambiguous or unconfirmed rows are kept, reported as `cutover_review` until a heartbeat carrying them is written (`review_state` pending -> reported in the record, so a lost heartbeat or a failed or stopped run never hides one; the doc has the query to check them until settled), and decisions are recorded by key in `pds.finance_cutover_matches` (`sql/finance_cutover_matches.sql`, applied 2026-11-16 except its `review_state` column, which is applied before the merge (until then every run stops, `cutover_provenance_unsaved`); **before the merge Riley runs `--dry-run` locally and accepts its counts, because the first run re-decides the cutover window**; the record is written before the ledger, the run's whole set in one statement (never in part), and a run that cannot write it writes nothing, `db_write_failed`, so a row is never left out on a match that is not on record; while the table is missing a run with decisions to record stops the same way, `cutover_provenance_unsaved`; any other read error fails the run before writing, `db_read_failed`) (Rocket Money never stored pending rows, so a row posted after it is kept unless matched), rows already written by SimpleFIN are rewritten in place. **Categories** (SimpleFIN sends none; `/financials` needs them to keep payments and transfers out of spending): a same-amount, opposite-sign pair on two of Riley's accounts within 5 days with payment / transfer wording on one side -> Credit Card Payment (a card on either side) or Internal Transfers (Zelle / Venmo / Cash App / PayPal never pair); else the category Rocket Money gave the same description, merchant name or first two words in the last 3 years (80-85% agreement); else payment / transfer wording; else none. Balance snapshots: `captured_at` = SimpleFIN's balance-date, liabilities stored as a positive amount owed (like the Rocket Money history), `kind` from the account's Rocket Money snapshots, NULL for a new account. **Output is counts only** (public Actions logs): never names, descriptions, amounts, ids or the URL; `--dry-run` (local only) prints the per-account matching for checking. Heartbeats `simplefin|transactions` + `simplefin|balances` on every run: `failed` (exit 1) when SimpleFIN cannot be read (403 = Access URL revoked or disabled: new setup token + `--claim --set-github-secret`; 402 = subscription lapsed), `partial` when SimpleFIN reports a connection problem (e.g. a bank needs reconnecting on SimpleFIN's site) or an account was skipped. Heartbeat text is an allowlist (SEC-07, 2026-11-16): a `NOTE_CODES` code + fixed wording + a count, never SimpleFIN's own message, a name or an id; `/status` and `/financials` re-render it from the codes alone (`lib/finance-status.ts` `SIMPLEFIN_NOTES`, kept equal by `tests/simplefin-notes.test.cjs`). Before the secret exists a scheduled run writes failed heartbeats and exits 0.

**Rocket Money harvester: RETIRED 2026-11-14.** `tools/rocketmoney_harvest/` and its Task Scheduler entry "Onyx Rocket Money Harvest" (disabled, not deleted) stay as the record of how the history was built and for a manual backfill (`import-csv.mjs`); the sign-in notes are in its README. Do not re-enable it as a feed: its sign-in lasted hours, not days.

## Cash forecast, budgets and taxes (2026-11-14)

Design: `docs/cash-flow-forecast.md` (backtest numbers in Section 9.1). Pages: `/financials/forecast`, `/financials/budgets` (both `force-dynamic` + `noindex`, server-rendered, never ISR) and a **Money** panel on Today (`GET /api/finance/alerts`). **Read-only: nothing moves money, pays or files anything.** All tables are service-role only (RLS on, no policies, no grants): `pds.finance_plan_items` (planned items, balance-positive cents, soft remove), `pds.finance_plan_drivers` (keys `settings`, `tax` = the tax profile, `card:<account>`, `growth:<account>` or `growth:virtual-<slug>` for a planned account such as the SEP IRA, `scenario:<slug>`), `pds.finance_category_rules` + `pds.finance_txn_categories` (category fixes, applied when the ledger is read by `loadCategoryFixes`; stored rows untouched), `pds.finance_budgets` (`__total__` = overall), `pds.finance_forecast_snapshots` (weekly). Routes `/api/finance/{forecast/*,budgets,categories,alerts}` are owner-session only: **never add them to `isCiRoute()`**.
- **Engine** `lib/cash-forecast.ts` (pure, seeded, no clock; config `lib/cash-forecast-config.ts`): cash pool = Cash accounts (checking + savings); streams by schedule with US bank-holiday rules; card payments = each card's MONTHLY TOTAL paid (mean of the last 3 months), also for payments that cannot be paired with the card's own rows (per payee); everyday baseline = mean weekly net flow of what is left (only unusually large money IN is left out; rows the budget ignores are kept); block-bootstrap low/high bands (backtest: ~80% coverage); planned items matched to actuals (late money in dropped, late money out kept); 0% promo end milestones (dates read from balance-transfer row text `EXPIRES MM/YYYY`, else the `card:` driver); net worth 24 months (cards with APR/promo, investments at an assumed 5% plus contributions). Backtest: `cash-forecast-backtest.yml` (manual, prints percentages only). **Safe to move is gated** (`result.eligibility`, read only through `lib/cash-forecast-eligibility.ts`): a missing, invalid, unreadable or stale (>48 h, any size) pool balance (a balance row the ledger parser rejects is kept as unusable, never dropped: `forecastBalanceRows`), a truncated read (history, or the paged plan items / plan drivers / category fixes stopping at their page limit), a failed plan read (`setupPending`), a saved tax profile / move plan that no longer parses, or a failed category-fix read, or under 4 weeks of history make `safeToMoveCents` null and the tile shows the reasons in the same part; only an account Riley leaves out (tile button, driver `safe-to-move`, one account per request, compare-and-swap on `updated_at`) is not counted in the amount and is named beside it (never automatic; it does not clear an unreadable balance or a debt in another currency), and the low-cash alert takes the same accounts out (`eligibility.leftOutCents`); a stored result past `eligibility.validUntil` is withheld when served (`forecastLoadAt`, `cashCheckAt`) and recomputed (Today: answered marked `updating`), and the tile re-checks it on the browser's clock; the what-if row and Today (`cash` in `/api/finance/alerts`) read the same result (doc Section 4.1; test: `frontend/tests/cash-forecast-eligibility.test.cjs`).
- **Everything editable on the page**: detected streams (paycheck, card payments, bills) via drivers `adjust:<streamId>` ({from, amountCents} or {from, stop}); forecast settings in the one `settings` driver (bufferCents, inflationPct, lookbackWeeks, cardMonths, lowPercentile; every save merges); planned items repeat monthly or yearly (stored as month x12); tax rules in the profile (bracketIndexPct for unpublished federal years, default 2.7%; gaRatePct / ncRatePct overrides; employerStateWithholding NC | none). The move, investment-account rows, card APR / promo, forecast settings and tax profile autosave after a pause or on blur, then the page re-reads (`lib/use-finance-autosave.ts`). Adding a planned item, a goal or a planned account, recording a tax payment, and the stream Set amount / Stop / Reset stay buttons.
- **Every year's bonus**: the tax profile's `annualBonus` (amount, profit share, growth %, first plan year) generates a bonus + profit share each January for 4 plan years (`allOneOffs`; an explicit January "bonus" one-off replaces that year's); `raisePct` grows salary each January (tax wages and the paycheck stream). The tax plan covers this year and the next two, so a January bonus received as a NY/NYC resident is taxed there.
- **Taxes** `lib/tax-plan.ts` + `lib/tax-tables.ts`: federal, Georgia resident period, NC nonresident share (credit in Georgia), NY part-year (income-percentage method) + NYC; employer withholds NC only; estimated payments, refunds and after-tax bonuses become forecast lines (`tax:*`, `pay:*`). **Tax years are picked by cash date, not calendar year** (`taxYearsFor`, 2026-11-14): every year with a line inside the two-year window, and LAST year stays in after New Year until its January estimate, April balance and refund are more than the late-match window (31 days) behind; a tax line whose date passed is kept for that window, so the engine matches it to the payment or refund, or keeps counting an unpaid balance as of tomorrow (recording it in `estimatesPaid` settles it). Never go back to "this year + N": a year's January and April lines vanished on Jan 1 (Codex #168). **Every table names its basis (2026-11-16, PIPE-10):** `published` (source URL, check date, effective years: federal 2026 + 2027, Georgia 2026 4.99% / $15,000, NC by S.L. 2026-41, NY 2026 and 2027-2032 with the 601(d-1) recapture), `assumption` (federal 2028+ indexed by `bracketIndexPct`, also when Riley entered the index; Georgia 2027+ until OPB's Dec 1 report is entered) or `override` (a Georgia / NC rate Riley entered); an assumption past its `staleAfter` date shows a visible line on that year, and tables unchecked for a year (`TABLES_CHECKED`) one line above the years. The yearly refresh is owned by the Onyx Roadmap row "[TAX-REFRESH] Refresh built-in tax tables" (due each December 15). Part-year: wages and other income split at the move date by receipt date; the rounded NYC months prorate only the NYC standard deduction. Due dates move like IRC 7503 (`taxDueDate`). Planning estimates, not filing.
- **What-if** `lib/cash-forecast-scenario.ts`: levers in the URL, recomputed on the server (the browser never receives transactions); saved scenarios = drivers `scenario:<slug>`. The other-income lever is a change against the tax profile's own figure from `otherIncomeStart` (default: next month), received as one twelfth at each month end (`wi:other:*` lines) and taxed in the year it is received (`TaxProfile.otherIncomeChange`, `otherIncomeFor`), so its cash and its tax agree; the profile's own other income is taken as already in the history and adds no receipts.
- **Budgets** `lib/finance-budgets.ts`: spending = counted rows after category fixes (card payments and transfers never count); pace, projected month end, suggested = median of 3 months; uncategorized merchants are filed as soon as a category is picked (merchant rule); budget amounts autosave (the overall field: empty changes nothing, 0 clears it). **Alerts** `lib/finance-alerts.ts`: low cash on the cautious path within 30 days, budget over / heading over, 0% promo within 60 days, tax payment within 14 days. `GET /api/finance/alerts` answers from the stored result (`pds.finance_result_cache`) with `asOf` (when computed), `updating: true` when it is an older stored answer being recomputed after the response (inputs changed, a new ET day, a new build), and `partial` (`forecast` | `budgets`) when one read failed (never stored). Today says so under the alerts and asks once more after 4 s with `?fresh=1` (computes before answering unless the stored answer is current), so an older answer is never shown as current and a new alert appears within seconds; an older empty answer that could not be updated, or a partial one, shows the panel with that note instead of looking like an all-clear (`lib/money-alerts-view.ts`, import-free, bundled by name in `tests/today-regression.cjs`; Codex #191 D5). A stored answer loads only the parse rules (PERF-02, 2026-11-16): `lib/finance-result-cache-server.ts` `import()`s the forecast, budgets and subscription-detection modules inside the computation and takes the service-role client from the small `lib/finance-service-client.ts`, so a request answered from the stored row does not load the forecast engine; keep new computation imports lazy there. Whether this shortens the cold call is a hypothesis not yet measured (`docs/perf-bursts-2026-11.md`, last section).
- **Snapshot** `cash-forecast-snapshot.yml` (Mondays 12:30 UTC) → `frontend/scripts/cash-forecast-snapshot.cjs` → heartbeat `finance_forecast|snapshot`, `/status` card **Cash Forecast** (>8 days degraded, >15 days or failed red); the page shows forecast vs actual from the snapshots.
- **Plan & assumptions** on `/financials/forecast` (`PlanConfig.tsx`, `lib/finance-plan.ts`): the NYC move as driver `move` (date, rent now, NYC rent, moving costs, deposit, deposit refund, living-cost change; it is the single source of the move date and overrides the tax profile's), each investment account's return / monthly contribution / start (drivers `growth:<account>` and planned accounts `growth:virtual-<slug>` such as the SEP IRA or an HSA), and inflation (`settings.inflationPct`). Seeded values are marked as estimates.
- **Subscriptions + cancel tracker** on `/financials/budgets` (`lib/finance-subscriptions.ts`, `pds.finance_cancel_marks`, `PUT /api/finance/subscriptions`): Riley cancels on the merchant's site and marks it; the page reports waiting / stopped / still charging from the ledger. Onyx never cancels. Feature comparison: `docs/finance-vs-rocket-money.md`.
- **Recategorize** any transaction on `/financials` ("This one" = `finance_txn_categories`, "All from this merchant" = `finance_category_rules`). **Savings goals** on `/financials/forecast` (`pds.finance_goals`, `lib/finance-goals.ts`, `/api/finance/goals`): progress from real balances, monthly need, and the forecast check for goals on checking + savings. Tracking only.
- Tests (synthetic only): `frontend/tests/cash-forecast.test.cjs`, `cash-forecast-store.test.cjs`, `tax-plan.test.cjs`, `finance-budgets.test.cjs`. Keep real amounts, merchants and names out of tests, logs, PR text and commits.
