## Speed budget

- **Speed budget (a standing requirement, restated by Riley 2026-11-14): nothing Riley waits for takes a full second.** Every page shows something the instant it is clicked (`loading.tsx` for anything not ISR), data is preloaded in the background when the app opens and served from the client cache, and no API or database call on a page takes 1 s. `perf-timing.yml` samples production hourly (not per deployment) and goes red on a breach (`perf-report.cjs --budget`, `budgetViolations` in `e2e/perf-stats.cjs`): any single API / database / Worker call of 1 s or more (the slowest call per view, not a mean), a page's data taking 1 s in any warm view or on the cold first visit, or a page not measured completely (a missing navigation is never a pass). It covers full loads of Today (every panel), Log (every section with its data), Check-in, the dashboards, Status, Financials, Budgets and Cash forecast, plus in-app navigations clicked from the sidebar after Today settles; each breach is labelled repeatable or isolated. The cloud watchdog raises a red run as `speed-budget-broken`; a red run is fixed in the next PR, not reported for later. Every frontend change states its before/after timing. A page's first GETs can start with the HTML instead of after the JavaScript and hydration (`lib/early-fetch.ts`: an inline script starts them, the client takes each response once for the same URL within 10 s; a 401, a redirect to sign-in or a network error is fetched again by the client so session-end handling still sees it). Used by `/check-in`, `/status` (its one read, same cache mode as the page's own fetch) and Today (`/` and `/today`: `app/today/EarlyReads.tsx` + `lib/today-early.ts` start reading, urgent email, orders, renewals, money alerts, the calendar for local today + tomorrow and the agents Worker's inbox with the session's token read from the Supabase cookie, and preconnect to the Worker) and `/agents` (`app/agents/EarlyInbox.tsx`: the inbox, or, when the URL opens one conversation with `?t=`, that conversation's first 60 messages, which AgentsChat takes once) and `/log` (`app/log/EarlyReads.tsx` + `lib/log-early.ts`: the check-in, supplements today / stacks / products, weight, reading, behavioral today and the journal list for the New York date; each section takes its answer through `cachedJson(url, { get: logEarlyGet(url, routed) })`, the embedded check-in through `earlyRead`; the Uber Eats section's Supabase reads, which a plain script cannot make, start when LogLoader's module runs after a full load, `app/log/early-delivery.ts`). GET only and read-only: never `/api/experiments/today` (it stamps the arm as revealed), never anything that writes or marks read; only the routed page takes them, never its copy in the continuous scroll. A URL added there must equal the client's own (`tests/early-fetch.test.cjs` checks Today's and /log's).

## Input saves itself

- **Input saves itself (Riley, 2026-11-15: "Onyx should autosave when I input data").** No Save buttons for data entry: use `lib/autosave.ts` (`useAutosave` in `lib/use-autosave.ts`, status line `components/AutosaveStatus.tsx`, `saveRequest` for the fetch). A tap saves after a short delay (a burst of taps is one request), typing after a pause and at once on Enter / blur / page hidden (keepalive) / unmount; one request in flight, the newest value wins; a 4xx (`AutosaveRefused`) is shown with Retry and not retried, anything else retries with backoff; everything not saved yet counts as unsaved work, so the updater never reloads over it. A new record is created once its required fields are complete and later edits UPDATE that record (never a second create). What the Say it box fills is Riley's own words and saves the same way (a journal entry the model only guessed at waits for Keep). Still never on open or on scroll (`useInFeed`). An explicit button stays only where the tap IS the action (Log a dose, Log it for a stack, Record payment), for a batch with no update path (lab results), or where a half-finished record must not land (photo-to-product review); say why in the code. Tests: `frontend/tests/autosave.test.cjs`, `frontend/tests/autosave-forms.test.cjs`.

## UI copy

- **UI copy (2026-11-14).** Screens show headings, numbers, units, legends and labels. No explanatory paragraphs on the screen: how a number is worked out, where the data comes from, privacy and sync notes go behind `components/InfoHint.tsx` (an "i" popover, or `variant="disclosure"` for a longer "About this" row), closed by default; on a card use ChartCard / SectionHeader's `hint` prop. A subtitle is at most one short line. Keep visible: empty / failed / loading states (tests and the smoke suite match their exact text), error messages and anything that changes what Riley should do. **Exception, Riley's decision: statistical explanations stay visible** (what a test or estimate means, how to read it, assumptions, caveats, sample-size and "association, not causation" notes: `/analytics/hrv`, `/bland-altman`, the caffeine × HRV comparison, travel analysis, experiments); tighten them, never hide them, and use ChartCard's visible `info` prop for them. Put InfoHint next to a heading element, never inside it (its "About …" name would join the heading's name). Offline UI harnesses that copy only `lib/` files (procurement, financials CSV preview) use a plain `<details>` instead.

## Navigation

- **Navigation has a single source of truth: `frontend/src/lib/nav.ts` (`NAV_SECTIONS`).** `Sidebar.tsx` (desktop), `MobileNav.tsx` (mobile PWA drawer), and `CommandPalette.tsx` all consume it — add new routes there once (label, href, icon, shortcut, section) and every surface updates together. (Historical note: the two components used to maintain independent `nav` arrays that had to be edited in pairs; that convention is obsolete.)

## Frontend perf architecture

- **Frontend perf architecture (2026-06-11, see `docs/perf_report_2026-06-11.md`)**: middleware verifies session JWTs **locally** via `supabase.auth.getClaims()` (project signs with ES256; never reintroduce a per-request network `getUser()` — it cost ~50-150 ms × ~13 requests per page view). Ten read-only dashboards are **ISR pages** (`export const revalidate = 3600`, matching the hourly ETL cadence): a server `page.tsx` runs the same `lib/queries` fns and passes `initial` data into a `<Name>Loader.tsx` client wrapper hosting the `dynamic(ssr:false)` chunk; the client seeds state from props and keeps its mount fetch as a **silent revalidation** (no skeleton — never skip it, a stale snapshot must heal). Pattern contracts: (1) server prefetch args must **explicitly mirror** the client effect's default-state args (several fn defaults diverge); (2) prefetch fns must `throw` on PostgREST error so the fail-open `try/catch` actually fails open; (3) write-coupled pages (`/supplements`, `/habits` with its on-load Notion-sync POST) are deliberately NOT ISR. Heavy tables are read via **explicit all-scalar column lists** (`WHOOP_*_COLS`/`GARMIN_*_COLS`/`EIGHT_SLEEP_TRENDS_COLS` in `queries.ts`) — `raw_json`-class jsonb blobs must never ride in page-load selects (whoop_cycles is ~70 kB/row of raw_json), and when an ETL adds a scalar column it must be appended to the matching list.

## Theme

- **Theme: Direction D "Instrument" (2026-11-14, replaced the Terminal theme).** Dark only: warm graphite surfaces (`surface` #1A1A18, `surface-sunken` #151513 for the side rails, `surface-card` #232321, `surface-raised` #2C2C29), one signal-orange accent `#FF6A1A` for controls, selection, focus and the primary action (text on it: `text-on-accent`), WHOOP-style status colors `up` / `mid` / `down` (#5BC46E / #F4C84E / #F0584E) that only mean state and always come with an icon or a word, Archivo for text and DM Mono (`font-mono` / `font-display`) for numbers and small labels (both vendored in `app/fonts`, see `SOURCE.txt`). Shapes: cards `rounded-card shadow-card`, buttons / inputs / nav items `rounded-control`, the primary action `bg-accent text-on-accent rounded-full`. Success marks ("Saved", "on time") use `text-up`, never the accent. `components/MetricRing.tsx` draws the 270° dial used for recovery, strain, habits and reading. All colors come from the tokens in `app/globals.css` or, for charts, `lib/chart-theme.ts` (categorical and device colors validated for color-vision separation on the card surface; Garmin / WHOOP / Eight Sleep pass for every pair). `frontend/scripts/test-theme-tokens.mjs` (CI) fails on a Terminal-palette hex, on `rounded-[4px|5px|6px]`, or when the chart palette drifts from the CSS tokens.

## Client cache, warm-up and skeletons

- **Client cache, warm-up and skeletons (2026-11-14; `lib/client-cache.ts`, `lib/client-cache-idb.ts`, `lib/warmup.ts`, `components/AppData.tsx`)**. Every client-fetched page renders at once from the shared cache and then revalidates (the mount fetch is never skipped). Rules every page follows: (1) **one key per GET**: the URL (path + query) for `/api/*`, `"<area>:<name>"` for other reads (`CACHE_KEYS`); store the raw JSON so Today, the page and the warm-up share it, and check a cached copy like a fresh answer before showing it. (2) **The server is the source of truth**: every cached read is revalidated; 404 / 410 / 204 or a fetcher answering null removes the entry; set state with the `sameJson` bailout. (3) **Persisted to IndexedDB, scoped**: the store records the Supabase user id and `CACHE_SCHEMA_VERSION`; another user or another version deletes the whole store before anything is read (bump the version when a cached shape changes). (4) **Memory only, never on disk**: finance, procurement, medical records, screen time, experiments (`/api/experiments/today` also stamps the arm as revealed, so the warm-up never calls it) and anything token / auth / session shaped (`isSensitiveKey`; add a pattern there for any new sensitive route); the `/financials*`, `/procurement`, `/screen-time` and `/health/records` server payloads live only in the router's memory cache. Mixed payloads that can quote those (the agents inbox and threads `agents:*`, `/api/status` heartbeat text, `/api/urgent-email`) and care items are memory-only too (SEC-03, 2026-11-16); `attach()` deletes any persisted row whose key is memory-only under the current rules, so a policy change needs no sign-out (schema 2 also cleared older stores). The browser's own HTTP cache is outside that wipe, so such a route that is CDN-cached sends `Cache-Control: private, no-store` and puts the CDN rule in `Vercel-CDN-Cache-Control` (Vercel consumes it), as `/api/status` does. (5) **Expiry and size**: every entry has a timestamp and a max age (7 days by default), expired entries are deleted when read and by the sweep at startup and once a day; the store is capped at 25 MB with least-recently-used eviction, a quota error evicts and retries once, nothing throws into a page. (6) **Writes**: keep the optimistic UI; `AppData` watches fetch responses, and a successful non-GET to `/api/<area>/…` (or the agents Worker) drops the `/api/<area>` and `<area>:` entries and refetches registered ones in the background (`writeInvalidates`; a page that writes its own state through, like `/habits` taps, is listed there as an exception). (7) **Session end wipes everything**: sign-out (Sidebar / MobileNav call `wipeClientData()`; Supabase `SIGNED_OUT`), any `/api` 401 or redirect to `/login`, a load without a session and every `/login` visit clear the memory cache, the IndexedDB store, Cache Storage and this app's localStorage keys (`onyx*`, `chartCard.*`; others stay). An auth error that is not proof of sign-out (offline with an expired token) only turns persistence off. **Warm-up**: nav links use `navIntentProps(href)` (no viewport prefetch; hover / focus / pointer-down warm that page) and `AppData` warms every page 2.5 s after the first page has loaded (then in an idle slot), one step per idle slot, tabs and quick links first then by local visit counts, and again after the app was hidden 10 minutes: `router.prefetch` (full for static / ISR / read-only pages, `auto` = code + skeleton for write-coupled server pages without `router.refresh()`: `/health`, `/health/records`, `/orders`, `/procurement`) plus each page's GET reads (`DATA` in `AppData.tsx`; GET only, nothing written or marked read). A new page with client fetches adds its reads there. **Never blank**: every force-dynamic route has a `loading.tsx` (`components/PageSkeleton.tsx`: real heading, theme tokens, no animation). `/` renders Today directly (no redirect). Tests: `tests/client-cache.test.cjs`, `tests/warmup.test.cjs`.

## Continuous scroll

- **Continuous scroll (2026-11-14; `components/ContinuousScroll.tsx`, `lib/feed-order.ts`, `lib/feed-registry.ts`, `lib/feed-seed.ts`, `components/FeedContext.tsx`)**. Below the end of the routed page the COMPLETE next page continues, then the next, in Riley's area order; scrolling up continues into the previous page. AppShell wraps the routed page in `<ContinuousScroll>` (not on `/login`, `/auth`, `/agents`, `/chat`, `/account`, `/install`, which are also left out of the sequence). **Convention:** every page in the scroll has `app/<route>/FeedSection.tsx` (`"use client"`, default export, no props) rendering the page's full content client-side, heading included, with its data from the client cache (finance, procurement, medical records and screen time stay memory-only there, as the cache already enforces by key). A FeedSection's heading carries `data-testid="feed-page-heading"`, never `page-heading` (the smoke suite looks for `page-heading` on the routed page): clients pass it as an optional `headingTestId` prop (Loaders forward it), or read `usePageHeadingTestId()` inside `InFeed`. **`lib/feed-registry.ts`** maps route -> `() => import("@/app/<route>/FeedSection")`; a route without an entry is skipped (the routed page always keeps its own place). `page.tsx` files never change for this: a direct visit or a reload renders the routed page normally. ISR pages render their Loader with `initial` = `readFeedSeed(route)`: a memory-only `<area>:feed` cache entry the page's client writes with `writeFeedSeed` after each successful load of its DEFAULT view (same shape and args as its server prefetch); the client still revalidates silently. **Order:** `feedSequence(NAV_HREFS, parseAreaOrder(value, known), routed, hasFeedSection)`: the UI preference `layout.areas` (this device's `onyx.layout.areas` copy first; shapes accepted by `parseAreaOrder`: `{order, hidden}`, a Personalize page layout `{v, grids: {main: {order, hide}}}`, or a list of hrefs / `{href, hidden}`; ids are hrefs or `analytics.hrv` / `analytics-hrv` style), else the nav order with Today first; hidden areas are skipped. **Rules:** the scroll starts 2 s after the routed page opened (then in an idle slot), or at once on the first wheel, touch, key or pointer gesture, so the opened page's own reads are not slowed by its neighbours' (speed budget, 2026-11-15); the next page is appended about 1.5 viewports before it is reached and the previous one prepended about 1 viewport before; pages load and mount one per idle frame with a skeleton (`PageSkeleton`) until then; only the page in view, its neighbours and pages within 1.5 viewports stay mounted (the routed page always), and a page more than 3 viewports away becomes a placeholder of its measured height; native scroll anchoring is off inside the scroll (Safari has none) and the element at the top of the screen is held in place by hand whenever anything above it changes height; every page has its own error boundary; mounting a page is a React transition (rendered in short slices, never one long task), and when the element at the top of the screen is replaced the page holding it keeps the screen still instead. **Scrolling never writes (2026-11-15):** a page in the scroll makes no request other than GET when it mounts or comes into view, and no GET with a side effect: no auto-save, nothing marked read, no notification cleared, nothing answered. The shared client checks `useInFeed()` (true inside every FeedSection; a `feed` prop where a test bundles the component by name, like `TodayClient`) and skips: the `/habits` Notion sync (`POST /api/habits/sync`), the `/activities` tag suggestions (`POST /api/activities/suggest-tags`, a model call that stores its answer), Today's experiment arm (`GET /api/experiments/today` stamps it as revealed; the scroll shows the copy `/today` read this session, if any) and the Personalize layout sync (`PartGrid`). The routed page keeps its own behaviour, and taps Riley makes inside the scroll still write exactly as on the page. A new page with a mount-time write gates it the same way. The page-data GETs of the finance pages and Today's money alerts may refresh the stored derived results in `pds.finance_result_cache` on the server, exactly as a visit to the page does; that is a cache of computed numbers, not a data change. Test: `frontend/tests/feed-no-writes.test.cjs`. **Registered (every nav page but Agents, Onyx Chat and Check-in, 25):** Today, Log, Activities, Nutrition, Supplements, Caffeine, Habits, Reading, Sleep, HRV, Travel, Bland-Altman, Screen Time, Spotify, Journal, Wins, Health, Medical records, Orders, Procurement, Financials, Budgets, Cash forecast, NYC, Status; the server-rendered ones read `GET /api/{travel,care,medical,orders,procurement,screen-time,finance}/page-data` (owner session, same-origin, no-store, the page's own server functions). **Page in view** = the page across the middle of the screen: `useActiveRoute()` (Sidebar, which also scrolls the item into view; MobileNav tab bar and drawer; CommandPalette's "Here"), `document.title` and the address bar follow it. The address changes with `history.replaceState` carrying the router's own state (`__NA`), so Next does not treat it as a navigation and `router.refresh()` still refreshes the routed page; the scroll puts the address back if the router rewrites it (on the next scroll and after every router update), but never while a navigation is under way: until the new routed page's reset effect has run (`syncedForRef`), nothing is written, because the previous page's observers would put its address back over the new page (2026-11-15). A nav click navigates normally and the scroll starts again from that page; the routed page is always in the scroll's list (a list built around the page being left, which a click landing as the scroll starts could leave behind, is reset to the routed page: 2026-11-15, the new page was otherwise not rendered and the address was rewritten to the old one). `GET /api/wins` (owner session, same-origin, no-store, `getWins()`) feeds the Wins page in the scroll. **Automated suites:** `sessionStorage["onyx.feed"] = "off"` (`FEED_OFF_SESSION_KEY`) turns the scroll off in that tab; the smoke suite sets it for every test, since its checks are about the routed page alone (a neighbour's chart must not stand in for a broken one). The perf timing run keeps the scroll on (neighbours' requests are part of a page view) but takes data-ready, chart and empty-state from the routed page only: neighbours are `section[data-feed-route]`, the routed page is `[data-feed-root] > div[data-feed-route]`. Tests: `frontend/tests/feed-order.test.cjs`.

## Frontend render conventions

- **Frontend render conventions (perf round 3, 2026-06-11)**: (1) **every recharts series element sets `isAnimationActive={false}`** — profiling showed mount animations never affect first paint (they run post-paint), cost up to ~820 ms of jank, and fully replay on every revalidation commit; (2) **ISR clients' silent-revalidation setters use the deep-equal bailout** `setX(prev => sameJson(prev, next) ? prev : next)` (`sameJson` in `lib/format.ts`) — the refetch is byte-identical to the seed in the common case, so the guard lets React skip the whole re-render; this makes **deterministic query ordering load-bearing** (any non-unique sort key needs a secondary `.order()`); (3) **chart-dense pages wrap below-fold sections in `components/DeferredMount.tsx`** (one-section-per-frame scheduler; everything mounts unconditionally without scroll — required by the smoke suite's below-fold assertions; never wrap above-fold content; give placeholders a realistic `minHeight`); (4) **tier-2 perf matviews** (`sql/perf_tier2_matviews.sql`): `tz_log_gaps_mat` + `hrv_prediction_gaps_mat` (/api/status), `spotify_daily_signature_mat`, `recovery_vs_pace_mat`, `hrv_residuals_mat` — same drift rule as the matrix matview (drop+recreate the `_mat` in the same migration as any change to its source view; never CASCADE); refreshed by `pds.refresh_perf_matviews()` at :12/:27/:42/:57 with ONE `perf_mats` heartbeat + /status card covering all five; both refresh functions use `REFRESH MATERIALIZED VIEW CONCURRENTLY` (2026-11-15, `sql/matview_refresh_concurrently.sql`): a plain refresh held an exclusive lock until the function committed, so page reads of these matviews (and, through held PostgREST connections, unrelated reads) waited 1-5 s twice an hour. Keep a unique, non-partial index on every matview.
