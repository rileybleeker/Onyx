## Flights

- **Flights — `pds.flights` from Delta confirmation emails (`flights_email_etl.py`, 2026-11-08).** Delta has **no public API for a traveler's own bookings** (developer portal is partner-only; TripIt's public API closed to new integrations Feb 2026) and its emails carry **no schema.org FlightReservation markup**, so the ETL is a **text parser over IMAP**. It reads **BOTH Gmail accounts** (rileybleeklm@ via `IMAP_EMAIL`/`IMAP_APP_PASSWORD`, rileybleeker@ via `IMAP_EMAIL_2`/`IMAP_APP_PASSWORD_2`; `_3.._5` accepted) read-only (`BODY.PEEK`, Gmail's `\All` folder so archived mail counts — inbox-triage archives the Updates category) and handles five operational email kinds from `DeltaAirLines@t.delta.com`/`@g.delta.com`: **receipt** ("Your Flight Receipt - NAME DDMONYY") + **award_receipt** ("Congrats On Your SkyMiles Award Trip") = the full itinerary (flight, cabin, CITY names, local times, ticket #; IATA codes come from the baggage block's "Sun 01 Nov 2026 / ATL-YYZ" row per direction, else the `CITY_TO_IATA` map); **trip_details** ("Your XXX > YYY Trip Details", ~3 days before each direction, carries IATA codes + seat; TWO templates — the Oct-2026+ "Flight 1 of N" layout and the older `DEPARTURE / YYZ / "6:30 PM Thu, May 07 DL2714" / DESTINATION / ATL / "8:55 PM …"` event layout, auto-detected); **checkin** ("It's Time To Check In For Your Flight", day before; one `TRIP ONE/TWO` block per direction, each with its own date, flight as `DL 2714` / regional `9E 4958` (→ normalized to the DL-marketed number) / bare `904`, cities only → IATA via `CITY_TO_IATA` + a **learned map** from rows receipts/trip-details already labeled, and it may CREATE a row when both airports resolve — needed because corporate/Concur bookings never produce a receipt in Gmail); **schedule_change** (marks the PNR's segments `status='changed'`; the later trip_details/checkin emails carry the corrected times and flip them back); **cancellation/refund** (carries only the 13-digit TICKET number → every segment on that ticket → `cancelled`). Promotional mail (`@o.delta.com`) is ignored. **One row per flight SEGMENT**, natural key `(confirmation_number, flight_number, dep_local_date)` — every email kind carries those three, so receipt → trip_details → checkin converge on one row; **latest email wins** (a row is only overwritten by an email at least as new as the one that wrote it; a receipt also marks segments it no longer lists `superseded`). IATA → IANA tz via the `airportsdata` package; `dep_time`/`arr_time` are real instants, the ADR-0001 quad is derived from `dep_time` with the airport offset as the **source-field tier** (`dep_utc_offset`), and `arr_behavioral_date` = (arr local − 6h). Overnight arrivals: explicit "**Thu 30APR" marker, else arrival instant ≤ departure instant → +1 day. `pds.flight_email_log` is the parse ledger (one row per operational email: `parsed`/`unmatched`/`error`) — re-runs skip known Message-IDs unless `--reprocess`; `status='error'` rows are the "Delta changed their template" signal. **Consumers:** (1) the HRV feature `journal_traveled_on_a_plane` via **`pds.flight_day_unified`** — the "Traveled on a plane?" habit was **retired 2026-11-09** (see the flight-day bridge bullet; the `/check-in` plane pre-fill was removed with it); (2) **`user_tz_log` flight-auto path**: landed segments whose arrival-airport TZ has a different UTC offset than the log resolves at the landing instant get a `user_tz_log` row (`notes='flight-auto: DL108 ATL→MAD conf …'`), effective at the exact landing instant; same-offset cases skip; priority stays Manual > GPS-auto > WHOOP-auto > flight-auto (gaps only); (4) the **Flights table on `/analytics/travel`** (ISR hourly; upcoming segments first, then history; `pds.trips` below it still only lists non-ET trips, so Toronto shows up here and not there); (3) `/status` **Flights** card (badge DELTA) = heartbeat age (`flights|email`, cron every 3h → >4h partial, >12h failed) — a quiet travel month is healthy; a `partial` heartbeat also flags "only 1 of 2 accounts configured" or a parse error. **Parser QA:** `python flights_email_etl.py --file <saved .html|.txt>` prints the parsed segments; the 2026-11-08 samples (receipt, award receipt w/ overnight MAD arrival, trip details, check-in) all round-trip, and the four real segments they describe (HUBS4H ATL↔MAD Apr/May 2026, G9R752 ATL↔YYZ Nov 2026) were seeded into `pds.flights` to validate the trigger + consumers. Not joined into the HRV matrix (the plane habit already carries the signal); a future `is_flight_day` feature can read `pds.flights` directly. **Credential gotcha (2026-11-08):** the ETL logs each mailbox as `fp=<sha256[:8]>` because CI masks the address — rileybleeklm = `f9cc8009`, rileybleeker = `efbd0e49`. The legacy `IMAP_EMAIL` secret (2026-03-30) turned out to be a THIRD mailbox (`0b263cb6`), and the rileybleeklm App Password in `~/.gmail_app_password` was already revoked (AUTHENTICATIONFAILED) — so the slots ended up as: `IMAP_EMAIL_2`/`IMAP_APP_PASSWORD_2` = **rileybleeker** (working since 2026-11-08 18:57Z; that inbox holds zero Delta mail — all Delta goes to rileybleeklm), and `IMAP_EMAIL_3`/`IMAP_APP_PASSWORD_3` = **rileybleeklm** (pending a fresh App Password; 2-Step Verification must be on first). Until slot 3 works the Flights card stays `partial` and names the missing account in its error text.
- **Flight-day bridge (`sql/flight_day_unified.sql`, 2026-11-09).** The WHOOP-derived habit "Traveled on a plane?" was **deactivated in Notion** (Active=false — name frozen, all 308 rows preserved) because `pds.flights` now records flights automatically; it no longer appears on `/check-in`. Unlike the melatonin/sauna/caffeine drops, the **feature identity is kept**: `hrv_analysis.py:build_feature_matrix` OVERWRITES `journal_traveled_on_a_plane` (label "Air Travel", journal family, causal binary enumeration) with the read-only view `pds.flight_day_unified.flew`, one row per behavioral day: **1** = a confirmed/changed segment departs or lands that behavioral day OR the frozen habit said Yes (keeps the 6 non-Delta Yes days of Feb–May 2026); **0** = inside tracker coverage with neither (this fills the never-answered days and overrides the habit-No days that had a tracked flight); **NaN** = before coverage and unanswered. Coverage starts at the behavioral day of the earliest `parsed` row in `pds.flight_email_log` (a 1200-day IMAP backfill on 2026-11-09 reached Aug 2023 → 66 flight days vs 22 habit Yes), so a longer `flights-email.yml -f days=N` backfill widens it automatically. **Known gap: non-Delta flights after retirement read 0** — add the airline to `flights_email_etl.py` if that starts to matter. `source_flag` ('flight'|'habit'|'both'|'tracker_no_flight'|'habit_no') audits each day.

## Online orders

- **Online orders — `/orders` from shipping and delivery emails (`orders_email_etl.py`, 2026-11-12, `sql/online_orders_schema.sql`).** Tracks what Riley ordered online, what is on the way, what arrived and what is overdue. No store or carrier gives Riley an API, so the emails are the source: one Gmail search per account (subject words like shipped / delivered / out for delivery / order confirmed; Promotions + Social and food-delivery, travel and digital senders excluded in `EXCLUDED_SENDER_DOMAINS`), read-only like the other email ETLs (it reuses `flights_email_etl.py`'s IMAP plumbing; Riley chose the email path on 2026-11-12 knowing the email-risk note). Each email becomes one `pds.online_order_events` row keyed by Message-ID (status ordered / shipped / out_for_delivery / delivered / delayed / exception / canceled, store, order number, tracking numbers + carrier, expected date, up to 5 item names; `ignored` / `error` rows too, so a re-run skips what it read; bump `PARSER_VERSION` to re-read everything). **Never stored: bodies, the shipping address, phone numbers, prices or payment details**; USPS numbers printed with the 420+ZIP prefix are stored without it, and item names that look like an address or the recipient's name are dropped. Every run then **recomputes `pds.online_orders` from all events** (pure `build_orders`): emails join when they share store + order number or a tracking number (a store's shipped email, Amazon's "package from X" email via the TBA number in its tracking link, and UPS / FedEx notices land on one row); emails with no number, and "delivered" emails that quote another number (Thorne does), join the same store's nearest open order from 21 days before to 5 after; Amazon emails without a tracking link are matched to the store by name. `confirms_delivery` = the store (or Amazon / the carrier) emailed "delivered" for at least 60 % of its last six shipped orders older than 10 days. **"Overdue" is decided at read time** in `frontend/src/lib/online-orders.ts` (`classifyOrder`): on the way until 2 days past the expected date (10 days after shipping with no date), then **Needs attention** if the store usually confirms delivery, otherwise **No delivery email** (quiet); a carrier-reported problem = attention; ordered 7+ days with no shipping email = attention only for a store that ships and only with an order number; everything drops off 30 days after shipping (45 after ordering); delivered / canceled stay listed 30 days. Riley's one-tap **Got it** (arrived) / **Hide** / **Undo** go to `PATCH /api/orders/[key]` (owner session, same-origin JSON, ≤256 bytes, `{action}` only) → `pds.online_order_marks`, stored under the order's key and matched by any alias, so a key change from a later email keeps the answer; the ETL never touches marks. **All three tables are service-role only** (RLS on, no policies, no anon / authenticated grants); `/orders` is `force-dynamic` (not ISR) and reads them server-side via `lib/online-orders-server.ts` (`server-only`). Today shows a **Packages** panel only when something needs attention or arrives today (`GET /api/orders/summary`). `/status` card **Online Orders** (badge GMAIL) = `online_orders|email` heartbeat age (>4 h partial, >12 h or failed red; partial also = an account missing or an email failed to parse). **Personal Amazon.com orders (2026-11-12)** send no email to either Gmail account (checked: the 400-day backfill found none), so the Kindle harvester's 3-hourly pass on Riley's PC (same signed-in personal-account Chrome profile) also reads the "Your Orders" list (past 3 months, up to 3 pages; `tools/kindle_harvest/amazon-orders.mjs`, `--orders-only` to run just that step) and posts order number, order date, status, status / expected date and up to 5 item names (never the total, address or recipient) to **`POST /api/orders/amazon/import`** (an exact-path entry in `isCiRoute()`; `lib/amazon-orders.ts` validates and drops any item text with an amount). The route writes INSERT-ONLY `pds.online_order_events` rows keyed `amazon-web:<order>:<status>:<date>` (store `amazon.com`), so a status's first-seen time sticks and a changed expected date (a delay) is a new event; the next `orders_email_etl.py` run folds them into `pds.online_orders` (up to 3 h later). Heartbeat `amazon|orders` on every call (failed on an expired Amazon session or a harvester error, partial when cards could not be read); `/status` card **Amazon Orders** (badge AMAZON, Kindle-style >12 h / >48 h thresholds). Stores that never email on delivery (Thorne, Flakes) can only be closed with Got it. Tests: `tests/test_orders_email_etl.py` (44, synthetic), `frontend/tests/online-orders.test.cjs` (22), `tools/kindle_harvest/amazon-orders.test.mjs` (9).

## Google Calendar (read-only feeds)

- **Google Calendar — `pds.calendar_events` from the calendars' iCal feeds (`google_calendar_etl.py`, 2026-11-13, `sql/calendar_events_schema.sql`).** Read-only, one way (Riley's calendars → Onyx): this source never writes to a calendar and never reads or writes care items. **It is not the `/health` "Google Calendar sync" (care items → a calendar Onyx created; OAuth, `lib/care-google*`, `pds.ci_tokens` service `google_calendar`, see the Health section): opposite direction, no shared code, no sign-in.** Do not put that "Onyx care" calendar's address in the secret (its events are copies of care items the page already shows). Source: Google Calendar's "secret address in iCal format", one per calendar, listed in the secret **`GOOGLE_CALENDAR_ICS_SECRET`** = a JSON list of `{account, calendar, url}` (`account` / `calendar` are short labels Riley picks: letters, digits, space, `_ . -`, never an address; any ICS feed works, e.g. a published Outlook calendar; same JSON in `~/.onyx_gcal_ics.json` on the PC). Runs hourly (`google-calendar-etl.yml`, :55): one GET per feed (Google builds it per request, no ETag), expands recurrences with `icalendar` + `recurring-ical-events` inside **ET today −400 d .. +400 d** and upserts one row per instance. Stored: title, `start_at` / `end_at`, `all_day`, `start_date` / `end_date` (**inclusive**; an all-day event's exclusive DTEND minus one day; a timed event's local dates in `tz`), `tz` (the event's TZID, else the calendar's zone; NULL for all-day), location, status (`confirmed` | `tentative` | `cancelled`), the two labels, `recurring`. **Not stored: description, attendees, organizer, conference links, the UID, the feed URL.** Links, meeting ids and passcodes are also cut out of the title and location (`_scrub` in the ETL); a location that was only a meeting link is stored as "Online meeting". No `onyx_*` date columns (not a behavior source; an all-day event has no instant). Key `event_key` = sha256(account, calendar, UID, original slot)[:32]: the slot is empty for a one-off (moving it updates the same row) and the RECURRENCE-ID as a UTC instant for a series (a moved instance keeps its row). **The X-WR-TIMEZONE trap:** `recurring-ical-events` applies Google's `X-WR-TIMEZONE` header by default, which rewrites UTC-form series into the calendar zone before expansion, so they drift an hour across DST and edited instances come out twice; the ETL reads the header (display zone for UTC-form and floating times) and **removes it before expansion** (`tests/test_google_calendar.py` pins this; never drop that `cal.pop`). **Secrets (the repo and its Actions logs are public):** a feed URL is a bearer credential for the whole calendar, so it never reaches a log, an exception, a traceback or `sync_log`: `httpx` / `httpcore` loggers are at WARNING (httpx logs the full URL at INFO), every URL is registered with `::add-mask::` (GitHub masks only a secret's whole value, not the URLs inside the JSON), fetch errors are re-raised as a plain message `from None`, `retry_helper` is not used (it logs exception text), and database / parser error TEXT is never echoed (it can quote a row or a feed line) — only the type and code. Logs and `--dry-run` print counts only and name a feed by position (`calendar 1/2`); the heartbeat (owner-only) names it by label. **Removal:** the feed lists what exists now, so after a fully validated fetch + parse the calendar's rows not seen this run (inside the window, one day in from each edge) are removed; **never for a calendar whose fetch or parse failed** (a reset address answers 404, or 200 with a web page: the body must start with `BEGIN:VCALENDAR` and end with `END:VCALENDAR`); nor for one that parsed only partly (a malformed series or a skipped event: what parsed is still upserted, nothing is removed, so the unreadable events keep their last known rows, and the heartbeat is `partial`); a run that would remove more than half of a calendar's rows (once over 25) is refused → `partial`, override with the workflow input `allow_large_removal`; rows of a calendar no longer in the secret are removed. Cancelled instances are upserted as `cancelled` (so a stored one flips) and left out of every count and every read. Heartbeat `google_calendar|events` on every run: `success` / `partial` (a feed failed, a malformed series or event was skipped, a large removal was refused) / `failed` (every feed failed, the secret is missing or not valid JSON, the table is missing → the message names the SQL file). **Recovery:** `HTTP 404` for a calendar = its secret address was reset or is wrong → copy the new one (Calendar settings → the calendar → Integrate calendar) into the secret and the dotfile; to revoke a leaked address press Reset there. **Consumers:** `GET /api/calendar/events?from&to[&summary=1]` (owner session only, NOT in `isCiRoute()`, `force-dynamic`, `no-store`, range ≤ 62 days, the query is padded a day each side; reader `lib/calendar-events-server.ts`, `server-only`, service role, explicit columns; `not_connected` when the table is missing) → `/health` (the "Your calendar events" card under the connection card shows the real state: synced with labels, event counts and last sync age / not synced yet / late / sync failing / couldn't be checked, and has no button; Month + Agenda show the events after each day's care items, labelled "Google Calendar: <label> (read-only)", as entries with no care-item id; `lib/care-planner.ts` stays import-free; the events path issues GETs only) and Today's Calendar panel. Pure helpers in `lib/calendar-events.ts` (import-free; day bucketing uses the browser's zone: a timed event is listed on the day it starts, one of 24 h or more also on the later days). `/status` card **Google Calendar** (badge GOOGLE; dedicated limit-1 heartbeat read; >3 h partial, >8 h or a failed run red; heartbeat only, no event rows on that cacheable endpoint). **iCloud (CalDAV, 2026-11-17, `caldav_source.py`, optional):** the GitHub secret `ICLOUD_CALDAV_SECRET` = `{"account": "<label>", "username": "<apple id>", "password": "<app-specific password>"}` (a list holds several Apple IDs; unset = no iCloud source; the app-specific password also opens iCloud Mail, so it lives only in GitHub secrets, never in a file or chat). The ETL discovers every VEVENT calendar in the account (PROPFIND principal, home set, listing; reminders lists are skipped), runs one `calendar-query` REPORT per calendar for the window and merges the event resources into one iCalendar text that goes through the same `expand_events` path as a Google feed (account label = the secret's, calendar label = the iCloud calendar name sanitised to the label rule, `Home 2` on a repeat). Read-only (PROPFIND / REPORT only); the credential is sent only to `*.icloud.com` over https, redirects are followed by hand and checked; credentials are masked in Actions and never reach a log, an exception or a heartbeat. Same safety rules as a feed: a failed discovery or calendar never reconciles (rows kept), an unreadable event resource fails that calendar rather than letting its stored events be removed. Apple's own OAuth is a closed pilot, so CalDAV + app password is the only route. Built against the CalDAV standard and iCloud's documented behaviour with a mock server; NOT yet run against a real iCloud account. **The work Outlook calendar needs no code:** Outlook on the web > Settings > Calendar > Shared calendars > Publish a calendar (availability only keeps subjects and client names inside the tenant), then add the ICS link as one more `{account, calendar, url}` entry in `GOOGLE_CALENDAR_ICS_SECRET`; whether the employer allows publishing is Riley's call. Tests: `tests/test_icloud_caldav.py` (synthetic, `httpx.MockTransport`). Known limits: a declined invitation still shows (the decline is only on the attendee line, which is not read); ICS has no event type, so working-location / out-of-office entries look like ordinary events. Tests: `tests/test_google_calendar.py` (62, synthetic ICS), `frontend/tests/calendar-events.test.cjs`, `frontend/tests/health-calendar.test.cjs`, `frontend/scripts/test-care-planner.mjs`, `tests/today-regression.cjs`.
