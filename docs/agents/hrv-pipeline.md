## Alignment and dates

- **HRV alignment rule — one place: `hrv_alignment.py` (fixed 2026-11-10).** Row D of `pds.daily_health_matrix_behavioral` is behavioral day D, and its `whoop_hrv_rmssd` is the HRV of the sleep that CLOSES day D (WHOOP cycle dated by sleep onset − 6 h). Every consumer — Spearman / Welch / Granger / OLS, the causal layer, XGBoost, SARIMAX, Prophet and the backtest — scores a day-D behaviour against the SAME row's HRV via `al.add_outcome` / `al.outcome_series` (horizon h = the sleep closing day D+h−1). **Never build an outcome with `.shift(-…)` in the pipeline files** — the live test greps for it. Three column groups sit on another day in the matrix and are re-keyed by date in `al.realign_matrix` before any feature is derived (live checks 2026-11-10): WHOOP cycle totals (`whoop_day_strain`, `whoop_kilojoule`, `whoop_cycle_avg/max_hr`) describe the waking day AFTER row D's sleep (strain row D vs workouts row D+1 r=0.83, same row −0.01) → moved one day later; `eight_sleep_*` and `garmin_hrv_*` are keyed by the wake-up day (the previous night sits on row D; r=0.84 / 0.82 with WHOOP one row earlier) → moved one day earlier; the pandas merges of `garmin_sleep` / `garmin_hrv` / `eight_sleep_trends` extras go through `al.wake_date_to_closing_day`. `whoop_steps` (a WHOOP cycle total merged in pandas, not a matrix column) is dated from each cycle's own local start by `al.cycle_waking_day` (= cycle date + 1 for a night-time onset), cycles on one day summed. Garmin daily summary / stress / zones / training status stay on the clock day (activity = day D, overnight fields = the night before day D — both before row D's sleep). Garmin activities and WHOOP workouts are keyed on `onyx_behavioral_date`. Columns measured from the outcome sleep or anchored to its onset (`al.is_same_sleep`, `al.NEEDS_SLEEP_ONSET`) are mediators for the causal layer and never forecast inputs; other measurements of that night's HRV / RHR (`al.OUTCOME_TWINS`) are left out of the Spearman driver ranking. **The forecast** predicts from behavioral today's row (`al.serve_index`, ET − 6 h): tonight's sleep, the HRV Riley wakes up to tomorrow. `pds.hrv_predictions.prediction_date` = the behavioral date of the predicted sleep (same key as the matrix, the backtest and SARIMAX / Prophet; `actual_hrv` = matrix row `prediction_date`), and `/analytics/hrv` shows the wake-up date (+1). The model pickle carries `alignment = al.ALIGNMENT_VERSION`; `hrv_predict.py` refuses a pickle from another rule. It also carries `preprocessing` (2026-11-16, PIPE-07): the sparse Garmin columns (`HIGH_VALUE_SPARSE_FEATURES`) are forward-filled by ONE function, `fill_sparse_features` (at most 7 calendar days, on the full frame before rows without an outcome are dropped), in both `prepare_ml_data` and `serve_features`; `hrv_predict.py` serves a pickle stamped with the current fill with that same fill (an older, unstamped pickle keeps the old 7-row serving fill, which never matched its training, until the next retrain, with an `hrv_predict|preprocessing` partial heartbeat at most every 12 h) and refuses an unknown one (`GUARD model_preprocessing:`). Test: `tests/test_hrv_sparse_fill.py`. **Model publication (2026-11-16, PIPE-08):** `hrv_model_artifact.py` and `sql/hrv_model_artifacts.sql` publish each trained model once with its provenance and serve it by registry rule (a pin or an unreadable registry fails closed); test `tests/test_hrv_model_artifact.py`. **Runtime guard** (`check_alignment` at the start of every retrain): a row whose HRV ≠ the recovery of the WHOOP cycle dated to it, or a re-keyed column that lines up with an adjacent row, fails the run (`GUARD hrv_alignment:` failed heartbeat); the alcohol canary (drinking must lower the same night's HRV more than the next night's) writes a `GUARD alcohol_canary:` partial heartbeat if it reverses. History: `b0828fa` (2026-04-04) introduced `shift(-1)`, correct under the old wake-day matrix; ADR-0001 (`165b879` + `a04d35e`, 2026-05-25) re-dated the matrix and left it, so from 2026-05-25 to 2026-11-10 every behaviour was scored against the night after the one it preceded (the re-audit's "DISPUTED P0", gemini F-001). Findings from that period are void; `pds.hrv_analysis_results_pre_alignment_20261110` holds the last pre-fix snapshot for comparison. Brief: `docs/handoff-hrv-alignment-2026-11-10.md`. **Dashboard side of the cutover (2026-11-11, `lib/hrv-forecast-cutover.ts`):** live rows in `pds.hrv_predictions_latest` with `prediction_date` < 2026-11-10 were made under the old one-night-late pairing; the walk-forward backtest rows are re-run by every retrain, so they follow the current rule. The Prediction-vs-Actual chart marks the first same-night forecast with a dashed line and a caption, draws no red miss-dots on old-pairing points, and the Residual Distribution histogram (`getHrvResiduals`, read from `hrv_predictions_eval` so rows carry `model_version`) leaves out nights whose only row is an old-pairing live forecast. It must NOT read `hrv_predictions_latest`: that view prefers a live row over a backtest row, so on ~170 dates it would serve the old-pairing live row and hide the same-night backtest residual the retrain rewrote (histogram 521 → 337 nights); `_eval` keeps the newest row, which is the backtest one (checked 2026-11-11: 514 backtest + 1 same-night live counted, 6 old-live-only nights left out). Any new frontend accuracy number built from forecast rows goes through `splitComparable` / `isSameNightComparable`.
- **All date arithmetic in the HRV pipeline uses ET, never naive `date.today()`.** Both `hrv_predict.py` and `hrv_analysis.py` define `et_today()` (`datetime.now(ZoneInfo("America/New_York")).date()`) and use it for `prediction_date`, `MODEL_VERSION`, and every "today"/"tomorrow". A naive `date.today()` returns the **UTC** date, so a late-ET-evening CI run (already the next UTC day) mis-tags by +1. `hrv_analysis.py` had exactly this bug — its `_behavioral_v1` retrain rows got `prediction_date`/`model_version` = ET **+2** on evening runs (e.g. a forecast meant for tomorrow tagged day-after-tomorrow), which then dragged the `/status` freshness anchor into the future and showed every fresh source as "Degraded". Fixed 2026-06-06: ET-anchored `hrv_analysis.py`, deleted the 455 spurious rollover rows, and added a `pds.hrv_predictions_latest` tiebreak so the canonical `_v1` predict path always wins over `_behavioral_v1` for the same `(prediction_date, model, horizon_days)`. The `/status` freshness anchor (`spineMaxDate`) also no longer includes any prediction date — freshness must track observed data, never a forecast.

## Tables, forecasts and accuracy rows

- HRV analysis tables: `hrv_predictions` (model forecasts + actuals), `hrv_model_metrics` (rolling eval), `hrv_analysis_results` (correlations, journal impact, model comparison as JSON)
- **Multi-horizon XGBoost + baseline backtest (h=1..7).** Previously only SARIMAX wrote multi-horizon rows to `pds.hrv_model_metrics`; XGBoost / baseline_naive / baseline_7d_avg / baseline_dow were `horizon_days=1` only, leaving the "Accuracy by Forecast Horizon" chart with only purple SARIMAX bars at t+2..t+7. Fixed by parameterizing `prepare_ml_data(df, horizon=1)` so the same feature matrix can be paired with the HRV of the sleep h−1 nights later (`hrv_alignment.outcome_series(df, h)`; h=1 = the same row) for any h, then iterating h ∈ [1..7] in `run_evaluation`'s walk-forward backtest (XGBoost retrains per fold per horizon; baselines compute per (i, h) — naive/7d_avg are constant across h while DOW shifts with the target weekday). Each h has its own residual std for prediction intervals. The h=1 row of each model is still stored under `eval_results[m_name]` for backward-compat with the headline "Model Comparison" table and CLI prints. Downstream analyses that conflate horizons (Diebold-Mariano paired test, error-mode-by-journal-flag, residual histograms / vs-predicted / DOW plots, rolling-30d-MAE chart) are explicitly filtered to `horizon_days == 1` — they're interpretable only for the headline tonight's-sleep model. Frontend `getHrvModelMetrics` bumped from `.limit(20)` → `.limit(100)` since one eval_date now writes ~36 rows (xgboost×7 + sarimax×7 + 3 baselines×7 + prophet×1). The chart will populate on the next `python hrv_analysis.py` run or the daily 12:00 UTC retrain. Hyperparameters: h>1 reuses h=1's tuned shape (max_depth=4, lr=0.05, n=200) without per-horizon Optuna so the multi-horizon sweep stays under a few minutes.
- **Live vs backtest accuracy rows (2026-11-11).** `pds.hrv_model_metrics` is keyed (eval_date, model, horizon_days): the retrain's walk-forward backtest uses the plain model names, and `hrv_predict.py` writes its live 30-day accuracy as `<model>_live_rolling` (h=1, real forecasts only, one per date, created after the 2026-11-11 01:00 ET alignment cutover, written once 5 nights are scored). Never write live metrics under a plain name: until 2026-11-11 the hourly job replaced the backtest h=1 row, so older eval_dates hold hybrid h=1 rows (page readers prefer `model_version 'backtest%'`).
- **One HRV input manifest (audit PIPE-09, 2026-11-16).** Every HRV input and how a correction to it is seen (row scan, the habit_journal trigger signal (habits-checkin.md, "Backdated habit completions trigger HRV retraining"), or a row-count + content fingerprint from `pds.hrv_source_fingerprint`, `sql/hrv_source_fingerprint.sql`, which sees edits and deletions without new triggers; dateless relations such as Garmin laps and supplement products are fingerprinted through their historical parent rows, and the supplement rollup through the matview the pipeline loads) lives in `hrv_feature_sources.py`; `hrv_analysis.py` records the fingerprints before it loads its data (`hrv_analysis_results` `lineage/source_fingerprints`) and `hrv_backfill_check.py` compares against them, and a check it cannot make is unknown, never "no backfill" (partial `hrv_analysis|backfill_check` heartbeat starting `GUARD hrv_backfill_detection:`, shown on the HRV Retrain card, and a precautionary retrain once the last one is 3 h old). `hrv_predict.py` also rescores forecasts of the last 35 days whose stored `actual_hrv` no longer matches the matrix (only `actual_hrv` / `residual` change; the issued forecast never does); when a model is left with fewer than 5 scored live forecasts its `<model>_live_rolling` rows are removed, so a number computed from actuals that are no longer true is never shown or used by the drift check. Uber Eats receipt coverage (`delivery_email_log`: unread receipts are days never zero-filled) is fingerprinted on its own, apart from `delivery_daily`. Tests: `tests/test_hrv_source_manifest.py`, `tests/test_hrv_live_metrics.py`.
- `pds.hrv_predictions_latest` view — DISTINCT ON (prediction_date, model, horizon_days) returning freshest row per forecast. **Live (non-backtest) predictions win when both exist for the same date; backtest rows fall through as fallback** — necessary because the daily prediction job only writes ONE row per day (the forecast for tonight's sleep), and the ~57 historical h=1 rows from before the `*_v1` naming convention still carry `model_version='backtest_initial'` despite being genuine day-ahead forecasts. An earlier "WHERE model_version NOT LIKE 'backtest%'" filter hid all of them and emptied the Prediction-vs-Actual chart; the current view tiebreaks via `CASE WHEN model_version LIKE 'backtest%' THEN 1 ELSE 0 END` in `ORDER BY` instead. **All UI/analytics reads should go through the view**; the raw table accumulates multiple runs per day and generic fetches hit row limits fast. DDL in `sql/hrv_predictions_latest.sql`.
- **HRV columns are not interchangeable across sources.** `whoop_recovery.hrv_rmssd_milli` is RMSSD in milliseconds, measured during the WHOOP-detected sleep cycle. `garmin_hrv.last_night_avg_ms` is Garmin's proprietary time-weighted average of 5-minute HRV samples during sleep — *not* RMSSD; the unit is ms but the algorithm is different. `eight_sleep_trends.avg_hrv` is undocumented by Eight Sleep. Treat each as its own variable; never average or substitute.

## HRV variable-coverage audit (2026-05-21)

- **HRV variable-coverage audit (2026-05-21)** — `docs/hrv_variable_coverage_audit_2026-05-21.md` enumerates every variable from every data source vs every test (Spearman, Welch journal/habit/supplement/nutrition, Granger, XGBoost/SHAP, SARIMAX/Prophet, AIPW/PSM causal). Fixes applied:

The fix derives `p_raw` from the AIPW Wald `|ate/se_if|` vs N(0,1), pools binary + continuous treatments into one family of ~150, applies `multipletests(method='fdr_bh')` at `FDR_Q_THRESHOLD=0.05` (shared with `hrv_analysis`), and sets `p_raw`, `p_fdr_adjusted`, `passes_fdr` per result row. `meta_payload` records the correction policy. ## Causal inference layer

- **Causal inference layer (Phase 2.5 of `hrv_analysis.py`).** Lives in `causal_inference.py` and runs after the descriptive stats. Treatments span every controllable variable across all data sources — see "Treatment coverage" subsection below. For each treatment the layer estimates the ATE on next-night HRV three ways:
  1. **Naive** — Welch's `mean(Y|T=1) − mean(Y|T=0)`. Same number the existing `journal_impact` / `supplement_impact` / `habit_impact` charts show; included as the unadjusted baseline.
  2. **Propensity Score Matching (PSM)** — 1:3 nearest-neighbor matching on logit propensity from a logistic model fit on the confounders, ATT estimated as the mean within-pair Y difference, CI by paired bootstrap (B=500). Common-support trimming at propensity ∈ [0.05, 0.95].
  3. **AIPW (doubly robust)** — logistic propensity + two Ridge outcome models (one per arm), combined via the AIPW influence function. **Cross-fitting uses blocked 5-fold (`_blocked_folds`: contiguous calendar blocks, training excludes `AIPW_FOLD_GAP=7` rows on each side of the test block, a fold needs `MIN_FOLD_ARM=10` days per arm) with overlap trimming** (days whose cross-fitted propensity is outside [0.05, 0.95] are dropped from the mean, not clipped). Never shuffled KFold (audit F-001, 2026-05-26: shuffled folds let the outcome model see a test day's HRV through the next day's `hrv_lag1`; the 7-row gap closes that). Never forward-only `TimeSeriesSplit` either (2026-11-11): with drifting treatment prevalence its tiny early folds were nearly one-armed, the saturated propensity clipped at 0.95 still weighted those days ×20, and the never-scored first sixth of rows was averaged in as zeros, which produced the ±50–155 ms AIPW rows (live "viewed a screen in bed" −130 ms vs naive +3 / PSM +6; same frame with blocked folds: +13). ATE = mean of per-row influence values. **Plausibility guard** (`plausibility_flags`): a row is `implausible` (with `implausible_reasons`) when |AIPW| > 1 SD of nightly HRV, when it is > 0.5 SD from both naive and PSM, when > 50% of days were trimmed, or when > 2 folds were skipped; implausible rows never pass FDR (`fdr_suppressed_by_plausibility`). Test: `tests/test_causal_aipw_synthetic.py` (known effects on a drifting, level-shifted synthetic frame; runs in `stats-pr-check.yml`). **Two CIs reported alongside each other**: (a) IF-based via `sd(ψ)/√n`, the familiar form consumers expect; (b) **block-bootstrap CI** (`_block_bootstrap_ci`, 7-day blocks × 1000 reps) which resamples contiguous time slices of ψ to preserve autocorrelation the IF SE assumes is i.i.d. The per-treatment `aipw_bb_width_ratio = width(bb_ci) / width(if_ci)` flags treatments where IF SE is too narrow; verification on 108 treatments (`audit/aipw_shift_findings.md`) found median ratio 1.13 with 6 treatments diverging >1.5× (`body_battery_drained`, `medium_stress_duration_min`, `journal_felt_recovered`, etc.) — for those, trust the BB CI. Unbiased if either the propensity or the outcome model is correct.

  **Confounder set** is pre-treatment lag-1 only (`hrv_lag1`, `hrv_7d_mean`, `whoop_day_strain_lag1`, `whoop_sleep_duration_milli_lag1`, `rolling_7d_training_load`, `sleep_debt_7d`, `day_of_week`, `is_weekend`). Supplement family additionally gets `journal_have_any_alcoholic_drinks_lag1` and `caffeine_total_mg_lag1` (unified caffeine log — the WHOOP caffeine checkbox is disregarded by policy, 2026-06-10) because supplement-conscious days tend to differ in adjacent lifestyle. **Same-night sleep/recovery/HRV-derived variables are DELIBERATELY EXCLUDED** — they are mediators on the very causal path being estimated; adjusting for them would block the effect (mediator-adjustment bias). The reported quantity is therefore the **total effect** (which includes the sleep-quality channel) — the actionable answer for "if I take magnesium tonight, what happens to my HRV tomorrow?" **Per-treatment exceptions live in one function, `adjustment_set()`** (2026-11-13; each result row stores the outcome as `confounders_used`): multi-day rolling treatments (`ROLLING_AGGREGATE_TREATMENTS`: 3-day / 7-day load, Garmin acute / chronic load and their ratio) drop `hrv_lag1`, `hrv_7d_mean`, `whoop_day_strain_lag1` (mediators inside the window), and a rolling treatment also drops an aggregate whose day window contains its own (`ROLLING_WINDOW_DAYS`: the 7-day total for the 3-day load; estimand in `ROLLING_TREATMENT_ESTIMAND`). `total_training_load` is one day's sum, so it is a daily treatment with the full set. Test: `tests/test_causal_adjustment_sets.py`.

  **Sensitivity** via the VanderWeele & Ding (2017) E-value — minimum strength on the risk-ratio scale that an unmeasured confounder would need (with both T and Y) to fully explain the estimate away. Continuous outcome → Cohen's d → RR via Chinn (2000): `RR ≈ exp(0.91·d)`, then `E = RR + √(RR·(RR−1))`. Higher = more robust to unmeasured confounding.

  **Cell-size gates:** treatments with fewer than 10 days in either arm are dropped entirely (recorded in `causal/dropped_low_n`); those with 10-19 in either arm are reported but flagged `low_n=true` (rendered with reduced opacity + ⚠ marker on the UI).

  **Storage:** five new rows in `pds.hrv_analysis_results` per run, all under `result_type='causal'`:
  - `binary_treatments` — list of binary-treatment results
  - `continuous_treatments` — list of median-split continuous-treatment results
  - `dag` — declared confounder sets + mediator exclusions + identifying assumptions (rendered as the DAG / Assumptions card on the UI for transparency)
  - `meta` — run metadata (estimator versions, bootstrap reps, fold counts, trim bounds)
  - `dropped_low_n` — treatments excluded for insufficient sample, with reason

  **Frontend:** new "Causal Inference" section on `/analytics/hrv` (between the descriptive impact charts and the Prediction-vs-Actual section) with (a) an explanation card describing purpose + method, (b) a forest plot of binary AIPW ATEs with 95% CI error bars, (c) a naive-vs-adjusted comparison table sorted by absolute attenuation, (d) a continuous-treatment forest plot, and (e) a DAG / Assumptions card rendering the stored DAG payload. Empty until `python hrv_analysis.py` runs. Implausible rows (`lib/causal-plausibility.ts`, which re-derives the SD and disagreement rules for rows stored before the guard existed) are left out of both forest plots and listed under them with the reason; the table shows them greyed (⊘) after the ranked rows. Node test: `frontend/scripts/test-causal-plausibility.mjs`.

  **Why this is meaningfully different from the existing correlation / Welch / Granger machinery:** every other test in the pipeline answers *what's associated with* HRV. The causal layer answers *what would change HRV if intervened on*, by adjusting for the lifestyle clustering that confounds the naive comparison (e.g. alcohol nights co-occur with restaurant nights and weekend nights — naive Welch's blames alcohol for the whole pile).

  **Treatment coverage (which variables get a causal estimate):**
  - **Binary treatments** auto-enumerated from the matrix by prefix:
    - `journal_*` (every WHOOP journal yes/no question — ~50 columns when fully populated)
    - `habit_*` (Notion-managed habit completions, dynamic)
    - `supplement_*_amount` (every compound from `pds.supplement_intake_by_compound`, binarized to taken/not-taken — ~50 compounds; most flagged `low_n=true` until tracking history accumulates)
  - **Binary treatments** explicitly listed in `EXPLICIT_BINARY_TREATMENTS` (so they survive renames): `had_evening_workout`, `is_run_day`, `is_rest_day`, `negative_split`.
  - **Continuous treatments** (median-split to put them on the same scale as the binaries), declared in `CONTINUOUS_TREATMENTS`. Covers every daytime/behavioral variable from every data source:
    - *Nutrition (MFP):* calories, protein/carbs/fat (g + % of cals), fiber, sugar, sodium, water, exercise_kcal, net_calories
    - *Daytime strain / activity (WHOOP + Garmin):* WHOOP day_strain, WHOOP kilojoule, steps (Garmin `total_steps` and WHOOP `whoop_steps`), total_kcal, active_kcal, moderate/vigorous intensity minutes, highly_active/active/sedentary seconds
    - *Training load:* rolling 3d/7d, acute, chronic, ATL/CTL ratio, total_training_load. **Rest days are load 0, unworn days NaN** (2026-11-14): `total_training_load` is 0 on a day the Garmin watch was worn (the worn rule in wearables-environment.md, "Garmin"; `garmin_worn_days` in `hrv_analysis.py`) with no activity, and stays NaN on a day it was not worn, so the load rows compare more vs less load with rest days included and "no sync" never reads as "rest". `rolling_3d/7d_training_load` sum it with `min_periods=1`: a window of worn rest days is 0, a window with no worn day is NaN (an unworn day inside an otherwise known window adds nothing). Acute / chronic load are Garmin's own values (`garmin_etl.training_load_from_status`, wearables-environment.md). Test: `tests/test_garmin_training_load.py`.
    - *Stress (Garmin):* avg / max stress level, high-stress duration, % high stress, stress ratio
    - *Body Battery (Garmin):* charged, drained
    - *Workout timing:* minutes from last workout to bedtime, strain÷hours-to-bed
    - *Workout aggregates (Garmin):* activity_count, duration_min, distance_km, calories, max aerobic/anaerobic TE, max/avg activity HR, total elevation gain
    - *Workout aggregates (WHOOP):* workout_count, total/avg strain, total kJ, peak/avg workout HR, total time in zones 4-5 / zones 0-1
    - *HR zones (Garmin daily):* zone_2 through zone_5 seconds
    - *Recovery state:* days_since_alcohol, days_since_sauna, days_since_hard_workout, days_since_rest_day, consecutive_run_days
  - **DELIBERATELY excluded as treatments** (they are mediators or near-tautological outcomes — see the module's docstring for the full DAG argument): every same-night sleep variable (WHOOP `whoop_sleep_*`, Garmin `garmin_sleep_*`, Eight Sleep `eight_sleep_*`), every HRV-derived variable (`whoop_recovery_score`, `whoop_rhr`, `garmin_rhr`, `whoop_skin_temp`, `hrv_z_28d`), sleep timing recorded from the sleep itself (`bedtime_hour`, `wake_hour`, `sleep_midpoint_hour`), and body-composition (`weight_kg`, `bmi`) which changes too slowly for a daily ATE.
  - **`pds.garmin_workouts` (planned workout templates) is intentionally NOT joined into the HRV pipeline** — it stores scheduled-workout plans (interval targets, distances), not executions. The execution-side data (`garmin_activities` + laps) drives all training-load features. Plans without execution would be noise; executions without plans are still observed.

## Habits in the analysis

- **Habits are analyzed as a first-class category in `hrv_analysis.py`** (alongside but separate from journal). The pipeline loads `source` from the unified `pds.journal` view and routes WHOOP entries through `pivot_journal` (`journal_*` columns) and habit completions through `pivot_habits` (`habit_*` columns, label preserved from Notion). After merging, unlogged days stay NaN (policy 2026-07-19; the per-habit first-completion-forward 0-fill was removed) — explicit Yes → 1.0, explicit No → 0.0, no row → NaN = "not logged = unknown". Four habit-specific `hrv_analysis_results` rows are written every run: `correlation/spearman_habit`, `habit_impact/all` (Welch's t-test mirroring `journal_impact`), `feature_importance/shap_habit`, and `model_comparison/error_modes_by_habit`. `habit_` is also in `CONTROLLABLE_FEATURE_PREFIXES` (actionable-only SHAP ranking) and in the SARIMAX/Prophet exog seed prefix list. The `/analytics/hrv` dashboard surfaces all four via dedicated Habit sub-sections in Prediction Drivers, HRV Correlates, and a sibling "Habit Impact" card next to Journal Impact. With sparse history (each habit needs ≥5 Yes-nights + ≥5 No-nights for the t-test, and ≥20 non-null days for Spearman) the chart populates incrementally as completions accumulate.

## Environment Sweet Spot

- **Environment Sweet Spot (`/analytics/hrv`, Environment section; fit + day inputs 2026-11-13).** Descriptive only (association, nothing adjusted for). `app/analytics/hrv/SweetSpotPanel.tsx` buckets nights by one input and shows the mean of one same-night outcome (WHOOP HRV / recovery / sleep efficiency / deep sleep) per bucket, ±1 SEM; all logic is pure in `lib/sweet-spot.ts` (test: `frontend/tests/sweet-spot.test.cjs`). Inputs: Pod room / bed temperature (Eight Sleep is wake-day keyed, so the temperature for row D's sleep is read from row D+1) and four day-D inputs read from the SAME row: `meal_last_meal_to_bedtime_min`, `nutrition_calories`, `caffeine_total_mg`, `caffeine_mg_at_bedtime`. Adding an input = one entry in `SWEET_SPOT_X` (its column joins the explicit select list `SWEET_SPOT_COLUMNS` automatically; a column that is not on the same row needs its pairing set). Thresholds: under 20 nights for the selected pair the chart is replaced by "Not enough nights yet"; the fitted curve (hand-rolled least-squares parabola on the nightly points, not the bars) is drawn from 30 nights; its peak is labelled only when the curve bends downward, the bend is at least 2 standard errors from zero, and the high point is strictly inside the observed range. `getEnvDoseResponseData()` (queries-hrv.ts) takes no arguments and returns compact short-key rows from the matview, so the ISR seed and the client revalidation cannot diverge and every toggle derives locally. **Pipeline version + adjusted view (2026-11-14):** `hrv_analysis.py` Phase 2.6 (`run_dose_response_continuous`, between the causal battery and the models, fail-open) computes every input x outcome pair on each retrain from the feature matrix (Eight Sleep already re-keyed by `al.realign_matrix`, outcome from `al.outcome_series`) and stores ONE row `pds.hrv_analysis_results` `dose_response_continuous / sweet_spot` (stored last and on its own; a failed block is stored as `status: "failed"`). Unadjusted numbers are the same arithmetic as `lib/sweet-spot.ts`; each pair also carries a confounder-ADJUSTED version: the causal layer's pre-treatment confounders for that input (`ci._confounders_for` + `ci.adjustment_set`, ffilled and day-of-week sin/cos exactly as `_prepare_treatment`), bars = least-squares bucket means at average confounders (regression with one intercept per bucket), curve = parabola fitted jointly with them; needs 50 nights with a complete confounder history. It is an adjusted association, not a causal estimate, and the panel says so. The page reads the row through the analysis batch (`loadSweetSpot` in queries-hrv.ts; `parseSweetSpotBaked` refuses another payload version, other thresholds, or an input built from another column / transform / bucket width) and reads the matview rows only when the row does not cover every pair (missing, failed, partial), computing those pairs in the browser as before; the "Adjusted" toggle is disabled with the reason when a pair has no adjusted version. Caffeine differs between the two sources: the feature matrix counts a logged-era day with no caffeine entry as 0 mg (zero-anchor), the matview leaves it empty (`pipelineCaveat`). Keep `DOSE_*` thresholds and `DOSE_RESPONSE_INPUTS` / `_OUTCOMES` equal to `SWEET_SPOT_*` / `SWEET_SPOT_X` / `SWEET_SPOT_Y`. Tests: `tests/test_dose_response_continuous.py` (synthetic), `frontend/tests/sweet-spot.test.cjs` (also checks the Python tables against the TypeScript), `frontend/scripts/test-hrv-analysis-batch.cjs` (18 panels).
