A complete export goes through `pds.replace_cronometer_servings_window`: servings and daily totals in one transaction under the shared lock, and a day with no food (any nutrient above 0 in the daily summary is food, so a water-only day is not empty) is offered for emptying only when the same export has food on a day before it AND after it (time between looks is not coverage: a day past the newest day with food, the window's first and last day and everything in a blank export are never emptied; the function refuses any other date), and is emptied only on a second look: one run's two files are one look (both can miss the same day), so the first complete export that shows a stored day empty records it in `pds.cronometer_empty_day_candidates` and a later one at least 6 h after still showing it empty empties it (food seen on the day starts the count over: any automated export that shows food on it, even when its rows for that day are not written (`p_food_dates`), and every call of the manual writer for each date it writes). Absent from both files = servings + daily row, listed with no food = servings, and its zero Total row replaces the stored daily row only then; each removed row is copied into `pds.cronometer_cleared_rows` first (the restore block at the end of the file is one statement under the same lock: it puts one copy back, the newest unless told otherwise, with the copied daily row in place of the zero Total row the emptying left, and refuses a day that has food again); at most `--max-empty-days` (default 3) stored days per run, counting days still waiting and days held only in the daily table (more = none, partial). In every writer a daily row with no food never replaces a stored daily row that has food except on a day emptied this way (`pds.cronometer_daily_rows_held`, under the lock; the reply's `daily_kept` counts the rows left out), so a first look, a refused run, a partial or manual export, or a blank Total row cannot wipe stored totals. A file with a row whose date cannot be read may be food on any day, so every day of the window then forgets its empty-day record. The automated export names which file is which (`run_import(roles=("servings", "daily"))`), so each file is checked as the file it is meant to be, never re-sorted by its header: a servings file whose header lost its Food Name column is refused as the servings file and its dated rows still count as food seen; files sorted by header (no roles) that are taken as neither make the export unusable and reset every day of the window. Days emptied or waiting leave a counts-only note on the `cronometer|servings` heartbeat. Manual imports never empty a day and send servings + daily totals in one call too (`pds.replace_cronometer_servings_and_daily`, same lock), so a manual daily row can no longer land on a day the automated run just emptied. `--dry-run` prints how many stored days a real run would empty (read only); `--no-empty-days` / `CRONOMETER_EMPTY_DAYS=off` imports like a manual export. ## Meal timing

- **`pds.meal_events` captures clock-time meal events for HRV timing analysis.** Deliberately separate from `pds.myfitnesspal_nutrition`: MFP carries macros at daily-totals grain with **no timestamps** (the CSV export drops per-meal times); `meal_events` carries clock-instant grain with **no macros**. The two are joined at view-time. Fact table: `event_id BIGSERIAL`, `event_date DATE NOT NULL` (behavioral-day, ET — same convention as `supplement_intake`; a 12:05 AM pre-bed meal is attributed to the previous day), `event_time TIMESTAMPTZ NOT NULL` (truthful clock instant), `kind TEXT DEFAULT 'last_meal'` (extensible: last_meal | first_meal | snack | other), `notes`, plus auto-touched `created_at` / `updated_at`. View `pds.meal_timing_daily` aggregates one row per ET date with `last_meal_time`, `last_meal_hour` (ET decimal hour 0-23.99, e.g. 19.75 = 7:45 PM), `first_meal_hour`, `eating_window_hours`, `meal_event_count`, `last_meal_kind`, plus the **bedtime-anchored `last_meal_to_bedtime_minutes`** — computed as `whoop_sleep.start_time − last_meal_time` against the WHOOP cycle that closes the behavioral day (the cycle whose `onyx_behavioral_date` is that day). The bedtime-anchored metric is what the HRV pipeline reads because it's monotonic in physiological lateness: a 1:30 AM meal + 1:35 AM bedtime resolves to 5 minutes, whereas the raw `last_meal_hour` would invert at midnight (0.083 < 19.75) and confuse any model using it directly. **The manual `/nutrition` meal-event quick-log UI (+ read-only timing display + edit modal) was REMOVED 2026-05-31** — Cronometer Gold per-entry timestamps now drive meal-timing via `pds.meal_timing_from_cronometer` (COALESCE'd ahead of `meal_timing_daily` in `daily_health_matrix_behavioral`). The `meal_events` table, the `/api/meals` route (GET/POST/PATCH/DELETE), and `pds.meal_timing_daily` are retained as the pre-Gold historical DB fallback and for any future programmatic logging; the post-midnight behavioral-day convention (logging 00:00–04:00 ET → attribute to yesterday) still applies to any row written. `/nutrition` itself was renamed from "Nutrition / Meal Timing" to just "Nutrition" (the standalone `/meals` page still 301-redirects there). The view is now joined into `daily_health_matrix` as `meal_last_hour`, `meal_first_hour`, `meal_eating_window_hours`, `meal_event_count`, and `meal_last_meal_to_bedtime_min`; `meal_` is in `CONTROLLABLE_FEATURE_PREFIXES` (SHAP-actionable) and `meal_last_meal_to_bedtime_min` + siblings are in `CONTINUOUS_TREATMENTS` in `causal_inference.py` (nutrition family — gets the lifestyle-clustering confounder set). Spearman + SHAP coverage activates automatically once ~18 days of logs clear the 5% non-null filter; AIPW causal estimates require ≥10 days in each median-split arm (and surface with `low_n=true` until 20). Schema in `meal_schema.sql`. **Photo-meal timing: `pds.meal_timing_from_photo_meals` (`sql/meal_timing_from_photo_meals.sql`) — view written, not applied, not in matrix** (2026-11-16): one row per behavioral day from `pds.photo_meals` real meals only (`capture_kind='photo'`, `deleted_at IS NULL`; drink captures and tombstones excluded), same column shape and WHOOP main-cycle bedtime anchor as `meal_timing_from_cronometer`, decimal hours in the local zone via `pds.tz_for_instant`. Additive only — deliberately NOT wired into `daily_health_matrix_behavioral`, because that needs the coordinated matview drop+recreate the file's header documents (the later wiring is `COALESCE(mtc.<x>, mtpm.<x>, mt.<x>)`). Structure test: `tests/test_meal_timing_photo_meals.py`.
- **`/nutrition` meal quick-log exposes both `last_meal` and `first_meal` kinds.** A two-pill row (Kind: last meal / first meal) above the time selector toggles `mealKind` in component state and is sent as `kind` in the `POST /api/meals` body. Defaults to `last_meal` to preserve the prior single-kind UX; the button label flips to "Log first meal" when first meal is selected. The behavioral-day attribution logic (post-midnight auto-yesterday) applies identically to both kinds — a 6 AM first meal that's the day's start lands on today, a 12:30 AM pre-bed last meal lands on yesterday, as before. `first_meal` events feed `meal_first_hour` and `meal_eating_window_hours` in the matrix, both of which were already wired through the HRV pipeline (Spearman / SHAP / causal) and just lacked an ergonomic logging surface.

## Caffeine

- **Unified caffeine layer (2026-06-09): `pds.caffeine_events` + `pds.caffeine_timing_daily` merge BOTH caffeine channels** — supplements (`pds.supplement_intake` × caffeine-bearing ingredients: FDA UNII `3G6A5W338E` or `ingredient_group`/`name ILIKE '%caffeine%'`, mg = quantity × doses, unit-normalized) and dietary (`pds.cronometer_servings` rows with `caffeine_mg > 0` — coffee/tea/chocolate, with Cronometer Gold per-entry timestamps). Both key on the behavioral day. `caffeine_events` is the per-event grain; `caffeine_timing_daily` aggregates one row per behavioral day: timing (`first/last_caffeine_hour` ET, `caffeine_window_hours`, bedtime-anchored `last_caffeine_to_bedtime_minutes` via the main WHOOP cycle closing the day — `whoop_main_cycle_per_behavioral_date`, dedup-safe, travel-robust) + quantity (`total_caffeine_mg` / `dietary_caffeine_mg` / `supplement_caffeine_mg`) + `caffeine_mg_at_bedtime` (5h half-life decay residual at sleep onset). **Timestamp trust rule:** an event's clock instant only feeds timing aggregates when its own behavioral attribution (`((event_time AT local tz) − 6h)::date` via `pds.tz_for_instant`) matches the claimed behavioral day — quarantines retro-logs (the `/supplements` date-override keeps `intake_time` = "now", so backdated doses carry next-day timestamps that previously produced negative bedtime gaps). Untrusted events still count toward mg totals and `caffeine_intake_count` (which counts ALL events, both channels). `caffeine_mg_at_bedtime` is NULL unless EVERY event that day has a trusted timestamp (dose-weighted — partial timing would silently under-count). Matrix: the five legacy `caffeine_*` columns in `pds.daily_health_matrix_behavioral` picked up unified semantics in place, and `caffeine_total_mg`/`caffeine_dietary_mg`/`caffeine_supplement_mg`/`caffeine_mg_at_bedtime` were appended (migration `daily_health_matrix_behavioral_caffeine_unified`, doc in `sql/caffeine_matrix_columns.sql`). **Pipeline contract: `caffeine_total_mg` is THE canonical caffeine quantity** — it replaced the dietary-only `nutrition_caffeine_mg` in `NUTRITION_COLS` and `CONTINUOUS_TREATMENTS` (`nutrition_caffeine_mg` stays in the view as archive but is no longer tested — two copies of one signal would double-dip the FDR family). **The WHOOP journal "Consumed caffeine?" checkbox is DISREGARDED by policy (Riley, 2026-06-10)** — it proved unreliable (two "No" nights carried 800-1000 mg of logged caffeine). `hrv_analysis.py` drops `journal_consumed_caffeine` right after the journal merge so it reaches no test family; the zero-anchor is log-based: in-era days with no caffeine event AND other logging activity (any supplement dose, or a Cronometer nutrition entry) anchor to 0 mg — the activity gate keeps lapsed-logging stretches from manufacturing fake zeros. `strain_x_caffeine` and the supplement-family causal confounder are repointed to the unified signal. Also derives `caffeine_total_mg_lag1`. `caffeine_mg_at_bedtime` (+ `caffeine_total_mg`) are `CONTINUOUS_TREATMENTS` family `nutrition`. Frontend: **`/caffeine` page** (KPI tiles, stacked dietary/supplement mg trend with FDA 400 mg reference, caffeine-window range chart, bedtime-gap trend with 6h reference, caffeine × next-night-HRV scatter + late-vs-early comparison) reads `caffeine_timing_daily` + matrix via `getCaffeineDaily`/`getCaffeineHrvPairs` in `lib/queries.ts`. ## Uber Eats delivery orders

- **Delivery orders — `pds.delivery_orders` from Uber Eats receipt emails (`delivery_email_etl.py`, 2026-11-09, `sql/delivery_orders_schema.sql`).** Uber has no API for a customer's own order history and the claude.ai Uber Eats connector only searches restaurants, so the ETL parses the receipt email (`noreply@uber.com`, subject "…order with Uber Eats") over IMAP, reusing the flights ETL's plumbing (imports its IMAP/HTML helpers; receipts arrive in rileybleeklm@). **The emails carry NO line items** (they sit behind the "full receipt" link) — this source gives meal TIMING and delivery COUNTS, not calories. **Two templates:** from Nov 2025 the receipt prints order time, pickup time + merchant address and delivery time ("Order completed … at …") → `time_source='receipt'`; before Nov 2025 it prints only the order DATE and the card-charge time. The charge posts 70 min after delivery in ~81% of orders (measured on 275 printed-time receipts) and the next morning in most of the rest, so `delivered_local = charge − 70 min` is kept ONLY when the implied order time lands on the weekday + daypart in the subject ("Friday evening order") → `payment_estimate`; otherwise the row keeps date + daypart only → `date_only` (behavioral date = printed date for afternoon/evening orders, NULL for "morning" ones, which could be a 1 AM awake-tail order). One row per order, natural key `(provider, order_key)` (merchant + order time, or merchant + first charge time on the old template); latest email wins; a tip-only receipt never overwrites the total; a FULL refund → `status='refunded'`; canceled receipts → `canceled`. An old-template receipt RE-SENT days later (card charged again → a different charge time, so a different key) is recognised as the same order by merchant + printed order date + daypart + total (`Store._twin`) and skipped; if the stored copy has no usable time and the new one does, the stored copy is deleted and replaced. **Estimated times (`time_source='payment_estimate'`, `raw_json.estimate_basis` says which):** (a) old template: card charge − 70 min, with a post-midnight order charged before dawn clamped to 00:00 of its printed date (so it keeps a time and lands on the previous behavioral day); (b) new template WITHOUT a courier timeline (the restaurant delivers itself, e.g. Umai): its "Order completed" stamp is a 90-minute auto-close, not a drop-off (12 of 19 such receipts sit at exactly 89–91 min vs 1 of 239 with a timeline), so order + 30 min is stored instead. `merchant_kind` (`restaurant` | `alcohol` | `store`) is a name-keyword guess (`ALCOHOL_WORDS`/`STORE_WORDS` in the ETL — extend when a new non-restaurant merchant appears; a correction for ONE merchant goes in `MERCHANT_KIND_OVERRIDES` / `MERCHANT_TZ_OVERRIDES` in the ETL, mirrored in `frontend/src/lib/delivery.ts` — NOT in an UPDATE on the table, which the next email or `--reprocess` overwrites): only `restaurant` rows count as meals. The trigger resolves the printed local wall-clock times to instants (WHOOP cycle offset → `user_tz_log` → ET) and the ADR-0001 quad from the delivery instant. **The delivery (home) address is never stored.** **`pds.delivery_daily`** = one row per behavioral day with a delivered order: counts by kind, first/last meal delivery time, `late_meal_delivery` (≥22:00 or <06:00 local), `last_meal_delivery_to_sleep_minutes` (WHOOP main-sleep onset, same join as caffeine/screen time), `untimed_meal_order_count`, `has_estimated_time`. `pds.delivery_email_log` is the parse ledger (`unmatched`/`error` = Uber changed the template). Only `parsed` rows count as done: an `error` or `unmatched` email is re-read on every run (heartbeat stays `partial` until it parses), and an `error` older than the 30-day window widens the search until it is read. `/status` **Delivery** card (badge UBER EATS) = `delivery|email` heartbeat age, same thresholds as Flights. **Time zone:** new-template receipts print the MERCHANT's clock, so the ETL derives `merchant_tz` (IANA) from the merchant address (US state / Canadian province / country maps in `delivery_email_etl.py`; split states get their dominant zone) and the trigger resolves the times in that zone, passing it to `derive_onyx_dates` as a source-field offset; old-template rows (no address) still use the WHOOP-cycle → `user_tz_log` → ET ladder. New-template receipts WITHOUT an address take `MERCHANT_TZ_OVERRIDES` or the zone of the same merchant's other receipts (when they all agree). (Added after an Atlanta order placed the evening Riley landed from Madrid was stored 6 h early — the cycle offset lags on travel-return days.) **HRV pipeline (2026-11-09, realigned 2026-11-10):** `hrv_analysis.py:merge_delivery_features()` merges `pds.delivery_daily` in pandas (not via the matrix view), fail-open: `delivery_meal_count`, `delivery_any_meal`, `delivery_late_meal`, `delivery_last_meal_to_sleep_min`. **Row placement: a delivery on behavioral day D sits on matrix row D** — row D holds the HRV of the sleep that closes day D, the sleep the meal preceded (`hrv_alignment.py`; until 2026-11-10 it was moved to row D−1 to offset the old next-row outcome). **`delivery_*` columns are excluded from the forecasting models** (`prepare_ml_data` exclude set + the SARIMAX/Prophet fallback ranking): when the evening forecast runs, today's receipts may not be parsed yet and today is never inside the zero-fill coverage window, so the newest row reads NaN where training rows read 0. They feed the Spearman and causal analyses only. Zero-fill: a no-order day is 0 only inside coverage = first delivery day → the later of the last delivery day and `delivery_covered_through` (newest `delivery|email` SUCCESS heartbeat, ET − 18 h − 1 day: a day counts as covered only 12 h after it ends, because receipts for late orders can arrive the next morning); days that may hold an unread receipt (`delivery_email_log.status <> 'parsed'`: its own behavioral day and the day before) are never zero-filled; a day with an untimed meal has a NaN late flag unless another meal that day is known late. Causal: `delivery_late_meal` + `delivery_any_meal` are `EXPLICIT_BINARY_TREATMENTS` (family nutrition — binary, not a median split, because the count is 0/1/2) and `delivery_last_meal_to_sleep_min` is a `CONTINUOUS_TREATMENTS` median split.
