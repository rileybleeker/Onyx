## Behavioral-day convention

- **Supplement intake — behavioral-day convention (NOT clock date).** A `pds.supplement_intake` row's `intake_date` should reflect the **day the intake belongs to behaviorally**, not the wall-clock date of the moment it was taken. A pre-bed supplement consumed at 12:05 AM ET — *before* the user has slept — belongs to the day that just ended, not the new clock date. Rationale (three converging reasons):
  1. **WHOOP cycle alignment.** WHOOP defines a "day" by bedtime-to-bedtime spans (see the `+12h` cycle rule, database.md). The awake-tail period after midnight but before sleep is part of the *previous* cycle, not the new one. Treating supplements the same way keeps the journal × cycle × intake triple consistent.
  2. **HRV pipeline correctness.** The pipeline scores day-N behaviours against row N's own HRV — the sleep that closes behavioral day N (`hrv_alignment.py`). A pre-bed supplement affects the *immediately following* sleep, which is exactly row N's sleep, so the intake must be on row N. A naive clock-date attribution at 12:05 AM would put it on row N+1 and score it against the night after — silently mis-training the model.
  3. **Stack consistency.** An "evening stack" (mag, melatonin, etc.) that sometimes lands at 11:55 PM and sometimes at 12:05 AM should not split across two rows of `daily_health_matrix` based on a 10-minute clock crossing that has no biological meaning.

  **MyFitnessPal — log on behavioral day via manual backdate (decision 2026-05-25).** Earlier versions of AGENTS.md said MFP follows "literal clock date" for energy-balance reasons. That was correct under one interpretation (clock-anchored calorie totals) but Riley's PRIMARY use of MFP is HRV/recovery analysis (mfp_* macro features feed `hrv_analysis.py`). For that use case, clock-date attribution creates the same awake-tail misalignment the ADR-0001 rewrite eliminated for every other source: a 1 AM heavy-fat meal would land on the wrong row vs. the HRV measuring its effect. Convention going forward:
  - **When logging a meal in MFP between 00:00 and ~5 AM ET that is genuinely pre-bed (your awake-tail), backdate it to yesterday in the MFP date picker.** The trip is "did I eat this meal before today's behavioral day ended?" — answer yes → log under yesterday.
  - The MFP daily-totals UI will look uneven on backdate days (yesterday shows ~2700 cal, today shows ~1800). That's the cost; the analytical correctness is the benefit.
  - The Onyx side requires no code change: the trigger sets `onyx_behavioral_date = calendar_date`, so behaviorally-logged MFP rows are correctly behavioral-attributed.
  - For pure energy-balance questions ("did I hit 180g protein on May 22?"), MFP's daily totals will reflect Riley's BEHAVIORAL day (May 22 = 10 AM May 22 → 1 AM May 23 clock-time), which is the right semantic for that question too (your fasting window starts at sleep, not at midnight).
  - For the temporal "when did I eat" question, `pds.meal_events` remains the source of truth (it has timestamps; MFP's standard CSV export does not).

  **Operational implications:**
  - `pds.supplement_intake.intake_date` is the canonical join key (behavioral day, ET).
  - `pds.supplement_intake.intake_time TIMESTAMPTZ` stores the truthful clock instant — kept independent of `intake_date` so a 12:05 AM May 21 click attributed to May 20 keeps the accurate timestamp without losing the date semantics.
  - Supplement logging (Log's Supplements section, chat, agent cards; `/supplements` itself no longer logs since 2026-11-15, see "One place to enter data"): **the behavioral attribution is automatic — log in real time.** Every logging path (`POST /api/supplements/log-intake`, `log-product`, and `logStackIntake`) defaults `intake_date` to `pds.behavioral_today_now()` — TZ-aware (travel, via `user_tz_log`) AND awake-tail-aware (−6h rule), so a 12:30 AM pre-bed dose lands on yesterday with zero manual action — while `intake_time` records the truthful clock instant. **Do NOT manually "correct" the pre-filled date to the clock date after midnight** — that breaks behavioral attribution and trips the caffeine layer's timestamp-trust quarantine. The manual date override exists for RETRO-logging only (remembered a dose from days ago); note retro-logged doses keep `intake_time` = "now", so they count toward mg totals but are excluded from timing aggregates by the trust rule. EditIntakeModal supports retroactive date adjustment for past intakes.
  - When ingesting historic supplement logs from any other source (Apple Health, manual CSV), the importer must apply the same rule.

## Products, intake and the compound rollup

- **Supplements: isolated dim/fact tables, joined in Python (NOT in `daily_health_matrix`).** `pds.supplement_products` (dim, JSONB ingredients) + `pds.supplement_intake` (fact, one row per intake event). The DB-level `pds.daily_supplement_matrix` view exists (one row per behavioral-day, with a `compounds_jsonb` map + `distinct_compounds` + `total_doses`) but is **not** LEFT JOINed into `daily_health_matrix_behavioral` — it's loaded directly by `hrv_analysis.py` (read of `supplement_intake_by_compound`) and merged in pandas. Same isolation principle as Spotify + Notion-journal: open-ended compound space + sparse coverage make a per-day SQL JOIN noisy compared to a Python merge that can filter on coverage. If you need supplements alongside other matrix variables, do `LEFT JOIN pds.daily_supplement_matrix dsm ON dsm.calendar_date = dhm.calendar_date` at query time. Compound names come from `pds.daily_supplement_matrix.compounds_jsonb` (a `{compound_name: {amount, unit, category}}` map — query specific compounds with `(compounds_jsonb->'Vitamin D'->>'amount')::numeric`). JSONB rather than hardcoded columns because the compound space is open-ended (50+ across a stack) and a user's supplement list changes — locking schema would be wrong. The underlying `pds.supplement_intake_by_compound` view explodes ingredient JSONB × dose and groups by FDA **UNII** code (when present) so cross-product summation just works: Vitamin C from a multivitamin and a standalone Vitamin C tablet roll up into one row. Product data comes from the **NIH DSLD** (Dietary Supplement Label Database) — public API at `https://api.ods.od.nih.gov/dsld/v9/`, no auth, covers vitamins/minerals/botanicals/nootropics with full ingredient lists. Seed paths: `python supplement_lookup.py search "<query>"` → `seed <dsld_id>`, or `seed-from-upc <upc>`, or the `/supplements` page's search/barcode-scan UI. The Next.js `/api/supplements/*` routes and the Python CLI share parsing logic (`frontend/src/lib/dsld.ts` mirrors `supplement_lookup.py:normalize_label`) so both produce identical rows. **Unit identity (HIST-UNIT-01):** the rollup keeps one row per compound and `unit_class` (`mass` = mg after conversion, IU only for vitamins A / D / E; any other unit literal, never converted); the `/supplements` table keys rows on that identity (`lib/supplement-units.ts`, ingredients with no readable amount listed apart), and `hrv_analysis.supplement_dose_response_rows` uses one class per compound, leaves out days with an intake in another class or without a readable amount (read from the intakes + products by `load_supplement_unquantified`, because the view filters those ingredients out), stores what it left out as `supplement_impact / dose_response_coverage` (listed under the `/analytics/hrv` dose-response chart), and stores an empty list when no estimate is left (an empty rollup included) so an older one never stays on the page, but publishes nothing and ends the run partial when that read fails (the last complete result stays). Tests: `tests/test_supplement_dose_units.py`, `frontend/tests/supplement-units.test.cjs`.
- **Melatonin: journal↔supplement bridge (`sql/melatonin_unified.sql`, 2026-06-14).** The WHOOP-derived journal question "Took a melatonin supplement?" (HAB-39) was duplicative with the `/supplements` tracker, so it's **deactivated in Notion** (Active=false — name stays frozen/un-renameable, all 288 rows preserved) and **dropped from the journal family** in `build_feature_matrix` (`journal_took_a_melatonin_supplement`, mirroring the `consumed_caffeine` / `ate_food_close_to_bedtime` / `used_a_sauna` drops). To avoid losing the ~288 frozen observations, the **read-only** view `pds.melatonin_unified` unifies them with the supplement-tracker mg dose on the shared behavioral-day axis (one row/day): `melatonin_present` (binary journal Yes/No, **overridden to taken on any day a real supplement dose exists** — pill log wins; also fills the 3-day journal gap 2026-06-08..10) is loaded as `supplement_melatonin_amount` so it joins the **supplement** family/confounders/labels while staying ~49% non-null on the HRV-valid basis (clears the 5% gate → no cutover gap in SHAP/causal). `melatonin_dose_mg` (NaN on non-dose days incl. the whole pre-tracking era — **never nominal-filled**, so no fabricated zeros) is a continuous supplement treatment (`causal_inference.py`) = dose-response *among* melatonin nights. The raw `pivot_supplements` melatonin column is dropped first so there's exactly ONE melatonin column (asserted: single column, domain ⊆ {0,1}). Read-only view → frozen era untouched; **supplement is source-of-truth going forward** (log via `/supplements`; the inactive habit no longer feeds journal). Takes effect on the next retrain — melatonin relocates from the Journal sub-sections to Supplement + Causal on `/analytics/hrv`. The dead `JOURNAL_LABELS["took_melatonin"]` key was removed (the real slug was always `took_a_melatonin_supplement`).

## Stacks and reminders

- **Supplement stacks — recurring consumption as a bill-of-materials (`supplement_stack_schema.sql`).** `pds.supplement_stack` (header: name, description, `is_active` soft-delete) + `pds.supplement_stack_item` (lines: `product_id` + `doses`, `UNIQUE(stack_id, product_id)`, `ON DELETE CASCADE`). A stack is a **template only** — logging one writes ordinary `pds.supplement_intake` rows (one per item, carrying that item's `doses`), so every rollup (`supplement_intake_by_compound`, `daily_supplement_matrix`) and the HRV/causal pipeline pick the rows up with **zero changes**. The one fact-table change is a nullable provenance column `supplement_intake.stack_id` (`ON DELETE SET NULL`) recording which stack produced an intake — enables grouped "undo all" and "logged from stack" labeling without ever breaking history when a stack is deleted. Shared batch-log logic lives in `frontend/src/lib/supplement-stacks.ts:logStackIntake` (used by both the API route and the chat tool), and it defaults `intake_date` to `pds.behavioral_today_now()` exactly like single-intake logging (awake-tail + TZ aware). Surfaces: (1) the **Stacks** card on `/supplements` (create/edit via `StackEditorModal.tsx` (autosaves: a new stack is created once it has a name and a product; the create sends a `client_key` UUID so a retried create returns the same stack, `sql/supplement_stack_client_key.sql`; every save is ONE call to `pds.save_supplement_stack` (`sql/supplement_stack_atomic_save.sql`, 2026-11-16): header + the complete item list in one transaction, checked against the `version` the editor loaded (409 `stale` → "Load the latest version"; a body with no version, i.e. an out-of-date page, is 409 `reload`), a malformed `items` is a 400 that changes nothing, a save with no clear answer (dropped connection, unknown error code, a reply that is not a saved row) is `unconfirmed`: shown as "Not confirmed" with Retry and resent with the same save id, which the function answers as a replay, never as "Nothing was changed" (after one, changing the form back to what it loaded is still sent, as the Autosaver's `unknownOutcome` option makes no value count as saved until a save answers; a failed re-read of the list after closing keeps Edit disabled, with Retry), and there is no fallback to the old multi-request save (503 until the SQL is applied, so apply it and run the read-only `sql/checks/verify_supplement_stack_atomic_save.sql` BEFORE merging; the behaviour checks `*_branch.sql` never run on production); logic in `lib/supplement-stack-save.ts` + `lib/supplement-stack-chain.ts`, test `frontend/tests/supplement-stack-save.test.cjs`); since 2026-11-15 a stack is logged on Log's Supplements section, Log it / Skip / Undo, not here); (2) the **`log_supplement_stack`** chat tool ("log my morning stack" → resolves the stack by case-insensitive name, returns the available-stacks list on a miss). API: `/api/supplements/stacks` (GET/POST/PATCH/DELETE — PATCH replaces all items on save; DELETE soft-deletes) + `/api/supplements/stacks/log` (POST → batch intake). **No `/status` card for stacks themselves** — they write to the existing `supplement_intake` table, so they aren't a new ingestion source (the supplements freshness signal is unchanged).
- **Supplement stack reminders (2026-11-11, `sql/supplement_stack_reminders.sql`, `lib/supplement-reminders.ts`).** A stack with `pds.supplement_stack.remind_time` (local `HH:MM`, NULL = off; set in the stack editor's "Reminder time" field; seeded 08:30 Morning Stack / 22:30 Night Stack) is offered as a `supplement` card with **Log it** / **Skip** buttons in `/agents`. The sms-reminders Worker does the posting and holds no Supabase credentials: it polls `POST /api/supplements/reminders/claim` (`{now?}`) and relays taps to `POST /api/supplements/reminders/respond` (`{stack_id, behavioral_date, action: 'log'|'skip'}`); both are exact-path CI-token routes in `isCiRoute()` — never widen to `/api/supplements/*`. **Claim** = an active stack whose local time (`pds.tz_for_instant(now)`, so travel works) is within 4 h after `remind_time`, with no `supplement_intake` for that stack on `pds.behavioral_date_for(now)` and no ledger row yet; the claim is an atomic `INSERT … ON CONFLICT DO NOTHING RETURNING` into `pds.supplement_stack_reminder` (PK `(stack_id, behavioral_date)`, status `prompted`/`logged`/`skipped`, service-role only), so concurrent polls can never prompt twice, and everything that can fail runs *before* that insert. The response also lists `settled` prompts that got logged another way (`/supplements`, chat) so the Worker can tick the card. A reminder time before 06:00 local belongs to the previous behavioral day (the −6 h awake-tail rule). **Respond** is idempotent with the ledger row as the lock (status-guarded UPDATE, only the winner writes intake via `logStackIntake`; a failed write restores the row): `log` stamps `intake_time` only when the tapped day is the current behavioral day, otherwise `NULL`; a repeat or an already-logged stack answers `already_logged`; only a (stack, day) the claim created can be answered (404 otherwise). `/status` **Supplement Reminders** card (badge AGENTS) = `supplement_reminders|prompt` heartbeat age (>3 h degraded, >8 h or failed red; a day with nothing due is healthy); the claim route writes it on every call that claims something and otherwise at most every 50 minutes. Tests: `frontend/tests/supplement-reminders.test.cjs`, `frontend/tests/agent-card-actions.test.cjs`.

## Supplements on /log

- **Supplements on `/log` (2026-11-15, `app/log/sections/Supplements.tsx`).** One row per active stack (reminder time, logged or not on behavioral today): **Log it** = `POST /api/supplements/stacks/log` with the stack id only (the server stamps `behavioral_today_now()` + now, so a screen left open overnight cannot write the old day), **Skip** only while that day's reminder card is still `prompted` (`POST /api/supplements/reminders/respond` with the owner session; the middleware admits a session there too), **Undo** deletes the stack's rows for the day. Log it does not answer the reminder row, so the next claim's `settled` list ticks the `/agents` card. **Log a product**: tap one of the `/supplements` products (shown without typing, most used first by single doses among the newest 200 intakes of the last 30 days from `GET /api/supplements/history` (one of the HTML's early reads; the options never wait for it), the order fixed on first display while the section is mounted, the search box filters them, a tap only selects; `lib/log-supplement-options.ts`), amount + unit, clock times, day → **`POST /api/supplements/log-product`** (owner session only, NOT in `isCiRoute()`; same-origin JSON, 2 KB cap), which calls the chat tool's `logSupplementIntake` (`lib/supplement-intake.ts`; now also takes an exact `product_id`, notes "Logged from /log"), so doses, times, the awake tail, the no-time rule and the duplicate skip are the chat tool's. **Logged today**: single products with Undo (`DELETE /api/supplements/log-intake`). Say it drafts (product / stack) are listed as suggestions and written only on the section's Save; a product suggestion can be moved into the form with Edit. `GET /api/supplements/today` also returns `stack_id` per intake and `reminders` (`[{stack_id, status}]` for that day, `null` when that read fails).

## Adding products: barcode and photo

- **Barcode scanning is built-in.** `BarcodeScannerModal` (`@zxing/browser`) opens the rear camera, detects UPC-A/UPC-E/EAN-13, calls back with the digit string. The `/supplements` Add Product flow uses this: scan a bottle → `/api/supplements/search?q=<upc>` → if exactly one hit, single-click seed; else show candidates. Camera resources are torn down on close/detect/unmount to avoid stale streams. Works in any HTTPS browser context — including the PWA standalone shell.
- **Custom-product fallback via photo + Claude vision.** When a product isn't in DSLD (private-label, niche brand, regional SKU), the Add Product modal exposes a "Not in DSLD? Add custom →" link. Flow: snap a photo of the Supplement Facts panel → client-side resize to 1600px JPEG @ 0.85 → `POST /api/supplements/extract-from-photo` (base64) → Claude vision (`claude-sonnet-5-5`, API default effort; from `lib/model-routing.ts`, pilot in `docs/model-routing-pilot.md`) reads the label → returns the same `NormalizedProduct` shape DSLD produces. The route prepends a **reference table of (ingredient_group, UNII, category) tuples derived from existing `pds.supplement_products`** to the prompt, so Claude maps extracted ingredients to the user's already-canonical compound vocabulary. A server-side post-pass also backfills `unii_code` + `category` from the reference table for any row Claude returned with a matching `ingredient_group` but null UNII. The extracted product lands in an editable review form (`CustomSupplementFlow.tsx`) where every field — including per-ingredient quantity, unit, UNII, category — can be hand-corrected before save. `POST /api/supplements/custom-product` writes the row with `product_id = "custom_<hex>"` and `dsld_id = null`; `raw_json` carries the Claude usage stats + reference-table size for replay. Cross-product compound rollup in `supplement_intake_by_compound` works transparently because matched UNII codes are the join key. **The photo is never persisted** — it's sent to Anthropic as base64 in the single vision call and discarded after the response. Files: `frontend/src/app/api/supplements/extract-from-photo/route.ts`, `frontend/src/app/api/supplements/custom-product/route.ts`, `frontend/src/components/CustomSupplementFlow.tsx`.
