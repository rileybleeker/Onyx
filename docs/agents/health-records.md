## Health & appointments (2026-11-13)

`/health` is a care planner (due-soon list, month / agenda calendar with projected repeats), not a medical record. Items are stored in **`pds.care_items`** (`sql/care_items_schema.sql`): label, kind, calendar date + optional wall-clock time + the IANA zone that time is in (stored as written, never converted, so 9:00 stays 9:00 across a DST change), "repeat N months after completion", note, booked / archived / last-completed, `removed_at` (soft removal; the app never physically removes a row) and `import_key`. **Service-role only** (RLS on, no policies, nothing granted to anon / authenticated): the page is `force-dynamic` (no ISR, `noindex`) and reads through `lib/care-items-server.ts` (`server-only`); the browser writes through **`/api/care/items`** (GET, POST), **`/api/care/items/[id]`** (PATCH, DELETE = soft removal, PATCH `{removed:false}` = Undo) and **`/api/care/items/import`** (the one-time, idempotent copy of the old browser-only planner, keyed on `import_key`). The continuous scroll's `/health` section (`app/health/FeedSection.tsx`) renders the same `HealthClient` from **`GET /api/care/page-data`** (exactly what `page.tsx` passes: `{initial, calendar}`; same-origin, no-store, kept in memory only by the client cache). Those routes are owner-session only (never add `/api/care` to `isCiRoute()`), same-origin, JSON, size-capped, strict about unknown fields; errors and logs carry a database code only, never item text, and nothing is written to `sync_log`. The add / edit form autosaves (`lib/autosave.ts`, 2026-11-15): a new item is created once it has a label and a valid date and Riley pauses, later edits update it, Done starts a new item, Undo takes the whole edit back. A create retried after a lost answer gets the stored row and sends newer edits as an update. Switching to another item never drops an unsaved or incomplete entry (the form says so); Clear empties a new entry. Writes are optimistic per item and revert only that item on failure (`applyOp` / `revertOp` / `inverseOp` in `lib/care-items.ts`); a failed save is classified by `isTransientSaveFailure` (offline / timeout / 5xx / 429 retry on their own through the autosave scheduler's backoff and keep the optimistic change, a real 4xx refusal reverts and stops at Retry); load failure, empty list and data are three different states. Date, repeat and time-zone logic is pure in `lib/care-planner.ts`. Sample data is display-only and is refused by the API. Not an ingestion source, so no `/status` card; Today is not wired. Docs: `docs/health-appointments.md`. Tests (synthetic only): `cd frontend && node scripts/test-care-planner.mjs && node --test tests/care-items.test.cjs`.

**Google Calendar sync (built 2026-11-13, NOT connected until Riley sets it up; steps in `docs/health-google-calendar.md`).** One way, Onyx to Google, with exactly ONE scope, `calendar.app.created` (Onyx can only touch calendars it created: never Riley's own calendars, never Gmail; do not add a scope). Onyx creates one calendar ("Onyx care") and keeps one event per active care item (label, date / time / zone, booked state; notes are never sent; no recurring events). Pure logic in `lib/care-google.ts` (`eventForItem`, `runSync` against a `CalendarApi` interface); server part in `lib/care-google-server.ts`; routes `/api/care/google/{status,start,callback,sync,disconnect}` are owner-session only. **Nothing calls Google unless `GOOGLE_CALENDAR_CLIENT_ID` + `GOOGLE_CALENDAR_CLIENT_SECRET` exist in Vercel AND a refresh token is stored** (`pds.ci_tokens`, `service='google_calendar'`); without the env vars there is no database call either. Sign-in is authorization code + PKCE with a `state` bound to a 10-minute httpOnly cookie scoped to the callback path; a grant with any other scope is revoked and not stored. Every event carries the private extended property `onyxCareItem=<item id>`, and an event is read and that tag checked before any rewrite or removal, so Onyx never edits an event it did not create. State lives in `pds.care_calendar_sync` (one row: calendar id, connected-at, last result as counts + a short code) and `pds.care_calendar_links` (item to event id, generation, digest; rows are kept and marked `gone`), both service-role only (`sql/care_calendar_sync_schema.sql`). A sync runs via `after()` on every care-item write, from Sync now, and from the **scheduled catch-up** `POST /api/jobs/care-calendar-catch-up` (2026-11-14: every 6 h; the route checks `x-onyx-ci-token` itself, so a browser session alone cannot run it, then calls the same `syncCareCalendar()`; it answers counts + a short code, 200 `{ran:false}` while not set up / not connected, 502 on a failed run). The schedule reaches it only once Riley adds its ONE exact path to middleware's `isCiRoute()` and the workflow `care-calendar-catch-up.yml` (both protected paths; exact text on the roadmap row); until then nothing calls it. Results are not written to `sync_log`: the `/status` card **Care Calendar** (`care_calendar`; logic in `lib/care-calendar-status.ts`, pure) reads only the `pds.care_calendar_sync` row (never `ci_tokens`, never an item, and nothing at all until the Google variables exist): unknown while not set up or not connected, red on a failed sync (with what to do), degraded after 14 h and red after 30 h without any sync. Tests: `cd frontend && node --test tests/care-google.test.cjs tests/status-heartbeats.test.cjs` (fake Google + in-memory database).

## Medical records (2026-11-14)

`/health/records` (nav: Medical records) stores **lab results** (test, number or text value, unit, reference range, collection date, lab, optional source document; grouped by test + unit with the latest value, High / Low / In range against the typed range only (`<` / `>` exclude the bound, `<=` `≤` `>=` `≥` and a span include it; stored as `ref_low_strict` / `ref_high_strict`), change since last, and a trend chart from two numeric results) and **documents** (PDF / JPEG / PNG / WebP / HEIC up to 25 MB with title, kind, date of service, provider, note). Tables `pds.medical_documents` + `pds.lab_results` and the storage bucket `medical-records` (`sql/medical_records_schema.sql`, applied) are **service-role only**: RLS on, no policies, no anon / authenticated grants, no `storage.objects` policy, private bucket with its own size and type limits. The page is `force-dynamic` + `noindex` and reads through `lib/medical-records-server.ts` (`server-only`); the browser uses `/api/medical/documents` (GET, POST = details + one-time signed upload token), `/api/medical/documents/[id]` (PATCH, DELETE = soft), `/api/medical/documents/[id]/complete` (server checks the file's size and type, then marks it `ready`; only ready documents are listed or served), `/api/medical/documents/[id]/file` (303 to a 60-second signed link, `?download=1` to save), `/api/medical/labs` (GET, POST a batch of up to 60, idempotent on browser-picked ids) and `/api/medical/labs/[id]` (PATCH, DELETE = soft). The continuous scroll's `/health/records` section (`app/health/records/FeedSection.tsx`) renders the same `RecordsClient` from **`GET /api/medical/page-data`** (`{documents, labs}` exactly as `page.tsx` passes them; same-origin, no-store, a memory-only key in the client cache). Files go straight from the browser to the bucket because Vercel caps request bodies at ~4.5 MB. **Never add `/api/medical` to `isCiRoute()`, never let a chat tool or model read these tables or files, never log record text** (errors carry a database code only; nothing goes to `sync_log`). Entry is by hand: reading a document with Claude would send it to Anthropic and needs Riley's decision first. Removal is soft everywhere and the file stays for Undo. Editing a lab result or a document's details autosaves (PATCH after a pause or on blur; Done closes). Adding lab results stays a batch with Save results. Not an ingestion source: no `/status` card. Smoke: in `PAGES` with `legitimateEmpty`. Docs: `docs/medical-records.md`. **Backups: Supabase's database backups do not hold the bucket's files**; RPO / RTO, the encrypted off-site plan (option A chosen: a PC job to OneDrive, not built yet) and the synthetic-file drill are in `docs/medical-records-recovery.md`, and `tools/medical_recovery/recovery_check.py` is the read-only, counts-only check (it never downloads a file from production). Tests (synthetic only): `cd frontend && node --test tests/medical-records.test.cjs`, `python tests/test_medical_recovery_check.py`.
- **Off-site backup (SEC-06, built 2026-11-16; supersedes "not built yet" above):** `tools/medical_recovery/offsite_backup.py` (weekly task "Onyx Medical Backup", `register-task.ps1`) streams both medical tables, every bucket file and a fixed list of hand-entered `pds` tables into `age` (public recipient `~/.onyx_backup_age_recipient` only; private key `~/.onyx_backup_age_key`, read only by `drill`) and writes ONLY the ciphertext to `~/OneDrive/Backups/onyx` (8 newest + first of 3 latest months + the newest backup whose `.ok` completeness marker verifies). Tables are paged by primary key with a keyset cursor, never an OFFSET, and their keys re-read after the last page; a run whose marker cannot be committed fails and prunes nothing; off-site success is verified from the new ciphertext's own OneDrive cloud-files state (the cfapi placeholder attribute bits read via `GetFileAttributesW`; a plain local file is `pending_upload`, a partial run that prunes nothing — retention runs only once the newest backup is confirmed in the cloud), polled for up to `--sync-wait` seconds; `drill` decrypts into `%LOCALAPPDATA%\Onyx\backup-drill`, verifies hashes and counts, and removes the copy. Its one count-free heartbeat `backup|medical_records` is the single exception to "nothing goes to `sync_log`" (decision 5) and feeds the `/status` card **Medical Backup** (>8 days degraded, >15 days or failed red). Details: `docs/medical-records-recovery.md` section 9. Tests: `python tests/test_medical_offsite_backup.py`, `node --test tests/medical-backup-status.test.cjs`.
