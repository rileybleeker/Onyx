## Phone screen time

- **Phone screen time v1 — the iOS Shortcuts open/close path is RETIRED (built 2026-11-08, retired 2026-11-13).** Two Shortcuts personal automations (App → Is Opened / Is Closed) were meant to POST every app open and close to `/api/screen-time/event` → `pds.phone_app_events`, paired into `pds.phone_app_sessions` and rolled up in `pds.phone_screen_daily`. The automations were never set up on the phone and the table **never received a row**; the Screen Time app (next bullet) replaced the idea before it was used (every app without ticking each one, Apple's own numbers, pickups and notifications). Removed 2026-11-13: the `/api/screen-time/event` route, its exact-path entry in `isCiRoute()` and the `/status` **Screen Time** card (it could only ever read Unknown / Never); `docs/screen_time_shortcuts_setup.md` is marked retired. Nothing else read these objects (checked: `hrv_analysis.py`, `causal_inference.py`, the frontend and the other repos read only `pds.phone_usage_*`). **Still in the database, on purpose:** the empty table and its two views (`sql/phone_screen_time_schema.sql`, kept as the record of what exists). Dropping them is a separate step that needs Riley's approval. Do not build on them, and do not re-add the route: screen time comes from the app.
- **Phone screen time v2 — the Onyx Screen Time iPhone app (2026-11-11, `tools/screentime_ios`, `sql/phone_usage_schema.sql`).** Uses Apple's iOS 26.4 Screen Time export API (`DeviceActivityData.activityData`), which outside the EU works only in a development-signed personal build: built and signed on a GitHub macOS runner (`screentime-ios.yml`; Riley has no Mac), installed over the air from `/install` (manifest served as text/xml by the public exact-path route `/api/screen-time/manifest/<32 hex>` because Supabase Storage serves XML as text/plain; one-tap token copy via the session-only `/api/screen-time/token`). Apple cert + profile expire **2027-11-10** (see the tools README for renewal). A daily Shortcuts Time-of-Day automation runs the app's "Sync Screen Time to Onyx" action (verified to work with the phone LOCKED) → `POST /api/screen-time/usage` (CI token) → `pds.phone_usage_segments` (hourly) + `phone_usage_items` → view `pds.phone_usage_daily` (total/late-night/after-midnight minutes, pickups, notifications, per-app + per-category minutes, bedtime-anchored `_est` columns). Every app, including future installs; the first sync backfilled ~30 days (Apple's retention). Service-role only. Heartbeat `screen_time|usage`, `/status` card "Screen Time app". **Failed syncs (2026-11-11):** the app POSTs `{failure: {stage, message}}` (stages `access`/`read`/`encode`/`network`/`http`) to the same route when a sync breaks, which writes a failed heartbeat so the card goes red on that run; a rejected upload (400) or DB error (500) logs one server-side and answers `logged: true` so the app does not report it twice. Heartbeat text never echoes usage data (sync_log is owner-readable). A missing or refused token cannot be reported, so the card still ages out (>36 h red). **HRV pipeline (2026-11-11):** `hrv_analysis.py:merge_screen_time_features` puts day D on row D (same night) as `screen_total_min`, `_late_night_min`, `_after_midnight_min`, `_pickups`, `_notifications`, `_social_min`, `_last_hour_before_sleep_min`, `_during_sleep_min`; a day counts only once a sync happened after it ended (partial days NaN), unreported days NaN (never zero-filled). `screen_` is in `NOT_FORECAST_PREFIXES` (with `delivery_`) so it stays out of the forecast; `screen_during_sleep_min` is same-sleep and `screen_last_hour_before_sleep_min` needs sleep onset (`hrv_alignment.py`). Six `CONTINUOUS_TREATMENTS` (family behavior); they sit in `dropped_low_n` until `MIN_CONTINUOUS_N` days accrue and then join the FDR family automatically — no manual step. Test: `tests/test_screen_time_features.py`.

## Screen Time page (2026-11-13)

`/screen-time` shows the Screen Time app's data (`pds.phone_usage_daily`, see "Phone screen time v2"): daily total, late-night minutes split at midnight, pickups + notifications, estimated minutes in the hour before WHOOP sleep onset and after it, top apps and top categories, for the last 14 / 30 / 90 days (`?days=`, 7 to 180, default 30). The view is service-role only, so the page follows the `/financials` pattern, NOT the ISR pattern: `force-dynamic`, `noindex`, read only by `lib/screen-time-server.ts` (`server-only`, explicit column list, logs an error code only) behind the owner-only middleware; the chart component gets its rows as props and the browser never queries the view. Failed query, empty window and data are three different screens. Pure logic in `lib/screen-time.ts`, mirroring the pipeline's readiness rules: a day is **complete** once a sync happened after it ended (`synced_at` >= day + 1 at 06:00 ET; the newest day is usually partial, drawn dimmed and left out of every average and top list), and the two sleep-anchored estimates are shown only when the day is complete, the WHOOP sleep is scored and the sync is at least an hour past sleep onset. Days the app never reported are gaps, never zeros. The export carries bundle ids, not app names (`phone_usage_items.name` is NULL), so top apps show a readable name derived from the id (`appLabel`) with the id beside it. Smoke: in `PAGES` with `legitimateEmpty` (a month without a sync skips; the failed-query text is a hard fail). Tests: `frontend/tests/screen-time.test.cjs` (synthetic rows; also renders the three states offline).

## PC activity logger (2026-11-14)

`tools/pc_activity_logger/activity_logger.py` (README there) runs on Riley's PC as one hidden process. Every 30 s it keeps two things: seconds since the last input (`GetLastInputInfo`, a timestamp only) and the foreground program's executable name. Never window titles, URLs, document names, keystrokes, the clipboard or the screen; `tests/test_pc_activity_aggregation.py` fails if the source gains one of those APIs. Active = input within 3 min and the screen not locked. Samples stay in `%LOCALAPPDATA%\Onyx\pc-activity` (removed 30 days after upload). Every hour each pending day is upserted to `pds.pc_activity_hours` / `pds.pc_activity_apps` (`sql/pc_activity_schema.sql`, service-role only; view `pds.pc_activity_daily` per behavioral day with late 21:00+ and per-program minutes) over PostgREST with `~/.onyx_supabase_secret`, plus a `pc_activity|usage` heartbeat through `sync_log_helper.log_sync` on every upload and on a crash. `/status` card "PC Activity" (>26 h degraded, >72 h or a failed row red). Standard library only: no pip install on the PC. **Not built yet:** check-in pre-fills from it ("Worked late?", "BI/Python/AL/Excel"), because the program-to-habit mapping and the late threshold need Riley's decision and some real data. The iPhone place-visits half of the same roadmap row needs iOS app work and a device test.

## AI tool usage harvester (2026-11-14)

`tools/ai_usage_harvest/ai_usage_harvest.py` (README there) runs on Riley's PC every 3 h as a hidden scheduled task ("Onyx AI Usage Harvest", `pythonw.exe`). It reads the session logs Claude Code (`~/.claude/projects/<project>/<session>.jsonl`, subagent transcripts nested under `<session>/`) and Codex (`~/.codex/sessions/**/*.jsonl[.zst]`) keep on the PC. **Privacy is the main requirement:** those logs hold whole conversations and possibly secrets, so each line is parsed in memory and only its time, record / block types, model name, token counts and (once per session) the working folder's NAME are kept. Never prompt or reply text, tool inputs or outputs, paths, branches, titles or ids. Rows are built from an allow-list and checked by `check_row` before upload; a failing row stops the upload with a `GUARD privacy:` failed heartbeat; errors are logged as their type name only. `tests/test_ai_usage_harvest.py` feeds synthetic logs whose every content field carries a marker and fails if it reaches the rows, the dry-run output, the upload, the heartbeat or the log. Never put real log lines in a test or a fixture.

One row per (device, behavioral day, tool, project) in `pds.ai_tool_usage_daily` (`sql/ai_tool_usage_schema.sql`, owner read + service role; **not applied yet**), upserted over PostgREST with `~/.onyx_supabase_secret` (it imports the PC activity logger's `Rest` client), plus an `ai_usage|sessions` heartbeat through `sync_log_helper.log_sync` on every run (`partial` = some files unreadable). `/status` card "AI Tool Usage" (heartbeat only; >26 h degraded, >72 h or failed red). Rules: top-level sessions only count as sessions / prompts / active minutes (subagents add tokens, tool calls and a subagent count); SDK (`sdk-*`) and Codex `exec` runs are left out; records repeated by resumed or forked sessions count once; behavioral day in the PC's zone; Codex times come from its turn / item events because the desktop app sometimes writes a turn's lines later in one batch. A day is re-sent until it has ended + 1 h, then final (`%LOCALAPPDATA%\Onyx\ai-usage\state.json`), so Claude Code deleting logs after ~30 days never shrinks a stored day; Claude Code days older than 25 days are not sent. Riley's steps: apply the SQL, then `pwsh -File tools\ai_usage_harvest\register-task.ps1`. **Not built yet:** any page or check-in use of the data. Tests: `tests/test_ai_usage_harvest.py`, `frontend/tests/ai-usage-status.test.cjs`.

## Desktop app (2026-11-14)

Onyx on Windows is the site installed as a PWA from Edge or Chrome (own window, Start menu + taskbar entry, Windows notifications for `/agents` via the existing `public/sw.js`, taskbar badge via `setAppBadge`); no Electron / Tauri shell, nothing to sign or update. `public/manifest.json`: **`id` and `start_url` stay `"/"`** (Edge derives the app identity from them; changing either turns existing installs into a second app), `scope` `/`, `theme_color` / `background_color` = `--color-surface` (`#1A1A18`, the title bar), `launch_handler` `focus-existing` (a launch focuses the open window; `components/DesktopApp.tsx:DesktopLaunchHandler` reads `launchQueue` and moves it only for a jump-list shortcut, a plain launch keeps the page that was open; rule in `lib/desktop-app.ts:launchTarget`), and a taskbar jump list (`shortcuts`: Today, Agents, Log, Status; every URL must be a `NAV_SECTIONS` route other than `/`). Inside the installed window (display mode `standalone` or `window-controls-overlay`, which have no browser toolbar) the sidebar shows **Reload** (`ReloadAppButton`, same as Ctrl R / F5; hidden in a normal tab and in `minimal-ui`). The sidebar shows **Install desktop app** only when the browser offers the install (`beforeinstallprompt`, caught at module load); Edge's address-bar install icon does the same. Start-at-sign-in is Edge's own per-app setting (`edge://apps`). The command-palette hint reads Ctrl K on Windows. **Go-to shortcuts (2026-11-15):** press G, then a page's key within 1.5 s to open it client-side on the warmed page (`lib/go-shortcuts.ts`, listener in `components/CommandPalette.tsx`); ignored while typing and with a modifier held. Keys are the `shortcut` of each `NAV_SECTIONS` item, unique and required (`tests/go-shortcuts.test.cjs`); all 26 letters are used, so Cash forecast is `4`. The sidebar (desktop width) and the palette show them as "G H". Headless Edge never fetches a manifest, so check installability in an off-screen headed window (`Page.getInstallabilityErrors`). Test: `frontend/tests/desktop-app.test.cjs`.

## Focus habit unlock (2026-11-13)

The Onyx Focus iPhone build (`tools/screentime_ios`, `project-focus.yml`; spec and limits in `tools/screentime_ios/FOCUS.md`, phone test steps H0 to H6 in `docs/focus-device-test.md`) can unlock its app block from real habits. Riley picks a few habits and a rule on the `/install` card "Focus: unlock with habits" (`components/FocusUnlockSettings.tsx`; each change autosaves, no Save button): **habits OR time** (finishing them unlocks early; the phone's unlock time unlocks regardless) or **habits AND time** (stays blocked after the unlock time until they are done). Default = nothing chosen = the phone's time-only rule, unchanged. Storage: `pds.focus_unlock_config` (`sql/focus_unlock_config.sql`; one row, `rule` + `habit_page_ids` = `habit_name_map.notion_page_id`, service-role only, at most 10). Routes: `GET/PUT /api/focus/config` (owner session only; PUT is same-origin JSON, at most 1 KB, ids must exist in `habit_name_map`) and **`GET /api/focus/unlock-status`, one more exact path in `isCiRoute()` (never widen it to `/api/focus/*`)**: read-only, answers the behavioral day (`pds.behavioral_today_now()`), the rule and, for the chosen habits only, name + whether `habit_journal` has `answer='Yes'` for that day. Decision table: `shouldUnlock` in `lib/focus-unlock.ts`, mirrored in `FocusCore/Sources/FocusCore/OnyxHabits.swift` (a node test fails if the two drift). **The phone checks only when the app is opened, on "Check now", or from the "Check Onyx Focus habits" shortcut action; there is no background check and no push**, so a finished habit unlocks nothing until then, and under AND the app must be opened once a day. A check that fails (offline, token refused, server error) falls back to the unlock time alone under both rules and says so on the Focus screen; an answer only counts when Onyx's behavioral day equals the phone's calendar day (so from 06:00). Not an ingestion source: no heartbeat, no `/status` card. Tests: `frontend/tests/focus-unlock.test.cjs`, `swift test` in `FocusCore` (run by `focus-ios.yml`). After a change to the Swift side, run `gh workflow run focus-ios-signed.yml` so `/install` offers the new build.
