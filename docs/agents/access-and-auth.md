## Auth

- **Auth**: Supabase Auth — email + password (primary) with magic link fallback. Single owner account; new sign-ups disabled (2026-11-10). RLS on all tables (see the access model under Database). `/account` page exposes `supabase.auth.updateUser({ password })` for self-service password changes.
  - **`/api/habits/*` boundary (2026-06-14):** these routes write `habit_journal` (+ trigger Notion) with the service-role key, so middleware enforces a valid Supabase session **OR** a constant-time `x-onyx-ci-token` shared secret (`ONYX_CI_TOKEN`, fail-closed when unset). It is **NOT** matcher-exempt anymore — do NOT re-exempt `/api/habits`, that re-opens public writes (the bug fixed here). Unauthenticated `/api/habits` → 401 JSON (not a 307 to /login a curl could swallow). The hourly `habits-sync.yml` curl sends the header; **`ONYX_CI_TOKEN` must exist in BOTH GitHub Actions secrets and Vercel env (Production)** — rotate in both + redeploy if leaked. Browser `/habits` calls use the session path (no token needed). The same carve-out (`isCiRoute()` in `middleware.ts`) also admits exactly one more path, `/api/reading/highlights/import`, for the local Kindle harvester (2026-11-07) — do not widen it to `/api/reading/*`. The Kindle harvester's Amazon order pass uses `/api/orders/amazon/import` (2026-11-12) — never widen it to `/api/orders/*` (the `/orders` PATCH must stay session-only). A third exact path, `/api/screen-time/usage`, admits the Onyx Screen Time iPhone app (2026-11-09); the v1 Shortcuts entry `/api/screen-time/event` was removed 2026-11-13 together with its route — do not re-add it.

## Access model

- **Access model (2026-11-10, `sql/pds_owner_only_read.sql`): the anon key reads NOTHING in `pds`** (no schema USAGE — the key ships in the site's JS and the repo is public). The signed-in owner (`auth.users` id `dc041abc-…`, the only account; sign-ups are OFF in Supabase Auth) reads tables through `owner_read` RLS policies; service role = full access. Frontend: `lib/supabase.ts` uses the service role on the server (ISR prefetch) and the cookie session in the browser; `middleware.ts` accepts only the owner id. A new table the browser reads needs `GRANT SELECT … TO authenticated` + an `owner_read` policy (re-run part 1 of that file). Older schema files that grant/create policies for anon are now inert — never `GRANT USAGE ON SCHEMA pds TO anon`. Screen Time v2 tables (`phone_usage_*`) are service-role only, not even owner-readable. **Materialized views (`*_mat`) have no row security, so the browser never reads one (SEC-01-B, 2026-11-16):** each read is a `read*` function in `lib/queries.ts` / `lib/queries-hrv.ts` that starts with `assertServerRead`, runs on the server with the service role and reaches the browser only through `GET /api/derived/<name>` (`lib/derived-reads.ts`: fixed names and date rule; owner session, same-origin, no-store, never in `isCiRoute()`); a new matview read adds a name there, and `frontend/tests/derived-reads.test.cjs` fails on a direct read anywhere else. `sql/pds_matview_revoke_authenticated.sql` (check: `sql/checks/verify_matview_revoke.sql`) makes every pds matview service-role only, and the pds default privileges grant `authenticated` on each new relation, so any migration that creates or recreates a matview ends with that REVOKE.
