## AI Chat

- **AI Chat**: Claude Sonnet 4, agentic tool-use loop with 32 tools (11 query + mark_habit_complete + log_supplement_stack + log_supplement_intake + the 4 reading tools `get_reading_status` / `log_reading_session` / `add_book_highlight` / `record_reading_quiz` + query_journal + query_journal_entries + query_eight_sleep + search_spotify_catalog + query_spotify_tracks_by_features + create_spotify_playlist + the 5 nutrition tools `query_nutrition` / `query_meals_log` / `query_vitamins` / `query_micronutrient_trend` / `query_photo_meals` (read-only: `pds.photo_meals` per-meal rows + `photo_meal_daily` totals, 14-day default / 90 max, fail-open on a missing relation), whose descriptions encode the food→Cronometer / supplements→Onyx split — and that a photo meal counts only on a day with no Cronometer log and never double-counts Uber Eats — so the model never double-counts). Habit completion via chat syncs to both Supabase and Notion. `log_supplement_stack` records a whole named supplement stack ("log my morning stack") as consumed — one intake per item — via `lib/supplement-stacks.ts`. `log_supplement_intake` (2026-11-09, `lib/supplement-intake.ts`) records ONE product from the `/supplements` list by name with a custom amount and clock times ("log 15 mg of Adderall at 8:30am and noon" → two rows of 1.5 doses of the 10 mg tablet): the product resolves by name, brand or ingredient text (brand names kept in an ingredient's `notes` match), a weight amount is divided by the label quantity and a count by the serving size, each time becomes an instant in the TZ from `pds.tz_for_instant` (a time before 06:00 is the awake tail = next calendar date, so it stays on the behavioral `intake_date`), and re-sending the same timed entry is skipped. No times: today → now, a past day → `intake_time` NULL. The chat system prompt also gets the current local time + behavioral day appended per request (the model has no clock). Playlist creation goes via `lib/spotify-server.ts` which refreshes the access token on every call against `pds.ci_tokens` and writes any rotated refresh token back so the Python ETL stays in sync. `query_journal_entries` supports semantic search via Voyage AI embeddings (voyage-3-large) — frontend embeds the user's query at request time, then RPC runs cosine similarity against pre-computed entry embeddings. **Chat replies and write receipts (2026-11-13):** `/chat` renders assistant replies as Markdown with the in-repo parser `lib/chat-markdown.ts` + `components/ChatMarkdown.tsx` (GFM tables, lists, bold, code, links; no markdown dependency). It builds React elements from a tree, so there is no HTML string anywhere and raw HTML in a reply shows as text; links are kept only for http(s), mailto and in-app paths. Write tools are the `WRITE_TOOLS` list in `lib/chat-receipts.ts` (habit, supplement intake, stack, reading session, highlight, quiz, playlist). Each carries the explicit-request gate in its description (`WRITE_GATE*`, mirrored in `CHAT_SCOPE`: only on an explicit request or a direct report in the user's latest message, never inferred; there is deliberately NO confirm dialog, so "log 15 mg of X at 8:30" still works in one message) and each produces a **receipt** that the server builds from the tool's own result (`buildWriteReceipt`), returned as `receipts` next to `response` (also on a 422 / 499 / 500 after a write ran) and shown in a box under the reply (`components/ChatReceipts.tsx`): saved / no change / not saved / check this. A new write tool must be added to `WRITE_TOOLS` (a test fails otherwise) and must answer `{success: true, …}` with the fields it wrote. **Write authority (SEC-05, 2026-11-16, `lib/chat-write-intent.ts`):** the description gate is not the boundary; before a write-tool call runs (and before the ledger records it) the route checks it against a grant built from the conversation the user sent, never from a tool result: the latest message is read as ACTIONS (one item asked for or reported, in a clause that is not a question, a condition ("if I take..."), a plan or a hedge, plus the argument-only clauses after it: "...and noon"), with quoted text masked out (double and curly quotes also over several lines, block quotes with their continuation lines, fenced and inline code; an unclosed quote or fence masks the rest). Each call must match one action: it names the record (every word of a product or stack, half of a habit's) as the object of a verb that fits the write ("log" / "mark" or "took" / "had" for an intake; "I read about X" and "I bought X" grant nothing) with the same polarity, read from the action's own clause before any "because" / "since" reason, never by counting negations ("I skipped X" allows only No for X, "I didn't take X" logs nothing, named both ways = refused, "I didn't skip X" or "...without X" = unclear, refused); "don't log X" / "log Y, not X" is a request not to write X (never a No) and "don't log it" refuses the whole message; its amount is that action's, in the unit kind `lib/supplement-intake.ts` counts it in (servings, pills, a weight: "2 servings" never becomes 2 capsules; one serving only when no other amount is stated), and an amount or time the action states cannot be left out; its times match the stated times one to one (a time sent twice must be said twice; a time shared by a list's last item is required for every item); a reading session's chapters are numbers said as chapters and its minutes a duration ("chapter 4 for 12 minutes" never gives chapter 12); the day it would write (its date, or the default when it sends none) is the day the action names, else its list's or sentence's, else today ("yesterday" with no date is refused; a sleep question defaults to last night); numbers arrive as numbers, never coerced from text; each action authorizes one write of each record (`commitWrite`: a repeated intake needs its own words); a reading write goes to the book the user named, else the book being read, and naming another known book refuses it (books unreadable = refused; a retry of a stored call is checked against the book it was first pinned to, `ChatLedger.storedContext`); stored recall / question / passage / comment text must be a verbatim span of the user's words. A short "yes" accepts only an assistant turn that asked exactly one question offering a write; a quiz result needs the user's own quiz request with the latest message answering a question of it (score within the questions asked AND answered, not stopped, not already recorded; "don't record a score" refuses it) or the user stating the score; a playlist needs an explicit request (each once per message). A refused call never runs and its receipt says why, lookup results are followed by `RETRIEVED_DATA_NOTE`, `CHAT_WRITES=off` makes chat read-only, and a new write tool is refused until it has a case in `authorizeWrite` (test: `frontend/tests/chat-write-intent.test.cjs`). A stack logged from chat for an earlier day stores no clock time (same rule as `/supplements`). **Replay-safe writes (SEC-04, 2026-11-16, `lib/chat-operations.ts`, `sql/chat_operations.sql`):** the page sends one `request_id` per message and the same id when a failed message is sent again unchanged (an edited one is new); a send whose answer never arrived is also remembered on the device until it is resolved, with no expiry (`onyx.chat.pending.<id>`, one key per send, written and removed alone so two tabs never overwrite each other's: per send a hash of the conversation + the id, never the text, wiped on sign-out; an unresolved send is never dropped to make room, so there is no cap on them; a first send refused before the route ran, 400 / 401 / 403 / 413, is not kept), and when the same conversation is sent again after a reload the page asks: **Retry that message** (the same request) or **Send as a new message** (a new id; the earlier send is abandoned on the server and forgotten only once that is recorded, otherwise it stays remembered next to the new one); a send whose account of what it saved was shown after a reload and dismissed is resolved and never matches a later message (after a reload each remembered send's account is shown in turn, newest first); "has not reached Onyx" is not proof on its own (the request may still be on its way), so dismissing it first records the id as abandoned (`POST /api/chat/operations` `{request_id, action: "abandon"}`, same-origin JSON, one ledger row under a conversation hash nothing matches), which refuses the request (409 `request_conflict`) if it arrives late, and the send is forgotten only once that row is recorded; when the request got there first, its account is shown instead. A retry whose ledger cannot be listed for what an earlier try saved answers `earlier_unconfirmed: true` (unknown, never "nothing"), the page says so and keeps the send remembered. Every write-tool call goes through the service-role ledger `pds.chat_operations` (owner, request, tool, n-th call, plus the behavioral day it first ran on). A retry's calls are matched to the stored rows by content (`matchingForm`: names the tools resolve case-insensitively, "8:30" = "08:30", empty fields ignored), in any order: a match gets the stored result and receipt back ("No change") instead of writing again; a call that matches nothing, or matches a call the earlier try refused, is refused (and again if repeated) whenever an earlier try wrote, or may have written, anything, so a retry never adds a write next to an earlier one (e.g. a replayed stack followed by its products one by one); it runs only when nothing earlier was written; a different intentional action is a new message; inside one try (a first try too) no new write starts while a call of that try is unconfirmed (it threw or says it may be incomplete), until a re-run of that same call confirms it, and a keyed re-run counts the try's own writes like an earlier try's; a re-run keeps the first try's day and book being read, and every date a ledger write is not given is sent as the operation's day, so a request that crosses the behavioral-day boundary while the model runs still writes on the day it was sent. A retry also answers as of the FIRST try: its local time, time zone and behavioral day are stored with the request row (`pds.chat_requests.context`, in the claim insert) and used for the retry's prompt and every new operation's default day, also when the first try stopped before recording any operation. **One try at a time:** each try holds a lease on its `pds.chat_requests` row (6 min, longer than the route's `maxDuration` 300 s, given back in `finally`); a retry while another try holds it gets 409 `request_in_progress` before the model runs. The operation id is the write's own key (`supplement_intake.client_event_key`, reading `client_key`, `book_highlights.client_key` on a highlight chat creates, `spotify_playlists.client_key`, written right after Spotify made the playlist with `track_count` NULL until the tracks are in); a failed database write counts as "not saved" only when its code is on the refusal allowlist in `lib/write-outcome.ts` (`definiteDbRefusal`: constraint, data, privilege and schema errors, a guard trigger's RAISE, a deadlock or serialization rollback, PostgREST request / schema-cache / JWT refusals); anything else (no code, a lost connection, 08007 transaction_resolution_unknown, 40003, a shutdown, PostgREST connection errors, any unlisted or future code) is "may be saved, check this", never "not saved", and a keyed write reads its rows back under the key; a reading session found under its key that an EARLIER call wrote is only read (its book finish, habit Yes and Notion entry are never made then: that call may have made them and Riley may have undone one since, such as a cleared habit answer; each one that shows nothing is listed as `unconfirmed` on the result and the receipt, which then reads "check this"), and the same holds for a highlight's Notion entry; only a session this call's own insert made, whose answer was lost, gets those steps (the habit Yes as one insert that does nothing when the day has an answer). Only keyed writes are re-run (`RERUN_SAFE`), and only read back (never written) when another call of the earlier try also wrote; a keyed intake or session Riley removed since leaves a tombstone (`pds.chat_operation_tombstones`, written by a trigger on the removal; an insert under it fails with SQLSTATE OXC01; the removal and the insert guard take one advisory transaction lock per operation id, so a retry crossing a removal never brings the row back), so a retry answers "removed since" and never writes it again; an unconfirmed habit answer is only checked (confirmed when the day holds exactly that answer, otherwise unconfirmed); a highlight is found by its key, or written only when no highlight of the book changed since the operation began, and then by one insert only (`addHighlight` `insert_only`: a highlight of that passage written meanwhile is never updated, only confirmed when it is what the call asked for); nothing is ever written over a change made since (`CHECK_ON_RERUN`); a re-run that comes back refused stays unconfirmed. A playlist left unconfirmed is looked up read-only by its key and never created again; a quiz result runs under the operation id as its `op_key` (`pds.reading_record_quiz`, with the operation's day), so a re-run answers the stored receipt, and in check mode it only reads `pds.reading_practice_ops` by that key; a new tool is in none of these sets, so it is never re-run. Fail closed: with a `request_id`, a missing ledger table or any ledger or owner-check failure runs no write tool (questions are still answered), and a keyed intake, session or highlight whose key column (or the tombstone table) is missing is refused, never written unkeyed (`logSession` with `require_client_key` refuses instead of its /log fallback), as is a playlist (checked before Spotify is asked for anything); only a request with no `request_id` (an older page) runs as before and is not called replay-safe. After a reload the page asks **`GET /api/chat/operations?request_id=`** (owner session only, never a CI route, read-only, no-store) what the remembered send saved and shows it, since the lost conversation cannot be re-sent as the same request. Tests: `frontend/scripts/test-chat.mjs` + `frontend/tests/chat-operations.test.cjs` + `frontend/tests/supplement-event-key.test.cjs` + `frontend/scripts/test-chat-markdown.mjs` (CI, via the `scripts/test-*.mjs` glob) and the browser check `node tests/chat-regression.cjs` (local only; needs a compile build for the CSS).

## Agents chat

- **Agents chat (`/agents`, 2026-10-18)** is Riley's channel to the personal agents (morning briefing, approvals, questions, leads) and replaces WhatsApp. The backend is the sms-reminders Worker (`C:\Users\riley\sms-reminders`, routes `/onyx/*`): it verifies the Supabase access token against this project's JWKS (only Riley's user id), stores the thread in its D1 and sends Web Push itself, so Onyx holds no secret for it. Client: `src/lib/agents-api.ts`; UI (2026-10-22, Messages-style): `src/app/agents/AgentsApp.tsx` routes `/agents` to `AgentsInbox.tsx` (Unread = open cards with their buttons + unread agent messages, filter chips per agent; All = one conversation per agent) and `/agents?t=<agent>` to `AgentsChat.tsx` (one conversation; `#m<id>` jumps to a message, `&reply=A12` starts a card answer); shared bits in `agent-ui.tsx`. Full-screen; AppShell drops the mobile bars on this route; push: `public/sw.js` (excluded from middleware). iPhone push needs the home-screen app. **Clearing (2026-11-12):** Unread has **Clear all** (every open card cleared + every message marked read) and an **×** on each card, with an 8-second Undo; both call the Worker's `POST /onyx/dismiss`, which only hides cards from Unread and the badge (the agent's Notion row, the decision ledger and the card's buttons in its conversation are untouched; a card the agent shows again returns). While the inbox is on screen, and on every clear, the app also closes Onyx's notifications in the phone's notification list (`clearDeviceNotifications()` in `lib/agents-api.ts`, via `getNotifications()`). The phone bottom bar (2026-11-15, `components/MobileNav.tsx`, `lib/mobile-tabs.ts`) is by default Today · Agents (with the unread count from the cached inbox and `setBadge()`, no polling of its own) · Log (opens `/log`, the Log screen, accent, centre; the quick-log sheet is gone) · Chat (`/chat`, Onyx Chat, the health Q&A) · More (the drawer); the four slots around Log can be chosen in Personalize (phone drawer, see Personalize); a tab is named after the page it opens and Trends lives in More and on Today.

## NYC apartment search

- **NYC apartment search (`/nyc`, 2026-11-07)** shows the nyc-scout agent's leads (personal-agents repo) as a Leaflet map (keyless OSM tiles darkened with a CSS filter — CARTO basemaps now require an API key) + sortable table. Data is NOT in Supabase: it lives in the Notion **"NYC Leads"** database (`967fdf52d6ee4aab9a5854298e564b43`, under Personal Agents; override with `NOTION_NYC_LEADS_DB`), read server-side with `NOTION_API_KEY` in `lib/nyc.ts` — so that database must stay shared with Onyx's Notion integration (a 404/403 renders as a "Couldn't load leads" banner and turns the `/status` NYC Scout card red). The scout upserts rows daily (key = `Number`); Riley's Interested / Toured / Pass buttons and note write ONLY the `Riley` / `Riley's note` properties (the note autosaves after a pause or when the box is left) via `PATCH /api/nyc/leads/[id]` (refuses pages outside the database, then `revalidateTag`), and the scout reads them next run. ISR hourly + silent mount revalidation via `GET /api/nyc/leads`, which answers from the Next data cache (tag `nyc-leads`, at most 5 minutes old, refreshed in the background; a live Notion query took 0.7-1.3 s, 2026-11-15). `/status` "NYC Scout" freshness = newest `Last verified` on a Live lead (daily-cadence thresholds).
