# DB perf follow-up, November 14, 2026

Follow-up to the 2026-06-07 re-audit (Notion row "DB perf: partitioning + materialized supplement rollups + redundant index cleanup"). The audit called all three items premature at the time. This pass measured them on the live database to decide again with numbers.

Everything here was read-only: catalog and statistics views, `EXPLAIN` without `ANALYZE`, and plain `SELECT`s. Nothing was applied. The SQL to apply is `sql/db_perf_2026_11.sql`; Riley applies it.

## Short version

| Finding | Verdict | Why, in one line |
|---|---|---|
| Partition `hrv_predictions` / `whoop_journal` (deepseek/F-006) | **Not worth it** | 22,097 and 12,360 rows. Partitioning starts to pay off around a million rows. |
| Materialize the supplement rollup (deepseek/F-008) | **Worth doing now** | About 69 s of DB time a day, roughly as much as the whole `refresh_perf_matviews` job. |
| Redundant `garmin_activity_laps(activity_id, lap_index)` index (gpt-5/F-006) | **Already done** | Removed live on 2026-06-08 (migration `20260608015255`). Only the unique index remains. |
| 12 other prefix-redundant indexes (found by this pass) | **Optional hygiene** | 656 kB in total, no measurable gain. Commented block, run by hand if you like. |
| `whoop_cycles` is 99% empty space (found by this pass) | **Worth doing now, by hand** | 425 kB of rows in a 40 MB file. It is the most-read table, and every full read touches 5,107 pages instead of ~55. |

## How the numbers were taken

- Postgres 17.6. Database 184 MB, `pds` schema 162 MB. `shared_buffers` 256 MB, `work_mem` 3.5 MB.
- The server restarted on 2026-11-11 07:21 UTC (the stall that day), and that reset the statistics. So every counter below covers **3.8 days** (to 2026-11-15 03:22 UTC). Counters such as `n_live_tup` read low for tables nobody wrote to since then. Row counts below come from `count(*)` or `reltuples`, not from those counters.
- Timings come from `pg_stat_statements` (mean per call over the window). "Expected" means estimated, not measured: I did not run `EXPLAIN ANALYZE`, and the matview does not exist yet.

## 1. Partitioning: not worth it

| Table | Rows | Total size | Growth | Writes since restart |
|---|---|---|---|---|
| `hrv_predictions` | 22,097 | 15 MB (5.7 MB heap, 9 MB indexes) | ~1,800 rows a month (June to November 2026) | 311 inserts, 179,283 updates |
| `whoop_journal` | 12,360 | 10 MB | none: newest `cycle_date` is 2026-06-08, the table is write-blocked | 0 |

At 1,800 rows a month, `hrv_predictions` reaches a million rows in roughly 45 years. Every query on it already uses an index (`uq_hrv_predictions_quad`: 179,608 scans; `idx_hrv_predictions_tiebreak`: 4,129). `whoop_journal` is a frozen archive, so partitioning it cannot help anything. Revisit if either table passes about a million rows.

What partitioning would not fix, but is worth knowing: the HRV pipeline rewrites rows it already has. 179,283 row updates in 3.8 days on a 22k-row table, and its upserts wrote 109 MB of WAL in that window (about 29 MB a day). See "Next" below.

## 2. Supplement rollup: worth doing now

`pds.supplement_intake_by_compound` expands every logged intake into its product's ingredients (3,309 intakes x 26 products = 18,236 JSONB rows) and parses each unit with regular expressions. It then groups the result into 10,609 rows over 178 days. All of that is redone on every read.

Who pays for it (3.8 days):

| Reader | Calls | Mean | Total | Note |
|---|---|---|---|---|
| `hrv_analysis.py`, full read of the rollup | 1,287 | 95 ms | 122 s | PostgREST caps pages at 1,000 rows, so each run reads 11 pages, and each page recomputes the whole rollup (117 runs = 1,287 pages). |
| `/nutrition` and the chat tools via `daily_micronutrient_totals` | 785 | 169 to 211 ms | 143 s | Recomputes the whole rollup inside a hash aggregate that spills past `work_mem`: 145,931 temp blocks (1.14 GB) written. |
| `/api/supplements/today` (one day) | 868 | 1.4 ms | 1 s | Already fast, because the date filter reaches the base table. Not changed. |
| `melatonin_unified` (pipeline) | 117 | 21 ms | 2 s | Filters reach the base table. Not changed. |

Together that is about 265 s in 3.8 days, roughly 69 s a day. For scale, `refresh_perf_matviews`, the heaviest job in the database, used 257 s in the same window. `daily_micronutrient_totals` is also the slowest REST call measured on `/nutrition` (193 to 247 ms p50 in `docs/perf-evidence-2026-11-12.md`). A full compute of the rollup took 280 ms in a direct query.

About the 1.14 GB of temp writes: each temp file lives for less than a second, so the operating system probably absorbs most of them before they reach the disk. Treat the disk-IO effect as uncertain. The CPU cost is not uncertain.

### What the SQL does (PART 2 of `sql/db_perf_2026_11.sql`)

1. **A matview copy** of the rollup, `pds.supplement_intake_by_compound_mat` (10,609 rows, ~2.1 MB). Its unique index is the rollup's own grouping key. That key was checked: no duplicates.
2. **Refresh only when something changed.** A pg_cron job runs every 5 minutes. It computes a fingerprint of everything the rollup depends on: intake rows, product ingredients, the view's definition and the two unit-conversion functions. That takes 10 to 25 ms. It rebuilds the matview only if the fingerprint moved, or once a day regardless. At today's logging rate (6 write statements in 3.8 days) that is about two rebuilds a day, each estimated at 0.3 to 0.5 s and ~2.4 MB of writes. A refresh every 30 minutes instead would write about 115 MB a day, on a database that has been warned about its disk-IO budget.
3. **No trigger on the supplement tables.** Logging a dose costs exactly what it costs today. A refresh inside the logging request was considered and rejected: it would add an estimated 0.3 to 0.5 s to every tap, against the rule that nothing Riley waits for takes a second.
4. **`daily_micronutrient_totals` reads the matview.** Only the `FROM` of one CTE changes, so the columns and rows are identical. A guard aborts the migration if that view changed after 2026-11-14 (md5 of its definition, `2264c161…`). Dry run on live data: the new definition over a snapshot of the rollup matched the current view row for row (179 = 179 rows, 0 differences in either direction).
5. **A heartbeat on every rebuild**: `pds.sync_log`, source `supplement_mat`, `success` or `failed` (with a schema-drift check). A failed rebuild never raises. The matview keeps its last good rows, and the job retries hourly rather than every 5 minutes. So a lasting error writes at most 24 heartbeats a day and cannot crowd other sources out of the 100-row history /status reads. The refresh has a 5 s `lock_timeout`, so it gives up rather than queueing behind a long reader.
6. **Readable by `service_role` only.** `daily_micronutrient_totals` runs with its owner's rights, so /nutrition and chat need no grant on the matview. That keeps it off the Data API for anon and authenticated, like the Garmin matviews since `security_lockdown_2026_06_06.sql`.
7. **Safe to re-run.** A guard at the top checks the md5 and that the view has no options, and accepts the already-applied state. It stops the migration before anything is created.

Freshness cost: a logged dose reaches `hrv_analysis.py` and the `/nutrition` vitamin totals within 5 minutes instead of at once. `/supplements` and `/api/supplements/today` still read the live tables and view, so the logging screen does not change. `/nutrition` is an ISR page that also refetches on mount, so a delay of up to 5 minutes on one card is the visible effect.

Expected effect (not yet measured): each rollup page becomes a plain scan of a 2.4 MB table (low single-digit ms instead of 95 ms), and `daily_micronutrient_totals` aggregates 10.6k narrow rows with no temp spill (tens of ms instead of 169 to 211). PART 3 of the SQL file has the queries to confirm it.

### Code in this PR

`hrv_analysis.py` reads the rollup through `fetch_supplement_rollup()`. It tries the matview and falls back to the live view if the matview is missing (`PGRST205` / `42P01`, the state until the SQL is applied) or errors. Both hold the same rows, so the fallback costs only time. Pages are still read unordered, as before. A rebuild landing between two of a run's 11 page requests could shift rows at a page boundary. The live view had the same exposure to writes, and the chance is small (about two rebuilds a day against a read of about a second). Sorting the pages would not remove it. Test: `tests/test_supplement_rollup_source.py` (synthetic, not run before merge per AGENTS.md).

The frontend needs no change: it reads `daily_micronutrient_totals`, which PART 2 re-points at the matview.

## 3. Redundant indexes

The audit's index, `garmin_activity_laps (activity_id, lap_index)`, is gone. It was removed live on 2026-06-08, and `pg_indexes` now shows only `garmin_activity_laps_unique (activity_id, lap_index, ts)`.

A scan of `pg_index` for btree indexes whose columns are a leading prefix of another btree index on the same table (same predicate, no expressions) found 12 more:

| Index | Size | Scans (3.8 d) | Covered by |
|---|---|---|---|
| `idx_habit_journal_date` | 136 kB | 8,303 | `habit_journal_pkey (cycle_date, question)` |
| `idx_spotify_plays_date` | 80 kB | 3,854 | `idx_spotify_plays_date_track (played_date_et, track_id)` |
| `idx_supplement_intake_date` (DESC) | 64 kB | 5,697 | `idx_supplement_intake_date_product (intake_date, product_id)` |
| `idx_sleep_calendar` (DESC) | 56 kB | 8 | `garmin_sleep_unique (calendar_date, sleep_id, ts)` |
| `idx_hr_calendar` (DESC) | 56 kB | 559,962 | `garmin_heart_rate_unique (calendar_date, ts)` |
| `idx_daily_calendar` (DESC) | 56 kB | 563,376 | `garmin_daily_summary_unique (calendar_date, ts)` |
| `idx_stress_calendar` (DESC) | 56 kB | 389,684 | `garmin_stress_unique (calendar_date, ts)` |
| `idx_training_cal` (DESC) | 48 kB | 559,302 | `garmin_training_status_unique (calendar_date, ts)` |
| `idx_hrv_calendar` (DESC) | 40 kB | 13 | `garmin_hrv_unique (calendar_date, ts)` |
| `idx_eight_sleep_trends_date` | 32 kB | 2,106 | `eight_sleep_trends_pkey (calendar_date, bed_side)` |
| `idx_supplement_stack_item_stack` | 16 kB | 399 | `supplement_stack_item_stack_id_product_id_key (stack_id, product_id)` |
| `idx_habit_metadata_history_page_from` | 16 kB | 0 | `habit_metadata_history_pkey (notion_page_id, valid_from)` |

Btree indexes scan in either direction, so a `DESC` single-column index is covered by the ascending composite. High scan counts only mean the planner currently prefers the smaller index. It will use the composite one instead, at practically the same cost for tables of about a thousand rows. Total saving: 656 kB and a little write work. The Garmin tables' updates are almost all HOT, so they skip index writes already. **Verdict: safe, cosmetic.** They are in PART 5 as a commented `DROP INDEX CONCURRENTLY` block with exact rollback statements, for Riley to run by hand or skip.

Not in that list on purpose: `hrv_predictions_input_hash_idx` (3.4 MB, 0 scans). It is unused, not redundant. Nothing in the code looks predictions up by hash: the `hrv_predictions_latest` view compares the hash inside an `OR`, and the planner did not use the index once in 3.8 days. Because the pipeline's upsert rewrites `input_data_hash`, an indexed column, every row whose hash changes cannot be a cheap in-place (HOT) update and must write all four indexes. Removing it is probably right, but it is a judgment call about future lookups, so it is listed under Next.

## 4. `whoop_cycles` (and two smaller tables) are mostly empty space

| Table | Rows | Live data | Heap file | Bytes on disk per row | Expected row size |
|---|---|---|---|---|---|
| `whoop_cycles` | 741 | 425 kB | **40 MB** (5,107 pages) | 56,460 | ~581 |
| `garmin_activity_laps` | 3,903 | 5.8 MB | 12 MB | 3,094 | ~1,588 |
| `garmin_sleep` | 243 | 1.2 MB | 2.3 MB | 9,918 | ~1,557 |

`whoop_cycles` is the most-read table in the database: 41.2 million page reads in 3.8 days, eight times the next table. 7,621 sequential scans each read all 5,107 pages to find 741 rows. The HRV pipeline's full read of it averages 366 ms (117 calls, about 5,065 pages each). The empty pages also sit in shared buffers: 40 MB out of 256 MB.

It is not growing now. Autovacuum ran three times since the restart, and dead rows are at 26. The space is left over from some past bulk rewrite, and plain vacuum never gives file space back. `VACUUM FULL` rewrites the table compactly, in well under a second at this size. It is in PART 4 as commented statements to run by hand, because it takes an exclusive lock and cannot run inside a migration. Expected: 40 MB to about 0.5 MB, and full reads about 1% of today's page count. The time saved is expected, not measured. `garmin_activity_laps` (also read in full by the pipeline: 468 calls, 127 ms mean) and `garmin_sleep` are about 2x and 6x their live size, so they are included too. PART 3g is a bloat watch that can be re-run any time.

## Next (not in this PR)

1. **HRV pipeline upsert churn.** 179,283 updates in 3.8 days on a 22k-row `hrv_predictions`, 109 MB of WAL. The pipeline re-upserts rows whose values did not change. Skipping unchanged rows in the pipeline would cut most of that write load. Then decide on `hrv_predictions_input_hash_idx` (above).
2. **`/status` card for the `supplement_mat` heartbeat** once PART 2 is applied (`api/status/route.ts` and `status/page.tsx`, like the Perf Matviews card; healthy if the newest row is `success` and under ~25 h old). A failed refresh otherwise leaves the pipeline and /nutrition on the last good rows with no visible alarm. If it gets a card, give it a limit-1 fetch and add it to the route's `matrix_mat`/`perf_mats` exclusion list, as those two have.
3. **Spotify "prior tracks" read** (`fetchPriorTrackIds` in `lib/queries.ts`): it reads every play before a date, page by page, to build a set of track ids. 2,877 calls, 103 s in 3.8 days. A `SELECT DISTINCT track_id` RPC, or a covering index `(played_at) INCLUDE (played_date_et, track_id)`, would likely cut it. This was not measured here, so measure first.
4. After PART 2 is applied, update the repo mirror `sql/daily_micronutrient_totals.sql` to the matview-backed definition, so that re-running the mirror does not silently undo the speedup (it would still return the same rows).
