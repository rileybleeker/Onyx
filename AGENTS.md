# Onyx — Agent Instructions

Read by every coding agent (Claude Code, Codex, Cursor, Copilot, Gemini CLI, …). This is the only project-instructions file; there is no CLAUDE.md.

Personal health data aggregation and analytics platform.
Syncs biometric data from Garmin, WHOOP, and Eight Sleep into a unified Supabase Postgres database,
visualized via a Next.js frontend with AI-powered analysis through Claude.

## Tech Stack

- **ETL**: Python 3, httpx, garminconnect, supabase-py, python-dotenv
- **Database**: Supabase (Postgres 17), schema `pds`, 19 tables + `journal` unified view + 3 HRV analysis tables (`hrv_predictions`, `hrv_model_metrics`, `hrv_analysis_results`) + Spotify (`spotify_plays`, `spotify_tracks`, `spotify_artists`, `spotify_playlists`, `spotify_daily_signature` view) + Supplements (`supplement_products`, `supplement_intake`, `supplement_intake_by_compound` view, `daily_supplement_matrix` view) + Notion personal Journal (`journal_entries` with pgvector embeddings, `search_journal_entries` RPC) + Tanita body comp (`tanita_measurements` raw + `weight_log` daily rollup)
- **Frontend**: Next.js 15, React 19, Tailwind CSS 4, Recharts 3.8, TypeScript 5
- **Frontend perf architecture (2026-06-11, see `docs/perf_report_2026-06-11.md`)**: middleware verifies session JWTs **locally** via `supabase.auth.getClaims()` (project signs with ES256; never reintroduce a per-request network `getUser()` — it cost ~50-150 ms × ~13 requests per page view). Ten read-only dashboards are **ISR pages** (`export const revalidate = 3600`, matching the hourly ETL cadence): a server `page.tsx` runs the same `lib/queries` fns and passes `initial` data into a `<Name>Loader.tsx` client wrapper hosting the `dynamic(ssr:false)` chunk; the client seeds state from props and keeps its mount fetch as a **silent revalidation** (no skeleton — never skip it, a stale snapshot must heal). Pattern contracts: (1) server prefetch args must **explicitly mirror** the client effect's default-state args (several fn defaults diverge); (2) prefetch fns must `throw` on PostgREST error so the fail-open `try/catch` actually fails open; (3) write-coupled pages (`/supplements`, `/habits` with its on-load Notion-sync POST) are deliberately NOT ISR. Heavy tables are read via **explicit all-scalar column lists** (`WHOOP_*_COLS`/`GARMIN_*_COLS`/`EIGHT_SLEEP_TRENDS_COLS` in `queries.ts`) — `raw_json`-class jsonb blobs must never ride in page-load selects (whoop_cycles is ~70 kB/row of raw_json), and when an ETL adds a scalar column it must be appended to the matching list.
- **Frontend render conventions (perf round 3, 2026-06-11)**: (1) **every recharts series element sets `isAnimationActive={false}`** — profiling showed mount animations never affect first paint (they run post-paint), cost up to ~820 ms of jank, and fully replay on every revalidation commit; (2) **ISR clients' silent-revalidation setters use the deep-equal bailout** `setX(prev => sameJson(prev, next) ? prev : next)` (`sameJson` in `lib/format.ts`) — the refetch is byte-identical to the seed in the common case, so the guard lets React skip the whole re-render; this makes **deterministic query ordering load-bearing** (any non-unique sort key needs a secondary `.order()`); (3) **chart-dense pages wrap below-fold sections in `components/DeferredMount.tsx`** (one-section-per-frame scheduler; everything mounts unconditionally without scroll — required by the smoke suite's below-fold assertions; never wrap above-fold content; give placeholders a realistic `minHeight`); (4) **tier-2 perf matviews** (`sql/perf_tier2_matviews.sql`): `tz_log_gaps_mat` + `hrv_prediction_gaps_mat` (/api/status), `spotify_daily_signature_mat`, `recovery_vs_pace_mat`, `hrv_residuals_mat` — same drift rule as the matrix matview (drop+recreate the `_mat` in the same migration as any change to its source view; never CASCADE); refreshed by `pds.refresh_perf_matviews()` at :12/:27/:42/:57 with ONE `perf_mats` heartbeat + /status card covering all five.
- **AI Chat**: Claude Sonnet 4, agentic tool-use loop with 28 tools (11 query + mark_habit_complete + log_supplement_stack + log_supplement_intake + the 4 reading tools `get_reading_status` / `log_reading_session` / `add_book_highlight` / `record_reading_quiz` + query_journal + query_journal_entries + query_eight_sleep + search_spotify_catalog + query_spotify_tracks_by_features + create_spotify_playlist + the 4 nutrition tools `query_nutrition` / `query_meals_log` / `query_vitamins` / `query_micronutrient_trend`, whose descriptions encode the food→Cronometer / supplements→Onyx split so the model never double-counts). Habit completion via chat syncs to both Supabase and Notion. `log_supplement_stack` records a whole named supplement stack ("log my morning stack") as consumed — one intake per item — via `lib/supplement-stacks.ts`. `log_supplement_intake` (2026-11-09, `lib/supplement-intake.ts`) records ONE product from the `/supplements` list by name with a custom amount and clock times ("log 15 mg of Adderall at 8:30am and noon" → two rows of 1.5 doses of the 10 mg tablet): the product resolves by name, brand or ingredient text (brand names kept in an ingredient's `notes` match), a weight amount is divided by the label quantity and a count by the serving size, each time becomes an instant in the TZ from `pds.tz_for_instant` (a time before 06:00 is the awake tail = next calendar date, so it stays on the behavioral `intake_date`), and re-sending the same timed entry is skipped. No times: today → now, a past day → `intake_time` NULL. The chat system prompt also gets the current local time + behavioral day appended per request (the model has no clock). Playlist creation goes via `lib/spotify-server.ts` which refreshes the access token on every call against `pds.ci_tokens` and writes any rotated refresh token back so the Python ETL stays in sync. `query_journal_entries` supports semantic search via Voyage AI embeddings (voyage-3-large) — frontend embeds the user's query at request time, then RPC runs cosine similarity against pre-computed entry embeddings. **Chat replies and write receipts (2026-11-13):** `/chat` renders assistant replies as Markdown with the in-repo parser `lib/chat-markdown.ts` + `components/ChatMarkdown.tsx` (GFM tables, lists, bold, code, links; no markdown dependency). It builds React elements from a tree, so there is no HTML string anywhere and raw HTML in a reply shows as text; links are kept only for http(s), mailto and in-app paths. Write tools are the `WRITE_TOOLS` list in `lib/chat-receipts.ts` (habit, supplement intake, stack, reading session, highlight, quiz, playlist). Each carries the explicit-request gate in its description (`WRITE_GATE*`, mirrored in `CHAT_SCOPE`: only on an explicit request or a direct report in the user's latest message, never inferred; there is deliberately NO confirm dialog, so "log 15 mg of X at 8:30" still works in one message) and each produces a **receipt** that the server builds from the tool's own result (`buildWriteReceipt`), returned as `receipts` next to `response` (also on a 422 / 499 / 500 after a write ran) and shown in a box under the reply (`components/ChatReceipts.tsx`): saved / no change / not saved / check this. A new write tool must be added to `WRITE_TOOLS` (a test fails otherwise) and must answer `{success: true, …}` with the fields it wrote. A stack logged from chat for an earlier day stores no clock time (same rule as `/supplements`). Tests: `frontend/scripts/test-chat.mjs` + `frontend/scripts/test-chat-markdown.mjs` (CI, via the `scripts/test-*.mjs` glob) and the browser check `node tests/chat-regression.cjs` (local only; needs a compile build for the CSS).
- **System Status**: `/status` page — source cards for every ingestion ETL + the HRV Analysis predict path + the **HRV Retrain** card (predict and retrain tracked separately because the predict path keeps writing fresh forecasts from the cached model even when the retrain pipeline crashes — the audit caught the `category`/`categories[]` rename had been breaking every retrain attempt for weeks before this card existed). Each card has a **Method** row (`automated` cyan / `semi-automated` amber-300 / `manual` amber-500) and a Cadence row, KPI summary, 20-entry sync history. The HRV Retrain card derives status from `pds.sync_log` heartbeats emitted by `hrv_analysis.py` (`source='hrv_analysis', data_type='retrain'`), with `MAX(hrv_analysis_results.computed_at)` as fallback for historical runs that predate the heartbeat. >30h since last successful retrain = `failed`, 26-30h = `partial`. **Lesson learned (audit 2026-05-26):** any pipeline that writes to Supabase needs a sync_log heartbeat on EVERY run (success or failure) — without one, silent failures escape monitoring because downstream effects (predictions, dashboards) keep looking healthy via cached state. The `METHOD` map in `api/status/route.ts` is the source of truth for the automated/semi-automated/manual category — semi-automated = cron import that requires a user-triggered export from the source app (WHOOP and MFP have no API export; user must request CSV via the source's web UI, then the IMAP cron picks it up). `GET /api/status` queries `pds.sync_log` by `(source, data_type)` key + `MAX()` date per data table. Auto-refreshes every 60s. ReccoBeats + MusicBrainz are *enrichment* subsystems (not ingestion) — their freshness is based on `sync_start` recency (heartbeat) rather than data age, because "no new items to enrich today" is healthy, not stale. `enrichmentSource()` helper in `api/status/route.ts` encodes that semantics: >12h since last heartbeat = failed, >4h = partial, otherwise success. `spotify_etl.py` writes a sync_log row for each subsystem every run (even with `records_synced=0`).
- **Auth**: Supabase Auth — email + password (primary) with magic link fallback. Single owner account; new sign-ups disabled (2026-11-10). RLS on all tables (see the access model under Database). `/account` page exposes `supabase.auth.updateUser({ password })` for self-service password changes.
  - **`/api/habits/*` boundary (2026-06-14):** these routes write `habit_journal` (+ trigger Notion) with the service-role key, so middleware enforces a valid Supabase session **OR** a constant-time `x-onyx-ci-token` shared secret (`ONYX_CI_TOKEN`, fail-closed when unset). ## Database

- Schema: `pds`
- All tables use upsert with conflict resolution (idempotent ETL)
- **`habit_journal` is THE single behavior table (WHOOP journal merge, 2026-06-11 — `sql/whoop_journal_merge.sql`).** The WHOOP in-app journal was replaced by the habits system: the 12,360-row WHOOP history (Oct 2024 → 2026-06-08, explicit Yes/No answers) was copied in verbatim with a `source` column ('whoop'|'habit'), and the 30 questions active in the final export became Notion habits with **VERBATIM question text as titles** (the question string is the HRV pipeline's variable identity — `journal_*` slugs derive from it). Key invariants:
  - **`source` routing is by QUESTION IDENTITY, not write path**: `habit_name_map.channel` ('whoop'|'habit') drives a trigger that stamps `source='whoop'` on any insert of a WHOOP-derived question — so post-cutover habit taps keep feeding the same `journal_*` feature columns. Native habits stay `source='habit'` → `habit_*` columns.
  - **WHOOP-derived habit names are FROZEN.** DB guard triggers RAISE on rename (map + journal level), and the sync route skips + surfaces blocked renames. Renaming one requires a coordinated migration (history rewrite + `hrv_analysis.py`/`causal_inference.py` hard-coded slug updates).
  - **The WHOOP era (cycle_date ≤ 2026-06-08, source='whoop') is IMMUTABLE** — guard trigger `zzz_block_frozen_whoop_era` rejects writes from every path; API routes also refuse with a clear error. Bypass for coordinated migrations only: `SET onyx.allow_frozen_writes = 'on'`.
  - **Date semantics across the cutover**: whoop-era rows keep `cycle_date` = WHOOP bedtime-day with a separate `behaviors_date` (bedtime−6h); post-cutover rows use `cycle_date` = behavior-day with `behaviors_date = cycle_date`. The **behaviors_date axis is continuous**; `cycle_date` is not. Behaviors-day **2026-06-08 is a permanent 1-day NaN hole** (final export covered through 06-07; the (2026-06-08, question) PK slots hold frozen rows) — do NOT "fix" it.
  - **Missing = unknown (NaN), post-cutover (policy REVERSED 2026-07-19; was missing=No 2026-06-11→2026-07-19)**: `hrv_analysis.py` no longer 0-fills unlogged `journal_*`/`habit_*` days — a missing row means "not logged", not "No". Explicit No rows map to 0.0 via `is_yes`; only explicitly answered days feed Welch No-arms, Spearman, and causal confounders post-cutover. The original 0-fill predated tri-state capture (absence was then the only way to express No); with explicit Yes/No rows and backdated grids, zero-filling would manufacture fake No days for unlogged gap weeks. Native daily habits' explicit-No backfill (AI, Lumosity, first completion → 2026-06-10) still stands as real data.
  - `pds.whoop_journal` is a **frozen archive** (write-blocked by trigger; kept as immutable backup of the original rows). The native 'Journaled' habit's 13 completions were merged into 'Journaled your thoughts?' (Yes-wins on behaviors_date; 6 No→Yes flips) and the habit retired.

- **Backdated habit completions trigger HRV retraining.** A Postgres trigger (`habit_journal_backfill_trigger`, defined in `sql/habit_journal_backfill_trigger.sql`) fires on every INSERT/UPDATE/DELETE on `pds.habit_journal` and emits a `pds.sync_log` row (`source='habit_journal', data_type='backfill_signal'`) whenever the affected `cycle_date` is in the past (ET). **No-op UPDATEs are suppressed (2026-06-11)** — the hourly sync's idempotent Last-Completed upserts previously fired 3 signals/hour, scheduling a full retrain EVERY hour (31 in 48h); the sync route also now skips the upsert when the completion row already exists. `hrv_backfill_check.py` reads this signal alongside its row-scan checks; either path setting `backfill_detected=true` triggers a full `hrv_analysis.py` retrain on the next hourly tick. The trigger covers paths the original row-scan missed: the UPDATE branch of upsert (which doesn't bump `synced_at` because the API call doesn't include it in the patch object) and DELETE (which leaves no row for `WHERE synced_at > last_analysis` to find — relevant when Riley undoes a backdated completion). Today's writes are deliberately suppressed by the trigger; same-day mutations are picked up by the daily safety-net retrain at 12:00 UTC instead, since an hourly retrain on every habit tap would be wasteful.

- **Causal inference layer (Phase 2.5 of `hrv_analysis.py`).** Lives in `causal_inference.py` and runs after the descriptive stats. Treatments span every controllable variable across all data sources — see "Treatment coverage" subsection below. For each treatment the layer estimates the ATE on next-night HRV three ways:
  1. **Naive** — Welch's `mean(Y|T=1) − mean(Y|T=0)`. Same number the existing `journal_impact` / `supplement_impact` / `habit_impact` charts show; included as the unadjusted baseline.
  2. **Propensity Score Matching (PSM)** — 1:3 nearest-neighbor matching on logit propensity from a logistic model fit on the confounders, ATT estimated as the mean within-pair Y difference, CI by paired bootstrap (B=500). Common-support trimming at propensity ∈ [0.05, 0.95].
  3. **AIPW (doubly robust)** — logistic propensity + two Ridge outcome models (one per arm), combined via the AIPW influence function. **Cross-fitting uses blocked 5-fold (`_blocked_folds`: contiguous calendar blocks, training excludes `AIPW_FOLD_GAP=7` rows on each side of the test block, a fold needs `MIN_FOLD_ARM=10` days per arm) with overlap trimming** (days whose cross-fitted propensity is outside [0.05, 0.95] are dropped from the mean, not clipped). Never shuffled KFold (audit F-001, 2026-05-26: shuffled folds let the outcome model see a test day's HRV through the next day's `hrv_lag1`; the 7-row gap closes that). Never forward-only `TimeSeriesSplit` either (2026-11-11): with drifting treatment prevalence its tiny early folds were nearly one-armed, the saturated propensity clipped at 0.95 still weighted those days ×20, and the never-scored first sixth of rows was averaged in as zeros, which produced the ±50–155 ms AIPW rows (live "viewed a screen in bed" −130 ms vs naive +3 / PSM +6; same frame with blocked folds: +13). ATE = mean of per-row influence values. **Plausibility guard** (`plausibility_flags`): a row is `implausible` (with `implausible_reasons`) when |AIPW| > 1 SD of nightly HRV, when it is > 0.5 SD from both naive and PSM, when > 50% of days were trimmed, or when > 2 folds were skipped; implausible rows never pass FDR (`fdr_suppressed_by_plausibility`). Test: `tests/test_causal_aipw_synthetic.py` (known effects on a drifting, level-shifted synthetic frame; runs in `stats-pr-check.yml`). **Two CIs reported alongside each other**: (a) IF-based via `sd(ψ)/√n`, the familiar form consumers expect; (b) **block-bootstrap CI** (`_block_bootstrap_ci`, 7-day blocks × 1000 reps) which resamples contiguous time slices of ψ to preserve autocorrelation the IF SE assumes is i.i.d. The per-treatment `aipw_bb_width_ratio = width(bb_ci) / width(if_ci)` flags treatments where IF SE is too narrow; verification on 108 treatments (`audit/aipw_shift_findings.md`) found median ratio 1.13 with 6 treatments diverging >1.5× (`body_battery_drained`, `medium_stress_duration_min`, `journal_felt_recovered`, etc.) — for those, trust the BB CI. Unbiased if either the propensity or the outcome model is correct.

  **Confounder set** is pre-treatment lag-1 only (`hrv_lag1`, `hrv_7d_mean`, `whoop_day_strain_lag1`, `whoop_sleep_duration_milli_lag1`, `rolling_7d_training_load`, `sleep_debt_7d`, `day_of_week`, `is_weekend`). Supplement family additionally gets `journal_have_any_alcoholic_drinks_lag1` and `caffeine_total_mg_lag1` (unified caffeine log — the WHOOP caffeine checkbox is disregarded by policy, 2026-06-10) because supplement-conscious days tend to differ in adjacent lifestyle. **Same-night sleep/recovery/HRV-derived variables are DELIBERATELY EXCLUDED** — they are mediators on the very causal path being estimated; adjusting for them would block the effect (mediator-adjustment bias). The reported quantity is therefore the **total effect** (which includes the sleep-quality channel) — the actionable answer for "if I take magnesium tonight, what happens to my HRV tomorrow?" **Per-treatment exceptions live in one function, `adjustment_set()`** (2026-11-13; each result row stores the outcome as `confounders_used`): multi-day rolling treatments (`ROLLING_AGGREGATE_TREATMENTS`: 3-day / 7-day load, Garmin acute / chronic load and their ratio) drop `hrv_lag1`, `hrv_7d_mean`, `whoop_day_strain_lag1` (mediators inside the window), and a rolling treatment also drops an aggregate whose day window contains its own (`ROLLING_WINDOW_DAYS`: the 7-day total for the 3-day load; estimand in `ROLLING_TREATMENT_ESTIMAND`). `total_training_load` is one day's sum, so it is a daily treatment with the full set. Test: `tests/test_causal_adjustment_sets.py`.

  **Sensitivity** via the VanderWeele & Ding (2017) E-value — minimum strength on the risk-ratio scale that an unmeasured confounder would need (with both T and Y) to fully explain the estimate away. Continuous outcome → Cohen's d → RR via Chinn (2000): `RR ≈ exp(0.91·d)`, then `E = RR + √(RR·(RR−1))`. Higher = more robust to unmeasured confounding.

  **GPS-based TZ auto-population** (ADR-0001 Phase 4 step 4): `gps_tz_backfill.py` scans `pds.garmin_activities` for `(start_latitude, start_longitude)` and inserts new `pds.user_tz_log` rows whenever the GPS-inferred IANA TZ disagrees with what `pds.tz_for_instant` currently returns.   **WHOOP-cycle-based TZ auto-population** (ADR-0001 Phase 4 step 4 extension): `whoop_tz_backfill.py` is the companion path for trips where Garmin GPS doesn't fire (rest trip, no outdoor activity, watch off). Runs automatically at the end of `whoop_etl.py`. Every WHOOP cycle ships a `timezone_offset` (e.g. `-06:00`) — the script detects cycles whose offset disagrees with `pds.tz_for_instant`'s current resolution and inserts new `user_tz_log` rows. Since WHOOP gives offset only (not IANA), the script picks the most-common IANA for that offset from Riley's MANUAL `user_tz_log` entries (history-derived), falling back to a generic offset → IANA map. Same-offset cases skip (no behavioral difference). The notes field tags every auto-insert (`whoop-auto: cycle <id> offset <off>; <provenance>; log was <prior_tz>`) so they're distinguishable from manual entries — and the history-derived defaults computed from ONLY manual entries to avoid bootstrap bias.

GPS gives exact IANA when available; WHOOP gives offset always. Together they cover essentially every realistic trip without manual maintenance — manual SQL is only needed if both devices are left at home.
- **Supplement intake — behavioral-day convention (NOT clock date).** A `pds.supplement_intake` row's `intake_date` should reflect the **day the intake belongs to behaviorally**, not the wall-clock date of the moment it was taken. A pre-bed supplement consumed at 12:05 AM ET — *before* the user has slept — belongs to the day that just ended, not the new clock date. Rationale (three converging reasons):
  1. **WHOOP cycle alignment.** WHOOP defines a "day" by bedtime-to-bedtime spans (see the `+12h` cycle rule above). The awake-tail period after midnight but before sleep is part of the *previous* cycle, not the new one. Treating supplements the same way keeps the journal × cycle × intake triple consistent.
  2. **HRV pipeline correctness.** The pipeline scores day-N behaviours against row N's own HRV — the sleep that closes behavioral day N (`hrv_alignment.py`). A pre-bed supplement affects the *immediately following* sleep, which is exactly row N's sleep, so the intake must be on row N. A naive clock-date attribution at 12:05 AM would put it on row N+1 and score it against the night after — silently mis-training the model.
  3. **Stack consistency.** An "evening stack" (mag, melatonin, etc.) that sometimes lands at 11:55 PM and sometimes at 12:05 AM should not split across two rows of `daily_health_matrix` based on a 10-minute clock crossing that has no biological meaning.

  **MyFitnessPal — log on behavioral day via manual backdate (decision 2026-05-25).** Earlier versions of this file said MFP follows "literal clock date" for energy-balance reasons. That was correct under one interpretation (clock-anchored calorie totals) but Riley's PRIMARY use of MFP is HRV/recovery analysis (mfp_* macro features feed `hrv_analysis.py`). For that use case, clock-date attribution creates the same awake-tail misalignment the ADR-0001 rewrite eliminated for every other source: a 1 AM heavy-fat meal would land on the wrong row vs. the HRV measuring its effect. Convention going forward:
  - **When logging a meal in MFP between 00:00 and ~5 AM ET that is genuinely pre-bed (your awake-tail), backdate it to yesterday in the MFP date picker.** The trip is "did I eat this meal before today's behavioral day ended?" — answer yes → log under yesterday.
  - The MFP daily-totals UI will look uneven on backdate days (yesterday shows ~2700 cal, today shows ~1800). That's the cost; the analytical correctness is the benefit.
  - The Onyx side requires no code change: the trigger sets `onyx_behavioral_date = calendar_date`, so behaviorally-logged MFP rows are correctly behavioral-attributed.
  - For pure energy-balance questions ("did I hit 180g protein on May 22?"), MFP's daily totals will reflect Riley's BEHAVIORAL day (May 22 = 10 AM May 22 → 1 AM May 23 clock-time), which is the right semantic for that question too (your fasting window starts at sleep, not at midnight).
  - For the temporal "when did I eat" question, `pds.meal_events` remains the source of truth (it has timestamps; MFP's standard CSV export does not).

  **Operational implications:**
  - `pds.supplement_intake.intake_date` is the canonical join key (behavioral day, ET).
  - `pds.supplement_intake.intake_time TIMESTAMPTZ` stores the truthful clock instant — kept independent of `intake_date` so a 12:05 AM May 21 click attributed to May 20 keeps the accurate timestamp without losing the date semantics.
  - `/supplements` UI: **the behavioral attribution is automatic — log in real time and just tap.** The quick-tap flow (and `POST /api/supplements/log-intake`, and `logStackIntake`) defaults `intake_date` to `pds.behavioral_today_now()` — TZ-aware (travel, via `user_tz_log`) AND awake-tail-aware (−6h rule), so a 12:30 AM pre-bed dose lands on yesterday with zero manual action — while `intake_time` records the truthful clock instant. **Do NOT manually "correct" the pre-filled date to the clock date after midnight** — that breaks behavioral attribution and trips the caffeine layer's timestamp-trust quarantine. The manual date override exists for RETRO-logging only (remembered a dose from days ago); note retro-logged doses keep `intake_time` = "now", so they count toward mg totals but are excluded from timing aggregates by the trust rule. EditIntakeModal supports retroactive date adjustment for past intakes.
  - When ingesting historic supplement logs from any other source (Apple Health, manual CSV), the importer must apply the same rule.

(3) The address of that tab is pasted into the card → `POST /api/spotify/exchange` (`{callback}`; the full address, the query alone or the bare code; the address and the query must carry their state) checks same-origin + JSON + a 4 KB cap, compares the pasted state with the cookie (constant-time; the cookie is cleared after one attempt, except when Spotify's token endpoint did not answer, so Finish can be pressed again; only a bare code carries no state and is accepted on the cookie being present), exchanges the code server-side, requires a refresh token and both scopes, makes ONE `recently-played` call with the new token and only then stores the blob.   - **`Title`** (title): short, specific, 3–8 words. Scannable in a list. Avoid generic titles like "Journal Entry" or "Note".
  - **`Date`** (date): today in `America/New_York`, date-only. Override if the user names a different date ("yesterday", explicit date).

  **Body — VERBATIM RULE.** The page body MUST be the user's raw text exactly as they said it. Do NOT summarize, paraphrase, condense, restructure, rewrite for clarity/flow/grammar, remove tangents/repetition/filler, add headings or bullet structure the user didn't provide, or add narrator framing ("Today Riley reflected on…"). The journal is a primary-source record of the user's own words. The ONLY editing allowed: sentence-ending punctuation + commas at clear speech pauses, paragraph breaks at natural topic shifts, capitalization, and unambiguous dictation-typo fixes (e.g. "their"/"there"). The `Title` is where summarization belongs — never let title-style condensation leak into the body. If the user explicitly asks for a summary ("just summarize this", "give me the gist"), summarize — otherwise the body is verbatim.

- **Every Python script that writes to Supabase emits a `pds.sync_log` heartbeat on EVERY run** — success AND failure, including uncaught exceptions. The audit caught silent retrain failures because `hrv_analysis.py` lacked a heartbeat, so its crashes were invisible to `/status`. Pattern: wrap `main()` in try/except in `if __name__ == "__main__"`, call `log_sync_entry(status='success'|'failed', records=N, error=str|None, duration=T)` in both branches. Without this, downstream effects (predictions, dashboards) keep looking healthy via cached state while the upstream pipeline is broken.
- **All date arithmetic in the HRV pipeline uses ET, never naive `date.today()`.** Both `hrv_predict.py` and `hrv_analysis.py` define `et_today()` (`datetime.now(ZoneInfo("America/New_York")).date()`) and use it for `prediction_date`, `MODEL_VERSION`, and every "today"/"tomorrow". A naive `date.today()` returns the **UTC** date, so a late-ET-evening CI run (already the next UTC day) mis-tags by +1. `hrv_analysis.py` had exactly this bug — its `_behavioral_v1` retrain rows got `prediction_date`/`model_version` = ET **+2** on evening runs (e.g. a forecast meant for tomorrow tagged day-after-tomorrow), which then dragged the `/status` freshness anchor into the future and showed every fresh source as "Degraded". Fixed 2026-06-06: ET-anchored `hrv_analysis.py`, deleted the 455 spurious rollover rows, and added a `pds.hrv_predictions_latest` tiebreak so the canonical `_v1` predict path always wins over `_behavioral_v1` for the same `(prediction_date, model, horizon_days)`. The `/status` freshness anchor (`spineMaxDate`) also no longer includes any prediction date — freshness must track observed data, never a forecast.
- **HRV alignment rule — one place: `hrv_alignment.py` (fixed 2026-11-10).** Row D of `pds.daily_health_matrix_behavioral` is behavioral day D, and its `whoop_hrv_rmssd` is the HRV of the sleep that CLOSES day D (WHOOP cycle dated by sleep onset − 6 h). Every consumer — Spearman / Welch / Granger / OLS, the causal layer, XGBoost, SARIMAX, Prophet and the backtest — scores a day-D behaviour against the SAME row's HRV via `al.add_outcome` / `al.outcome_series` (horizon h = the sleep closing day D+h−1). **Never build an outcome with `.shift(-…)` in the pipeline files** — the live test greps for it. Three column groups sit on another day in the matrix and are re-keyed by date in `al.realign_matrix` before any feature is derived (live checks 2026-11-10): WHOOP cycle totals (`whoop_day_strain`, `whoop_kilojoule`, `whoop_cycle_avg/max_hr`) describe the waking day AFTER row D's sleep (strain row D vs workouts row D+1 r=0.83, same row −0.01) → moved one day later; `eight_sleep_*` and `garmin_hrv_*` are keyed by the wake-up day (the previous night sits on row D; r=0.84 / 0.82 with WHOOP one row earlier) → moved one day earlier; the pandas merges of `garmin_sleep` / `garmin_hrv` / `eight_sleep_trends` extras go through `al.wake_date_to_closing_day`. `whoop_steps` (a WHOOP cycle total merged in pandas, not a matrix column) is dated from each cycle's own local start by `al.cycle_waking_day` (= cycle date + 1 for a night-time onset), cycles on one day summed. Garmin daily summary / stress / zones / training status stay on the clock day (activity = day D, overnight fields = the night before day D — both before row D's sleep). Garmin activities and WHOOP workouts are keyed on `onyx_behavioral_date`. Columns measured from the outcome sleep or anchored to its onset (`al.is_same_sleep`, `al.NEEDS_SLEEP_ONSET`) are mediators for the causal layer and never forecast inputs; other measurements of that night's HRV / RHR (`al.OUTCOME_TWINS`) are left out of the Spearman driver ranking. **The forecast** predicts from behavioral today's row (`al.serve_index`, ET − 6 h): tonight's sleep, the HRV Riley wakes up to tomorrow. `pds.hrv_predictions.prediction_date` = the behavioral date of the predicted sleep (same key as the matrix, the backtest and SARIMAX / Prophet; `actual_hrv` = matrix row `prediction_date`), and `/analytics/hrv` shows the wake-up date (+1). The model pickle carries `alignment = al.ALIGNMENT_VERSION`; `hrv_predict.py` refuses a pickle from another rule. **Runtime guard** (`check_alignment` at the start of every retrain): a row whose HRV ≠ the recovery of the WHOOP cycle dated to it, or a re-keyed column that lines up with an adjacent row, fails the run (`GUARD hrv_alignment:` failed heartbeat); the alcohol canary (drinking must lower the same night's HRV more than the next night's) writes a `GUARD alcohol_canary:` partial heartbeat if it reverses. History: `b0828fa` (2026-04-04) introduced `shift(-1)`, correct under the old wake-day matrix; ADR-0001 (`165b879` + `a04d35e`, 2026-05-25) re-dated the matrix and left it, so from 2026-05-25 to 2026-11-10 every behaviour was scored against the night after the one it preceded (the re-audit's "DISPUTED P0", gemini F-001). Findings from that period are void; `pds.hrv_analysis_results_pre_alignment_20261110` holds the last pre-fix snapshot for comparison. Brief: `docs/handoff-hrv-alignment-2026-11-10.md`. **Dashboard side of the cutover (2026-11-11, `lib/hrv-forecast-cutover.ts`):** live rows in `pds.hrv_predictions_latest` with `prediction_date` < 2026-11-10 were made under the old one-night-late pairing; the walk-forward backtest rows are re-run by every retrain, so they follow the current rule. The Prediction-vs-Actual chart marks the first same-night forecast with a dashed line and a caption, draws no red miss-dots on old-pairing points, and the Residual Distribution histogram (`getHrvResiduals`, read from `hrv_predictions_eval` so rows carry `model_version`) leaves out nights whose only row is an old-pairing live forecast. It must NOT read `hrv_predictions_latest`: that view prefers a live row over a backtest row, so on ~170 dates it would serve the old-pairing live row and hide the same-night backtest residual the retrain rewrote (histogram 521 → 337 nights); `_eval` keeps the newest row, which is the backtest one (checked 2026-11-11: 514 backtest + 1 same-night live counted, 6 old-live-only nights left out). Any new frontend accuracy number built from forecast rows goes through `splitComparable` / `isSameNightComparable`.
- **Audit and review findings are settled against the data, never against docs or tests (2026-11-10).** A finding that claims wrong results may be closed as refuted only by a check on live data or by running the code. This file, the audit CONTEXT files and the existing tests are what such a finding disputes, so they are not evidence against it. Anything left DISPUTED or unverified when an audit or review ends becomes a roadmap row in the same session (Tasks DB, `Source = "Onyx Roadmap"`) at the audit's severity (P0 → `Critical`, P1 → `High`), with what would settle it in Notes. ### Smoke testing (Playwright)

Production tripwire for the class of bug `tsc` + `lint` cannot catch: a panel that **should** have data silently falling back to its empty state. The Spotify FK-ordering, HRV `JSON.parse`-of-jsonb, and supplements renamed-column regressions all shipped green and only surfaced when Riley clicked around production — each as an empty/broken panel.

- **Core principle:** *empty-state fallback present where data should exist = test failure.*
- **What it covers:** loads every dashboard page against **real production data** (authenticated) and asserts (a) the page isn't bounced to `/login` and doesn't hit the Next.js client error boundary, (b) a real data element rendered (recharts data marks / table rows / journal list items), and (c) **known empty-state fallback strings are ABSENT**. Two pages get precise assertions: `/analytics/hrv` (HRV Correlates draws bars + none of the "…not yet computed" / "Run hrv_analysis.py to compute correlations" fallbacks) and `/supplements` (the "Today's compound totals" table is populated whenever `/api/supplements/today` reports intakes — the test self-skips on a legitimately empty day rather than false-fail). Strings that can be legitimately empty (ReccoBeats-thin Spotify subsets, manual-entry meal/weight sections, range-windowed lists) are intentionally **not** asserted.
- **Files:** `frontend/playwright.config.ts` (single chromium project, `retries:1`, reuses a saved `storageState`), `frontend/e2e/auth.setup.ts` (logs in once via `/login`, saves `e2e/.auth/state.json` — gitignored), `frontend/e2e/smoke.spec.ts`. The `e2e/` dir + `playwright.config.ts` are excluded from `tsconfig.json` so they don't affect `next build`.
- **Run locally:** `cd frontend && npx playwright test` (add `--ui` to watch / debug). Defaults to the prod Vercel URL via `SMOKE_BASE_URL`.
- **Required env** (3 vars) — read from `frontend/.env.local` locally and from **GitHub repo secrets** in CI: `SMOKE_TEST_EMAIL`, `SMOKE_TEST_PASSWORD`, `SMOKE_BASE_URL`. (The login uses Supabase Auth email+password; use a real app account.)
- **Scheduled-workflow keepalive:** GitHub auto-disables every cron workflow after 60 days without a push (happened 2026-09-18 → 2026-10-03 outage). `.github/workflows/keepalive.yml` runs Mondays 12:00 UTC and re-enables every workflow via the Actions API, which resets that clock without a dummy commit. If Onyx goes quiet, `gh workflow list --all` and look for `disabled_inactivity` first.
- **CI:** `.github/workflows/smoke-test.yml` runs every 6h (`0 */6 * * *`) + `workflow_dispatch`. A failure = red X + GitHub's failure email (the alert); CI keeps no Playwright trace, screenshot or HTML report and uploads no artifact (the repo is public and those hold signed-in pages); reproduce a failure locally with `npx playwright test`, where traces and screenshots stay on.
- **Adding a page:** append to the `PAGES` array (or add a dedicated `test.describe`) in `smoke.spec.ts`. For a manual-entry page whose own in-window empty-state is legitimate (e.g. `/caffeine` after a logging pause), set `legitimateEmpty` to that exact string — the test then SKIPs with a reason instead of failing; `/caffeine` additionally honours `?days=N` (7–730; the ISR seed is discarded for non-default windows) and a dedicated test loads `/caffeine?days=720` to assert the intake chart draws from real historical rows; note the shared Sidebar sparkline is a recharts svg, so the generic "charts" probe alone cannot tell "page empty" from "chart broke". Prefer text-absence of the real empty-state string + a "some data element exists" check over brittle per-element selectors.

## Health & appointments (2026-11-13)

`/health` is a care planner (due-soon list, month / agenda calendar with projected repeats), not a medical record. Items are stored in **`pds.care_items`** (`sql/care_items_schema.sql`): label, kind, calendar date + optional wall-clock time + the IANA zone that time is in (stored as written, never converted, so 9:00 stays 9:00 across a DST change), "repeat N months after completion", note, booked / archived / last-completed, `removed_at` (soft removal; the app never physically removes a row) and `import_key`. **Service-role only** (RLS on, no policies, nothing granted to anon / authenticated): the page is `force-dynamic` (no ISR, `noindex`) and reads through `lib/care-items-server.ts` (`server-only`); the browser writes through **`/api/care/items`** (GET, POST), **`/api/care/items/[id]`** (PATCH, DELETE = soft removal, PATCH `{removed:false}` = Undo) and **`/api/care/items/import`** (the one-time, idempotent copy of the old browser-only planner, keyed on `import_key`). Those routes are owner-session only (never add `/api/care` to `isCiRoute()`), same-origin, JSON, size-capped, strict about unknown fields; errors and logs carry a database code only, never item text, and nothing is written to `sync_log`. Writes are optimistic per item and revert only that item on failure (`applyOp` / `revertOp` / `inverseOp` in `lib/care-items.ts`); load failure, empty list and data are three different states. Date, repeat and time-zone logic is pure in `lib/care-planner.ts`. Sample data is display-only and is refused by the API. Not an ingestion source, so no `/status` card; Today is not wired. Docs: `docs/health-appointments.md`. Tests (synthetic only): `cd frontend && node scripts/test-care-planner.mjs && node --test tests/care-items.test.cjs`.

**Google Calendar sync (built 2026-11-13, NOT connected until Riley sets it up; steps in `docs/health-google-calendar.md`).** One way, Onyx to Google, with exactly ONE scope, `calendar.app.created` (Onyx can only touch calendars it created: never Riley's own calendars, never Gmail; do not add a scope). Onyx creates one calendar ("Onyx care") and keeps one event per active care item (label, date / time / zone, booked state; notes are never sent; no recurring events). Pure logic in `lib/care-google.ts` (`eventForItem`, `runSync` against a `CalendarApi` interface); server part in `lib/care-google-server.ts`; routes `/api/care/google/{status,start,callback,sync,disconnect}` are owner-session only. **Nothing calls Google unless `GOOGLE_CALENDAR_CLIENT_ID` + `GOOGLE_CALENDAR_CLIENT_SECRET` exist in Vercel AND a refresh token is stored** (`pds.ci_tokens`, `service='google_calendar'`); without the env vars there is no database call either. Sign-in is authorization code + PKCE with a `state` bound to a 10-minute httpOnly cookie scoped to the callback path; a grant with any other scope is revoked and not stored. Every event carries the private extended property `onyxCareItem=<item id>`, and an event is read and that tag checked before any rewrite or removal, so Onyx never edits an event it did not create. State lives in `pds.care_calendar_sync` (one row: calendar id, connected-at, last result as counts + a short code) and `pds.care_calendar_links` (item to event id, generation, digest; rows are kept and marked `gone`), both service-role only (`sql/care_calendar_sync_schema.sql`). A sync runs via `after()` on every care-item write and from Sync now; results are not written to `sync_log`. No `/status` card yet (add one once it is connected). ## Financials (2026-11-12)

`/financials` reads a persisted Rocket Money ledger: `pds.finance_accounts`, `pds.finance_transactions` (`txn_key`; **`amount_cents` is expense-positive**, purchases +, income and refunds -; a non-empty `ignored_from` excludes the row) and `pds.finance_balance_snapshots` (per account, `captured_at`, `balance_cents`, `kind` asset|liability|null). A Rocket Money importer and daily harvester fill them and write `sync_log` heartbeats `rocketmoney|transactions` and `rocketmoney|balances`. **Transactions are keyed on Rocket Money's own transaction id (`source_txn_id`, `sql/finance_source_txn_id.sql`, partial unique index), not on the name or the amount**: the daily harvester reads the Transactions list from inside the signed-in app (no email, no export button; pending rows skipped) and upserts by that id, attaching the id to an export-origin row with the same (account, date, amount) instead of inserting a twin, or inserting with `txn_key` = sha256(`rmid|`+id) first 32 hex; the 7,009 export rows were tied to their ids once by `tools/rocketmoney_harvest/reconcile-ids.mjs` (6,997 matched; the n-th row of a same-day group in the file takes the n-th smallest id). `import-csv.mjs` stays for manual backfills and inserts only the surplus of CSV rows per (account, date, amount) group so a re-import cannot duplicate web rows. **The tables are SERVICE-ROLE ONLY** (RLS on, no policies, no grants to anon/authenticated, like `phone_usage_*`): the browser never queries them, the only reader is `lib/finance-ledger-server.ts` (`server-only`, service role, explicit column lists, 1000-row count-driven paging) called from the server page behind the owner-only middleware, no chat/LLM tool reads finance data, and nothing logs rows (errors log a code only). **The page is `force-dynamic`, deliberately NOT ISR** (private data: no CDN or shared cache, `noindex`); do not copy the ISR pattern here. Logic is pure and unit-tested in `lib/finance-ledger.ts`: money in/out exclude the one `NON_SPENDING_CATEGORIES` constant (Internal Transfers, Credit Card Payment, Savings Transfer) and ignored rows; refunds count as money in; net worth subtracts liabilities by absolute value; a balance with `kind` null is shown as unclassified and left out (never guessed from the account type); non-USD is never mixed into USD totals; balances older than 48 h get a stale badge. The page keeps empty ledger, failed query and data as three different states. `/status` card **Rocket Money** (badge ROCKET MONEY, automated, `lib/finance-status.ts`): worst of the two heartbeats, more than 36 h degraded, more than 72 h or a failed/error run red with the importer's own error text (e.g. login required); heartbeats only, no amounts reach that cacheable endpoint. The browser-memory CSV workspace (PR #28) stays as a secondary "Preview a CSV" disclosure; it does not touch the ledger. Riley accepted the Rocket Money terms risk for the automated harvester on 2026-11-12, for a once-a-day visit; the 2-hourly keep-alive schedule (below) raises that to up to 12 visits a day, and Riley re-confirms the acceptance for that frequency before the scheduled task is switched to every 2 hours (see `docs/financials-rocket-money.md`, "Terms note"). Keep real finance data out of tests, screenshots, PR text and logs (the repo is public). Tests: `cd frontend && node --test tests/finance-ledger.test.cjs tests/finance-ledger-view.test.cjs tests/finance-ledger-server.test.cjs && node scripts/test-financials.mjs`.

**Rocket Money sign-in (2026-11-13, `tools/rocketmoney_harvest/lib/session.mjs` + `lib/browser.mjs`, README "Staying signed in").** The web sign-in is one short rolling cookie held by Rocket Money's API (reported as about 3 h 48 min after the app was last used; gone 8 hours after the 2026-11-11 sign-in), so the once-a-day harvester was signed out every day. Behind it, the sign-in service's cookies (`auth0` / `auth0_compat` on `auth.rocketaccount.com`) are **persistent, about 72 h** (in the profile, kept across restarts), yet the silent renewal was answered `login_required` once while the PC was awake, so the refusal is most likely the service's own. The task runs **every 2 hours** (well inside both 3 h 48 min and 72 h; a test pins it): a run imports once 20 hours have passed since the last import, the runs in between are keep-alive visits (open the app, write nothing to the ledger, one `rocketmoney|keepalive` heartbeat: success, partial on the first failed visit in a row, failed from the second; the `/status` card counts it only when newer than both import heartbeats and never as freshness). **The read-only guard is attached before any page can load:** Chrome is never asked to re-open old tabs (no `--restore-last-session`); a profile set to "Continue where you left off" has its saved tabs moved to the Recycle Bin before Chrome starts and the setting switched back (`lib/browser.mjs`). A visit counts as signed in when the Net Worth data arrives and as signed out only when the page rests on a sign-in screen (the silent renewal passes through redirect hops first); a refused transactions read after a signed-in landing is a transactions failure, not a sign-out (keep-alive goes on). A lost sign-in is reported at once by whichever run finds it: `login required: run node harvest.mjs --login; at <where>; silent renewal: <answer>; last signed in X h ago; sign-in lasted Y h; ...` (failed heartbeat for both data types; while signed out the sign-in page is re-opened only after 20 h, with `--force`, or once the profile was used). Sign-in is `node harvest.mjs --login` (a plain Chrome window; Riley signs in and closes it; the harvester then runs once). **Expected, not yet proven:** a sleep longer than the app cookie's lifetime ends the sign-in (a keep-alive cannot run while the PC sleeps); the first `signed in:` / `FAILED: login required` line after a long sleep settles it. Durable ways out if so: an always-on machine, another source (SimpleFIN), or `register-task.ps1 -Wake` (off by default; it would wake a closed laptop). Tests: `node --test tools/rocketmoney_harvest/test/*.test.mjs`.

## Focus habit unlock (2026-11-13)

The Onyx Focus iPhone build (`tools/screentime_ios`, `project-focus.yml`; spec and limits in `tools/screentime_ios/FOCUS.md`, phone test steps H0 to H6 in `docs/focus-device-test.md`) can unlock its app block from real habits.
